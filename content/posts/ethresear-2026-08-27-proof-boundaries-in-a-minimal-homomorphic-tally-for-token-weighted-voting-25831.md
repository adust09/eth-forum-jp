## 動機

準同型集計 (Homomorphic tallying) は簡単に要約できます。各投票を暗号化し、暗号文を合計し、その合計を復号します。より難しいのは、その合計が単なる有効なグループ計算ではなく、選挙を表すために証明が何を正確に拘束しなければならないかを特定することです。

私はトークン加重投票の単独研究実装であるCommitraを構築し、イーサリアムのSepolia上でエンドツーエンドで実行しました。これは2つのGroth16回路、BabyJubJub ElGamal、ブラウザサイドでの証明生成、リレーヤー、および100の固定集計バッチを使用しています。その結果は、機能する最小限の実装であると同時に、実装が行うこと、その証明が拘束すること、そして正直なクライアントまたはコーディネーターに依然として依存することの間のギャップを具体的に示したマップでもあります。

完全なソース、仕様、ビルド手順、アーティファクトハッシュ、および記録されたSepoliaでの実行はここにあります。

EVM上でのプライバシー保護型トークン加重投票: 準同型集計、Groth16、Sepolia。正確な証明スコープマップを備えた単独研究実装。

公開されていない3回の独立したコードレビューにより、以下の証明境界に収束しました。私は彼らの共通の知見を用いて、設計意図ではなく、強制される内容を中心に公開仕様を書き直しました。

## 先行研究とスコープ

[[MACI (Minimum Anti-Collusion Infrastructure)|MACI]]は共謀防止に焦点を当てており、異なる脅威モデルを持っています。ここでの参照点はMACI v3.0.0です。
そのリポジトリは2026-08-19にアーカイブされました。
VocdoniのDAVINCIは、準同型投票集計と集計復号化の最も近い先行研究です。
この投稿は比較や新規性の主張ではありません。これは、最小限の実装を使用して、その証明境界と失敗モードを検査可能にすることを目的としています。

## 実装された内容

各`voteId`について、サーバーは重みスナップショットへのEOAを保持します。投票者はウォレットで署名し、BabyJubJubキーと秘密のシークレットを導出し、Merkleリーフにキーと重みをコミットし、そのリーフをコーディネーターが受け入れたルートの下に登録します。

ブラウザでは、標準クライアントがYES、NO、またはABSTAINのいずれか1つに`weight`を暗号化し、他の2つの選択肢にはゼロを暗号化します。その後、Groth16投票証明を生成します。コーディネーターは証明をオンチェーンにリレーするため、参加者のEOAは意図された投票提出パスから除外され、参加者はガスを支払う必要がありません。

投票終了後、実装はプライベートDBバッチを100の暗号文セットにパディングし、それらを準同型的に合計し、有界なBSGS離散対数で集計を復号し、集計証明を生成し、3つの結果シグナルをオンチェーンに保存します。実装された集計パスは個々の投票ではなく集計を復号しますが、現在のコーディネーターは単一の秘密鍵を保持しており、技術的には投票を復号できます。

2つの回路ソースは、著者の開発リポジトリに2025-12-31までにすでにコミットされていました。リポジトリの[[PROVENANCE document|PROVENANCEドキュメント]]は、その開発記録を後の公開リリースと区別し、デプロイアドレスとアーティファクトハッシュをリストしています。

## 証明が実際に拘束するもの

以下の表は、意図されたプロトコルではなく、現在の回路について説明しています。

### 投票証明

| 今日拘束されているもの | 今日拘束されていないもの |
| --- | --- |
| リーフはコントラクトが受け入れたルートの下にある | 受け入れられたルートが意図されたEOAと重みスナップショットから来たものか |
| リーフは内部的にBabyJubJub公開鍵と(重み、秘密の重み)にコミットしている | 提出されたEOAがリクエスターによって所有されているか、コミットされた重みがそのスナップショットの重みに等しいか |
| `voterID`と`nullifier`は回路に提供された秘密のシークレットから導出される | `nullifier`がリーフまたは署名キーによって一意に決定されるか |
| 正確な`nullifier`は`voteId`ごとに1回のみ使用可能であり、オンチェーンで強制される | 投票者ごとに1票 |
| リーフにコミットされたEdDSAキーは、暗号文ハッシュ、`voteId`、`chainId`、`voterID`、および`nullifier`を含むハッシュに署名した | 暗号文がElGamal方程式を満たしているか |
| 対応する制約なし | 各平文が`{0, weight}`に含まれ、正確に1つの選択肢が完全な重みを持つか |

回路とは別に、サーバーは提出された暗号文座標のPoseidonハッシュを再計算し、リレーする前に`publicSignals[3]`と照合します。

サーバーは現在、非正規、曲線外、小部分群、および同一の`C1`ポイントをリレーする前に拒否します。これはサーバー側の緩和策であり、回路のギャップは残っています。有効な部分群ポイントは、証明が拘束しない平文を依然としてエンコードできます。

二重投票の境界も同様に狭いです。正確なナリファイアの再利用はオンチェーンで拒否されますが、ナリファイアはリーフに拘束されません。変更されたクライアントは、新しいプライベートナリファイアシークレットを選択し、同じリーフから別の有効な証明を生成できます。

### 集計証明

| 今日拘束されているもの | 今日拘束されていないもの |
| --- | --- |
| プライベートバッチには正確に100の暗号文セットが含まれ、`encryptedBatchHash`にハッシュされる | バッチがオンチェーンに提出された投票とダミーの正確な順序付きセットであるか |
| 公開集計グループ要素がそのプライベートバッチの準同型和である | ダミーハッシュがゼロ重みパディングを表すか。コントラクトは`registerDummyVotes`が1回呼び出されたことのみを記録する |
| 各公開集計スカラーが、設定された公開鍵の下で復号された集計グループ要素にマッピングされる | スカラーがサポートされる集計範囲内で一意の正規整数であるか、または3つの結果が範囲と合計の制約を満たすか |
| `coordinatorPubkey`が回路内の秘密鍵から導出され、コントラクトによって設定された座標と照合される | 証明が`voteId`、`chainId`、またはコントラクトデプロイメントに拘束されるか |

`voteId`ごとの結果ストレージはドメイン問題を解決しません。`voteId`とデプロイメントIDが集計の公開入力に存在しないため、残りの状態チェックがパスした場合、証明は別のクローズされた、ダミー登録された`voteId`にリプレイされる可能性があります。

また、整数表現の境界もあります。集計回路は、提供されたスカラーが復号されたBabyJubJubポイントにマッピングされることを証明します。意図された投票範囲内で一意の正規スカラーを強制せず、コントラクトは範囲または合計チェックなしで結果シグナルを保存します。

## 見落としがちだった4つの落とし穴

### 1. ハッシュバインディングは意味論的有効性ではない

証明内で暗号文座標をハッシュすることは、証明をそれらの座標にバインドします。しかし、それがコミットされた重みの暗号化であること、正確に1つのオプションが選択されたこと、あるいはサーバーサイドチェックが追加される前にポイントが有効であったことさえ証明しません。

ElGamal暗号化には公開鍵のみが必要です。変更されたクライアントは、任意の値を暗号化するためにコーディネーターの秘密鍵を必要としません。ポイント検証は不正な入力クラスを1つ削除しますが、有効なポイント上の任意の平文は依然として回路の問題です。

### 2. 決定論的なクライアントの振る舞いは回路の制約ではない

標準クライアントはウォレット署名から[[nullifier|ナリファイア]]シークレットを決定論的に導出するため、正直な再試行は同じ[[nullifier|ナリファイア]]を生成し、オンチェーンで失敗します。しかし、回路は[[nullifier|ナリファイア]]シークレットを自由なプライベート入力として受け入れます。証明は提供されたシークレットからの導出を検証しますが、そのシークレットがリーフに一意に結びついていることは検証しません。

この区別により、正確な[[nullifier|ナリファイア]]の単一使用は、1投票者1投票よりも弱いものになります。

### 3. あるバッチの正しい集計は、提出されたセットの集計ではない

集計証明は、Poseidonチェーンされたプライベートバッチ、その準同型和、およびその集計復号表現をチェックします。コントラクトは`VoteSubmitted`およびダミーイベントからそのバッチを再構築しません。したがって、コーディネーターが証人バッチを選択します。

ダミー登録も同じ境界を持ちます。投票コントラクトは任意のハッシュを受け入れ、それらを発行し、ブール値を設定します。集計の最終化はブール値をチェックし、パディングの内容や数をチェックしません。

結果の周りに`voteId`ストレージを追加しても、証明はその投票にバインドされず、グループの等価性だけでは1つの正規の整数結果を選択しません。バッチの同一性、証明ドメイン、およびスカラー範囲は別個のステートメントです。

### 4. オフチェーンのプライバシーはオブザーバーに依存する

リレーされたトランザクションパスは、参加者のEOAを投票のコールデータやイベントから除外します。これはチェーンオブザーバーに対する具体的な特性です。

これはサーバーの非リンク可能性ではありません。サーバーはEOAと重みスナップショットの行を保存し、トークンの順序、タイミング、接続メタデータ、ログを通じてEOA、リーフ、および後の公開コミットメントを関連付けることができます。また、現在、提出されたEOAの所有権を検証していません。標準フローのウォレット署名はプライベートクレデンシャルを導出しますが、認証証明としてサーバーに送信されません。

方向性: 短期的なサーバー強化フェーズでは、EOAごとの認証済み入場を導入し、その後、回路レベルでの適格性と重みバインディングを行います。

## 現在の信頼仮定

単一キーコーディネーターの信頼モデルは、ElGamal秘密鍵の所有以上のものです。承認されたコーディネーターは現在、以下のことが可能です。

- 個々の暗号文を復号する（ただし、実装された集計パスは集計のみを復号する）
- 投票のリレーを拒否する
- スナップショットにバインドすることなく、ゼロを含む任意のルートを承認する
- オンチェーンの期限、クォーラム、または最小カウントがないため、投票を即座かつ不可逆的に終了する
- ルート失効機能がないため、以前に受け入れられたすべてのルートを保持する
- 任意のハッシュまたは空の配列でダミー登録フラグを設定する
- プライベート集計バッチを選択する
- 互換性のある`voteId`またはデプロイメント間で集計証明をリプレイする
- 正規の範囲や合計の制約なしに集計スカラーを公開する

デプロイメントオーナーは永続的な承認済みコーディネーターであり、所有権移転機能はありません。コンストラクタで提供される検証者とコントラクトのアドレスは、ゼロ以外の値がチェックされますが、コードの同一性や公開されたアーティファクトとの対応はチェックされません。

さらに2つの仮定があります。

- 両方のGroth16証明鍵は、著者による単一のフェーズ2貢献で生成されました。そのランダム性が保持されていた場合、偽の証明が偽造される可能性があります。実際の回路リリースには、[[MPC (マルチパーティ計算)|マルチパーティ計算]]セレモニーが必要です。
- システムは[[receipt-freeness|領収書不要性]]ではありません。投票者はElGamalのランダム性を記録して開示することで投票を証明できます。共謀防止はこの実装のスコープ外です。

最近のサーバー強化パスでは、Cloudflare対応のレート制限、認証失敗のスロットリング、一般的な500エラー応答、ローカルに固定されたsnarkjsビルド、正確に100の実際の投票の処理、および6つの暗号文ポイントすべての検証が追加されました。これらは運用上の経路を閉鎖しますが、上記の回路ステートメントを変更するものではありません。

## 自己検証デバイスとしてのデモ

リクエストベースのSepoliaデモは、正直なクライアントフローのデモンストレーションであり、敵対的な選挙ではありません。これを実行する有用な方法は、自分が管理する複数のウォレットを用意し、各ランダムなデモの重みと選択を記録し、自分の合計と最終化されたオンチェーンの結果を比較することです。

自分の合計と最終化された合計を比較することで、参加者が知っている合計を変更する省略や置換を検出できますが、正確なバッチの同一性を確立するものではありません。異なるバッチでも同じ集計を生成する可能性があります。

デモへのアクセスは、[@0xgumi](https://x.com/0xgumi)へのDMで可能です。パスワードは公開されていません。

## 方向性

これらは問題提起であり、提供のコミットメントではありません。

### 投票回路入力の整合性

次の投票回路は、素数位数のElGamal構成、`{0, weight}`内の平文、完全な重みを持つ1つの選択肢、リーフにバインドされたキーマテリアルから一意に導出された[[nullifier|ナリファイア]]、および認証されたセットにバインドされた適格性と重みを制約する必要があります。

### 正規集計バインディング

集計ステートメントには、正確に順序付けられた提出済みセット、正規のダミー処理、投票とデプロイメントのドメイン分離、および回路とコントラクトで共有される一意のスカラー範囲と合計制約が必要です。

### 閾値復号

集計のみの復号は、単一のキーホルダーが投票を復号できない場合にのみ強制されるプロパティとなります。これには、分散型キー生成、部分復号、およびシェアの証明が必要です。

### 大規模な重みに対するセグメント分割

生の18桁のトークン残高では、単一のBSGS範囲は非現実的です。未解決の問題は、各離散対数範囲を扱いやすくし、回路表現を健全に保ちながら、正確な重みを維持することです。

### 機密性の高い結果

一部の設定では、正確な合計が開示されないままで、閾値の結果のみが必要とされます。未解決の問題は、集計、復号、クォーラム、および範囲の関係を弱めることなく、その結果を証明することです。

### クロスチェーン決済

別のチェーンに配信される証明は、そのブリッジの起源以上のものを認証する必要があります。ターゲットチェーンが安全に実行できるように、ソース投票、デプロイメント、および正規の提出済みセットにバインドされている必要があります。

## 質問

1. ブラウザサイドのGroth16証明において、BabyJubJub ElGamalポイントの有効性と、1つの選択肢`{0, weight}`割り当てを同時に制約する最も経済的な方法は何ですか？制約付き再暗号化は依然として実用的なベースラインでしょうか？
2. 投票ごとの[[nullifier|ナリファイア]]は、リーフにバインドされたキーシークレットから直接導出されるべきでしょうか、それとも投票間の非リンク可能性を維持しながら自由なシークレットを排除する、よりクリーンな構成があるでしょうか？
3. 集計証明を提出された暗号文の正確な順序付きセットにバインドするための、ガスと証明サイズの最適なトレードオフは何ですか？100のバッチの場合、オンチェーンアキュムレータ、格納されたハッシュ配列、または回路にブリッジされた異なるコミットメントのどれを推奨しますか？
