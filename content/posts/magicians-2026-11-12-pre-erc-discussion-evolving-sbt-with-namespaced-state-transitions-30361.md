*この議論は、フォーラムの投稿ごとの文字数制限のため、2つの投稿に分かれています。この最初の投稿では、コアインターフェース、成長、権限、および有効性について説明します。以下の続きの投稿では、プライベートな提示、ワンタイムの資格、リカバリ、実装例、および議論の質問について説明します。*

私は、検証済みの経験を時間とともに蓄積し、それらの経験が異なるアプリケーションをサポートできるようにするソウルバウンドクレデンシャル (SBT) の拡張を検討しています。

その動機は次のとおりです。

> 異なるプロトコルに散らばった過去の活動は、将来の適格性の証拠として再利用できるべきである。

個人は、ガバナンスに参加したり、コミュニティタスクを完了したり、流動性を提供したり、資産を借りたり返済したり、教育資格を取得したりするかもしれません。これらの経験は、メンバーシップのアップグレード、貢献者アクセス、専門的資格、イベントへの参加など、将来の要件をサポートできます。

提案されている設計では、永続的で譲渡不可能なクレデンシャルを使用して、これらの経験全体で継続性を維持します。アプリケーションは、その現在受け入れられている状態を発見し、その状態を承認したルールを特定し、サポートするクレームが引き続き使用可能であるかどうかを評価できます。

プライバシーに配慮したアプリケーションの場合、ホルダーは「少なくとも2つの適格な貢献があり、残高の閾値を満たしている」といった要件を、完全な活動履歴や正確な残高を提示に含めることなく証明できるべきです。

これは[[Pre-ERC|プレERC]]の議論です。以下のコアインターフェースと実装プロファイルは、レビューのための提案です。監査済みの実装やベンチマーク結果は主張されていません。

**成長と動的な有効性には異なる意味があります。** 成長とは、クレデンシャルが認識された経験を蓄積し、追加の資格をサポートできることを意味します。動的な有効性とは、その使用可能な状態が、修正、有効期限切れ、取り消し、承認の変更、および明示的に許可されたポリシー移行に対応できることを意味します。

これらの特性は共存できます。

- 完了したコミュニティタスクは、承認された経験を追加します。
- 修正は、既存の経験が認識される方法を変更します。
- 発行者が誤って発行された認証を取り消します。
- メンバーシップは、参加履歴は残るものの、有効期限が切れます。
- アプリケーションは、ホルダーの過去を書き換えることなく、要件を変更します。

状態の改訂は、承認された遷移とともに増加します。スコア、レベル、および現在の適格性は、単調に増加する必要はありません。

この設計では、常に3つのことを区別しています。

1. 承認された履歴記録。
2. それらの記録が現在、アプリケーションの要件を満たしているかどうか。
3. 特定のアプリケーション資格がすでに消費されているかどうか。

**提案されているコアは、承認された状態とその進化を標準化します。** 完全なシステムにはいくつかの責任があります。

| 責任 | 提案されている場所 |
| --- | --- |
| トランザクション、[[Attestation|アテステーション]]、およびスナップショットを収集する | インデクサーとソースアダプター |
| アクションを解釈し、そのソースを確立する | 証拠検証ルール |
| アクションがどの主体に属するかを確立する | 主体帰属ルール |
| クレームを認識または変更できる者を決定する | 名前空間ポリシー |
| 現在承認されている状態と改訂を維持する | SBT状態遷移インターフェース |
| プライベートクレームと証明資料を保持する | ホルダーのウォレットまたは選択されたストレージ |
| 資格要件を定義する | アプリケーションポリシー |
| 選択的開示提示を生成する | ホルダー制御のプルーバー |
| 現在の有効性を確認し、限定使用権を消費する | アプリケーション検証者と消費台帳 |

コアは、状態発見、ポリシー発見、および承認された状態遷移をカバーします。ユニバーサルインデクサー、分類サービス、評判式、または[[Zero-Knowledge-Proof|ゼロ知識システム]]は必要ありません。

共通の提出インターフェースにより、互換性のあるウォレットとリレーヤーが更新を一貫して処理できます。特定のポリシーの証拠を生成するには、そのポリシーのデータと検証プロファイルをサポートする必要があります。

**既存の標準はすでに実質的な動的機能を提供しています。** したがって、拡張のケースは「SBTは動的であるべき」というよりも具体的でなければなりません。

| 標準 | 関連する機能 | この提案との関係 |
| --- | --- | --- |
| [[ERC-5192|ERC-5192]] | 最小限のロックされたトークンインターフェースとロック中の転送制限 | 譲渡不可能性の可能な基盤。ここで提案されている状態遷移モデルは定義していません。 |
| [[ERC-5484|ERC-5484]] | 発行時の同意、バーン承認、および不変の発行済みメタデータ | 関連するライフサイクル制約。進化する状態は、そのメタデータ要件と調整する必要があります。 |
| [[ERC-5727|ERC-5727]] | トークンとクレジットの発行/取り消し、検証、およびオプションのライフサイクル拡張 | すでに動的な動作をサポートしています。この提案は、1つのクレデンシャル内で独立して管理され、バージョン管理された状態の共通セマンティクスを追加します。 |
| [[ERC-7508|ERC-7508]] | 動的なオンチェーン属性ときめ細かなアクセス制御 | 関連する属性インフラストラクチャ。提案されている追加は、証拠制約と先行者結合遷移に関するものです。 |
| [[ERC-7208|ERC-7208]] | 基盤となるデータと管理ロジックの分離 | 可能な実装インフラストラクチャ。クレデンシャル固有の遷移セマンティクスは依然として定義する必要があります。 |

[[ERC-5727]]では、トークンは一度に1つのスロットに属します。ここでは、クレデンシャルは複数の名前空間を含めることができ、それぞれが現在の状態ヘッドと承認ルールを持ちます。[[ERC-5727]]の実装は、拡張機能を通じてこれらの機能を提供できます。問題は、それらの共有セマンティクスを標準化することが有用かどうかです。

[[ERC-5484]]との互換性は想定されていません。互換性を主張する実装は、発行時に合意されたメタデータを保持し、その他の要件を満たす必要があります。`tokenURI`文字列を変更せずに、それが解決するメタデータを変更しても、互換性は確立されません。[[ERC-5727]]は[[ERC-5484]]を継承しているため、これは[[ERC-5727]]の拡張を検討する際にも重要です。[[ERC-5484]]仕様 ([https://eips.ethereum.org/EIPS/eip-5484#specification](https://eips.ethereum.org/EIPS/eip-5484#specification))、[[ERC-5727]]コア ([https://eips.ethereum.org/EIPS/eip-5727#core](https://eips.ethereum.org/EIPS/eip-5727#core))。

関連する作業には、提案されている[[ERC-8415|ERC-8415]] ([https://github.com/ethereum/ERCs/pull/2149](https://github.com/ethereum/ERCs/pull/2149)) が含まれます。これは、外部レジスタプロジェクションのバージョン管理されたコミットメントとプルーフバウンドアドミッションに関するものです。また、提案されている[[ERC-8404|ERC-8404]] ([https://github.com/ethereum/ERCs/pull/1980](https://github.com/ethereum/ERCs/pull/1980)) は、再計算可能な検証レシートに関するものです。どちらもこのドラフトの時点ではオープンなプルリクエストとして存在しています。

検討されている貢献は、以下のための共通コントラクトです。

> クレデンシャル名前空間の現在の状態、その状態を管理するポリシー、および正確な先行者からの証拠承認済み遷移。

名前空間、コミットメント、バージョンチェック、およびアトミックトランザクションは既存のメカニズムです。提案されている価値は、進化するクレデンシャルに対するそれらの相互運用可能な意味です。

**名前空間は、意味的および承認の境界を表します。** 状態は次のようにアドレス指定されます。

```
(chainId, credentialContract, tokenId, namespace)
```

1つのクレデンシャルには、コミュニティ貢献、教育資格、検証済みプロトコル活動のための名前空間が含まれる場合があります。

各名前空間は、そのスキーマ、認識された権限、許可された操作、および遷移ルールを識別します。ある名前空間に対する権限は、自動的に別の名前空間に対する権限を付与するものではありません。

異なるデプロイメントで使用される同じ名前空間識別子は、自動的に同等の意味を確立するものではありません。消費者は、デプロイメントとその適用されるポリシーを認識する必要があります。

名前空間は、普遍的な活動分類法を必要とするものでもありません。プロトコル名とアクションカテゴリは、レコード内のフィールドにすることができます。

例示的な分類には以下が含まれます。

| 活動ファミリー | アクション例 | 必要な解釈 |
| --- | --- | --- |
| 資産移動 | 送信、受信、ミント、バーン | 資産、単位、アクターロール、および移動が自発的であったかどうか |
| 交換と流動性 | スワップ、流動性追加、流動性削除 | 参加者、プールまたはポジション、資産、およびアクション境界 |
| レンディング | 供給、引き出し、借り入れ、返済、清算 | アクターロール、ポジション、および履歴と現在の状態の意味 |
| 予測市場 | ポジション取得、取引、決済済みポジションの償還 | 市場、ポジション、結果、および決済コンテキスト |
| ガバナンス | 提案、投票、委任 | ガバナンスシステム、提案、ロール、およびチェックポイント |
| コミュニティと資格 | タスク完了、参加、認証取得 | 認識する発行者、基準、有効性、および取り消し |

Uniswap、Aave、またはPolymarket関連のコントラクトとやり取りするだけでは、特定の意味のあるアクションが確立されるわけではありません。ソースアダプターは、ルーター、[[Smart-Account|スマートアカウント]]、リレーヤー、およびポジション所有権を考慮する必要があります。

既存のEtherscanラベルは、エンティティを識別し、活動を説明するのに役立ちます。それらは、主体がアクションを実行したことや、そのアクションが貢献として適格であることを確立するものではありません。ポリシーが外部の分類データセットに依存する場合、データセットのバージョンと信頼の前提を識別する必要があります。Etherscanメタデータドキュメント ([https://docs.etherscan.io/metadata/introduction](https://docs.etherscan.io/metadata/introduction))。

**承認された証拠には、帰属と認識の両方が必要です。** 検証プロセスは、以下の別々の質問に答える必要があります。

1. 基盤となるイベント、状態、または[[Attestation|アテステーション]]は存在するか？
2. 帰属ルールに基づいて、クレデンシャルの主体に属するか？
3. この種のクレームについて、ソースまたは発行者は認識されているか？
4. 証拠は、要求された状態変更を承認するか？

SBTを所有しているだけでは、任意の認識されたクレームを承認するものではありません。

レコードスキーマは、該当する場合、以下を識別する必要があります。

- スキーマとバージョン。
- 主体バインディング。
- ソースチェーン、コントラクト、認証済みチェックポイント、およびイベントまたは状態参照。
- プロトコルアクションと主体ロール。
- 資産、数量、および単位。
- 発行者または検証方法。
- 有効性境界。
- クレーム識別子と正規の経験またはアクション識別子。
- 認証済み取り消しレジストリと取り消しキー。
- 修正または置換の場合の以前のクレームへの参照。

暗号学的証明は、その検証ルールによってエンコードされたステートメントを確立します。それは、信頼できない発行者を権威あるものにしたり、本物のトランザクションが価値ある貢献を表すことを確立したりするものではありません。

例えば、コミュニティがタスクが完了したと表明することは、そのコミュニティの権限を伴います。アプリケーションはそれを受け入れるかどうかを決定する必要があります。

**最初の成長プロファイルは、履歴記録、記録ステータス、および重複会計を分離します。** 汎用的な`stateRoot`だけでは、以前の経験が保持されたことや、アクションが一度だけカウントされたことを確立することはできません。

成長を具体化するために、最初の実装プロファイルは以下の構造にコミットします。

```
stateRoot = Commit(
    profileId,
    recordsRoot,
    recordCount,
    recordStatusRoot,
    creditedActionsRoot
)
```

ここで：

- `recordsRoot` は、承認されたクレームレコードの追記専用シーケンスにコミットします。
- `recordCount` はそのシーケンスを記述します。これは貢献スコアではありません。
- `recordStatusRoot` は、アクティブまたは置き換えられたステータスや置換関係を含む、レコードの現在のローカルステータスにコミットします。
- `creditedActionsRoot` は、すでに会計に認められた正規の経験またはアクション識別子にコミットします。
- `profileId` は、適用されるエンコーディングと遷移ルールを識別します。

コミットメント構築と証明アルゴリズムは、プロファイルによって固定されなければなりません。プライバシーに配慮したフィールドには、適切な隠蔽コミットメントが必要です。

追加操作は、以前のレコードがコミットされたままであり、新しいレコードが有効な認識証拠を持ち、新しくクレジットされたアクションがまだクレジットされていないことを証明します。

修正は、影響を受けるレコードにリンクされた新しいレコードを追加します。関連するレコードステータスを更新し、基盤となる経験識別子を保持します。

新しいクレーム識別子は、新しい経験を作成しません。アプリケーションは、ルールに従って、個別の適格な経験識別子をカウントします。

例えば、承認されたタスクのカテゴリを修正すると、その資格値が変わる可能性があります。しかし、1つの完了したタスクが2つの完了したタスクになることはありません。

現在のレコードステータスコミットメントは、追記専用履歴には古いレコードが依然として含まれているため必要です。提示は、履歴への包含のみに依存することはできません。選択されたレコードが現在使用可能であることも確立する必要があります。

外部からの取り消しは別途確認されます。SBTの最後に承認された状態ではアクティブとマークされたレコードでも、発行者の取り消しレジストリを通じて使用不能になっている可能性があります。

このプロファイルは、検証可能な成長の具体的な意味を1つ提供します。他のプロファイルでは異なるデータ構造を使用する場合がありますが、その保存と会計の保証を明記する必要があります。

**候補となるコアには、3つのメソッドと1つの遷移イベントがあります。** 以下のスケッチは追加部分を示しており、基本トークンとインターフェース検出メソッドは省略されています。

```solidity
interface IEvolvingSBT {
    enum NamespaceStatus {
        Uninitialized,
        Active,
        Suspended,
        Revoked
    }

    struct StateHead {
        uint64 revision;
        bytes32 stateRoot;
        bytes32 policyId;
        NamespaceStatus status;
        uint64 validUntil;
    }

    struct PolicyDefinition {
        bytes32 schemaId;
        bytes32 rulesHash;
        address verifier;
        bytes32 verifierConfigHash;
        bytes32 authorizationHash;
        string specificationURI;
    }

    struct PolicyStatus {
        uint64 epoch;
        bool updatesEnabled;
        bool usesEnabled;
    }

    struct StateUpdate {
        bytes32 stateRoot;
        bytes32 policyId;
        NamespaceStatus status;
        uint64 validUntil;
    }

    struct Transition {
        uint256 tokenId;
        bytes32 namespace;

        uint64 expectedRevision;
        bytes32 expectedStateHash;

        uint64 sourcePolicyEpoch;
        uint64 targetPolicyEpoch;

        StateUpdate nextState;

        bytes32 operationsCommitment;
        uint64 deadline;
    }

    function stateOf(
        uint256 tokenId,
        bytes32 namespace
    ) external view returns (StateHead memory);

    function policyOf(
        bytes32 namespace,
        bytes32 policyId
    )
        external
        view
        returns (
            PolicyDefinition memory definition,
            PolicyStatus memory status
        );

    function applyTransition(
        Transition calldata change,
        bytes calldata evidence,
        bytes calldata authorization
    ) external returns (uint64 newRevision);

    event StateTransitioned(
        uint256 indexed tokenId,
        bytes32 indexed namespace,
        uint64 revision,
        bytes32 previousStateHash,
        bytes32 nextStateHash,
        bytes32 policyId,
        bytes32 transitionId
    );
}
```

`stateOf` は、現在承認されているヘッドを公開します。

`policyOf` は、不変のルール定義とその現在の運用制御を公開します。

`applyTransition` は、証拠を伴う更新のための共通の提出インターフェースを提供します。コントラクトは次のリビジョンを割り当てます。

書き込みメソッドが含まれているのは、意図されたワークフローが、ホルダーが証拠を保持し、互換性のあるウォレットまたはリレーヤーを通じて提出できるようにするためです。より狭い、消費者のみの設計では、書き込みインターフェースを拡張機能に分離することもできます。

このコアは、すべての経験カテゴリ、スコア更新、またはプロトコル統合のための個別のメソッドを導入しません。これらの操作は、適用されるポリシーの下で解釈されます。

必要に応じて、標準化された検証者プラグインABIは、別の追加となります。検証者アドレスだけでは、独立して実装されたプラグインが交換可能になるわけではありません。

**ポリシーのIDとライブ制御は分離されたままでなければなりません。** `policyId` は、スキーマ、検証動作、構成、および承認ルールをカバーする不変の定義を識別します。

`specificationURI` は発見場所です。その規範的な内容は、コミットされた定義と一致する必要があります。URLのコンテンツを変更しても、既存のポリシーがサイレントに変更されることはありません。

アップグレード可能なプロキシを通じてその動作が変更される可能性がある場合、固定された検証者アドレスも不十分です。ベースラインでは、固定された検証動作と依存関係が必要です。規範的な変更には、新しいポリシーIDが必要です。

ライブ制御には異なる意味があります。

- `updatesEnabled` は、新しい遷移が受け入れられるかどうかを制御します。
- `usesEnabled` は、アプリケーションがポリシーに依存できるかどうかを制御します。
- `epoch` は、これらのライブ制御が変更されるたびに変更されます。

登録された各`(namespace, policyId)`について、エポックは定義されたゼロ以外の値で始まり、単調に増加し、リセットすることはできません。オーバーフローはリバートします。

エポックの変更は、以前のエポックにバインドされた保留中の更新と提示を無効にします。履歴記録を消去するものではありません。

したがって、ポリシーを一時停止して再開しても、古い保留中の承認が再アクティブ化されることはありません。

ポリシー管理は最小限のABIの範囲外ですが、実装はその制御権限を開示し、強制する必要があります。アプリケーションは、どのポリシーと権限を受け入れるかを選択します。

**すべての遷移は、共有された[[Invariant|不変条件]]を満たす必要があります。**

1.  **存在と登録。** クレデンシャルが存在し、名前空間とターゲットポリシーがデプロイメントによって認識されている必要があります。不明なポリシーとサポートされていない名前空間は拒否されます。
    
2.  **承認された初期化。** 登録されているが初期化されていない名前空間には、正規のリビジョンゼロヘッドがあります。初期化には、名前空間の承認ルールと必要なホルダーの同意が必要です。
    
3.  **正確な先行者。** 期待されるリビジョンと状態ハッシュは、保存されている先行者と一致し、更新がコミットされたときに有効なままでなければなりません。
    
4.  **シーケンシャルなリビジョン。** コントラクトは現在のリビジョンに1を加えたものを割り当てます。呼び出し元はリビジョンをスキップしたりリセットしたりすることはできません。
    
5.  **期限。** リクエストにはゼロ以外の期限があり、期限を過ぎると拒否されます。
    
6.  **現在のポリシー制御。** 関連する更新制御が操作を許可し、提供されたポリシーエポックがライブ状態と一致する必要があります。初期化にはソースポリシーがなく、ソースエポックゼロを使用します。
    
7.  **完全なバインディング。** 検証は、チェーン、クレデンシャルコントラクト、トークン、名前空間、先行者、提案された状態、ポリシー、エポック、操作コミットメント、および期限をバインドします。
    
8.  **証拠と許可。** 検証は、ソースの信頼性、主体の帰属、認識された権限、操作の許可、および会計制約をチェックします。
    
9.  **移行承認。** `policyId` の変更には、ソースポリシーの移行許可とターゲットポリシーの受け入れ許可が必要です。
    
10. **アトミックな承認。** 検証、状態ストレージ、およびイベント発行は同時に成功します。失敗した操作は部分的な更新を残しません。
     

1つのポリシーの下での通常の更新の場合、ソースとターゲットのポリシーエポックは同じです。

証拠と承認バイトは、発見可能なプロファイルに従う必要があります。それらは、提案された結果に関する未チェックの[[transaction-assertions|アサーション]]として機能することはできません。

ホルダーの制御に依存する承認は、そのプロファイルによって指定された現在の承認状態またはエポックをチェックする必要があります。

**操作の許可は、一般的な「更新可能」許可よりも狭いものでなければなりません。**

| 操作 | 必要な権限と制約 |
| --- | --- |
| 追加 | 認識された発行者またはソース検証者。サポートされているクレームのみが追加可能 |
| 修正 | 定義された修正権限。影響を受けるレコードと置換はリンクされている必要がある |
| 一時停止 | 定義された名前空間権限 |
| 再開 | 明示的な再開権限とルール |
| 名前空間の取り消し | 定義された取り消し権限 |
| 有効期限の延長 | その有効性を付与することを許可された権限 |
| ポリシーの移行 | ソース移行承認とターゲット受け入れ |

通常の追加では、新しい経験が提供されたという理由だけで、一時停止を解除したり、有効性を延長したりすることはできません。

最初のライフサイクルプロファイルでは、`Active`と`Suspended`間の承認された遷移を許可し、`Revoked`をその名前空間の終端として扱います。

`validUntil == 0` は、名前空間レベルの有効期限がないことを意味します。個々のレコードは依然として有効期限が切れる可能性があります。

有効期限は時間に対して評価されます。時間が経過しても、トランザクションが自動的に実行されたり、リビジョンが進んだりすることはありません。

**クレデンシャルと名前空間のIDはリセットできません。** ベースラインでは、以下の制限が採用されています。

- `tokenId` は、バーン後を含め、同じクレデンシャルコントラクト内で再利用されることはありません。
- 初期化された名前空間は、クリアされてリビジョンゼロで再初期化されることはありません。
- 初期化された名前空間は、`Uninitialized` に戻ることはできません。
- リビジョンとポリシーエポックは、ラップアラウンドしたりリセットしたりすることはできません。

バーンされたクレデンシャルは使用不能なままであり、公開状態クエリは基本ライフサイクルルールに従ってリバートする場合があります。実装は、識別子の再利用を防ぐために十分なライフサイクル情報を保持する必要があります。

これらの制限は、同じIDドメインが以前の見かけの状態に戻ったという理由で、古い承認が再び有効になるのを防ぎます。

将来、識別子の再利用を許可するプロファイルでは、関連するすべてのコミットメント、承認、および証明に明示的なインスタンス生成がバインドされている必要があります。

**互換性のある移行は、履歴参照以上のものを保持する必要があります。** 提案されている成長プロファイルの場合、移行は以下を保持または検証可能なマッピングを提供する必要があります。

- 承認された履歴記録。
- すでに承認された正規のアクション識別子。
- 現在のレコードステータスと置換関係。
- 適用される取り消し依存関係。
- 安定した主体と資格のバインディング。

移行によって、すでにカウントされたアクションが新しいものとして表示されたり、データ構造を変更するだけで置き換えられたレコードが復元されたりすることはありません。

ターゲットポリシーは、承認された経験の評価方法を変更する場合がありますが、その変更は明示的であり、消費するアプリケーションによって承認される必要があります。

これらの継続性保証を破棄する移行は、この成長プロファイルとの互換性を主張することはできません。

**リビジョン保護と証拠の重複排除は、異なる障害に対処します。** リビジョンチェックは、競合する更新が同じ先行者を上書きするのを防ぎます。

これは、同じアクションが後のリビジョンに対して再度提出されるのを防ぐものではありません。

正規化された流動性アクションの場合、ポリシーは認証されたソース参照と参加者ロールから正規の識別子を導き出すことができます。アダプターは、複数のログが1つのアクションを表す時期を定義する必要があります。

同じアクションの異なる証明を提出しても、別のクレジットが作成されるわけではありません。

[[Attestation|アテステーション]]の場合、プロファイルは安定した経験識別子と特定の発行済みクレームの識別子を区別します。これにより、既存の経験に関する修正されたクレームを、別の経験を作成することなく許可します。

重複排除は、関連する会計ルールに適用されます。同じ履歴でも、複数のアプリケーションをサポートできます。

**個々のクレームの取り消しは、ホルダーの協力なしに機能する必要があります。** 最初のプロファイルでは、同じチェーン上の発行者制御の取り消しレジストリを使用します。

各取り消し可能なクレームは、その発行者、レジストリ、および取り消しキーを、その主体とコンテンツとともに認証します。ホルダーは、クレームが取り消されていないレジストリに置き換えることはできません。

発行者は、ホルダーのプライベートSBT証人やホルダーの署名を取得することなく、クレームを直接取り消すことができます。

最初のレジストリプロファイルは単調な取り消しを使用します。一度取り消されると、クレームは取り消されたままになります。誤った取り消しは、修正ルールに基づいて新しいリンクされたクレームを発行することで対処されます。

古い取り消し可能なクレームを無効にする修正の場合、古いクレームは、置換の承認前または承認と同時に取り消されます。置換は経験識別子を保持し、新しいクレーム識別子を受け取ります。

これにより、有用な特性が生まれます。ホルダーがSBTの更新を拒否した場合でも、無効な古いクレームは新しい資格をサポートできません。

レジストリは、権限のローテーション、リカバリ、および履歴の解釈を定義する必要があります。その動作はサイレントに変更できず、移行によって既存の取り消しが消去されることはありません。

発行者キーのローテーションにも承認ルールが必要です。新しく提出されたクレームは、引退したキーによって署名された以前のタイムスタンプが含まれているという理由だけで、本当に古いものとして扱われることはありません。古いキーでの遅延承認には、適用されるカットオフルールを満たす認証済み発行または登録の証拠が必要です。

**現在の有効性には、すべてのサポートする依存関係が含まれます。** 取り消し可能なクレームを使用する資格は、それらの現在の非取り消しと、サポートする依存関係の有効性を証明する必要があります。

これには、キャッシュされたレベル、スコア、または中間計算を通じて継承された依存関係が含まれます。

以前に有効だった計算証明は、その基盤となるクレームが今日でも有効であることを確立するものではありません。

したがって、最初の実装では、完全にチェックできる境界のあるサポートセットを使用します。サポートする依存関係を検証できないキャッシュされたスコアは、現在の資格には不十分です。

SBTヘッドは、外部からの取り消し後も変更されない場合があります。後の状態遷移でローカルな帳簿を更新できますが、取り消しが適格性に影響を与えるための前提条件ではありません。

名前空間の更新が一時停止されている場合でも、独立した取り消しレジストリは使用可能なままです。ポリシー全体での依存は、`usesEnabled` を通じて個別に停止できます。
