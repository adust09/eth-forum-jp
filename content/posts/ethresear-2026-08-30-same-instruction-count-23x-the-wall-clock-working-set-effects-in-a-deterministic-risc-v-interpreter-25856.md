> [!note] 原文
> [Same instruction count, 23x the wall clock: working-set effects in a deterministic RISC-V interpreter](https://ethresear.ch/t/same-instruction-count-23x-the-wall-clock-working-set-effects-in-a-deterministic-risc-v-interpreter/25856) — cristiandkzk (2026-08-30)

決定論的RISC-Vインタプリタで実行コストを測定してきました。

これは、異種マシン間で安全性を保つプロトコルレベルの実行予算を割り当てるという、狭い問題意識に基づいています。予算はステップ数で表され、私が答えようとした疑問は、ステップ数が実時間 (wall clock) をどれだけ厳密に制約するかというものでした。得られた答えは予想よりも緩かったため、提案ではなく測定結果を投稿します。

**\*\*用語について、この部分が誤読されがちだからです。\*\*** 「ステップ (step)」とは、インタプリタのループによって実行される1つのRV32IM命令のことです。ホストCPUの命令ではありません。以下のすべての数値は1秒あたりのインタプリタステップ数であり、測定されているチェーンは `RISC-V命令 → インタプリタディスパッチ → ホストCPUの作業` であって、`RISC-V命令 → 1つのハードウェア命令` ではありません。

これは**\*\*ネイティブインタプリタの実行コストに関するものであり、ZK証明コストに関するものではありません。\*\*** 以下で引用するオペコードごとの作業は証明に関するものですが、ここでは実行自体が価格設定されるリソースである場合に、同様の区別が現れるかどうかを問うています。

**\*\*出所。\*\*** 2台のマシン、両方とも `--release` で実行：

-   **\*\*参照機:\** Motorola Edge 40 Neo — MediaTek MT6879V/ZA、2つのクラスターに8コア（2.5 GHzが2コア、2.0 GHzが6コア）、8 GB RAM、Android 15、rustc 1.97.1。
    比較的制約のある参照マシンです。予算はこれに合わせて調整されます。コアの配置は固定されていないため、実行はどちらかのクラスターに割り当てられる可能性があります。
-   **\*\*2台目:\** Intel Core i5-9400、6コア / 6スレッド、ベース2.90 GHz、合計L2キャッシュ1.5 MB、L3キャッシュ9 MB、Windows 11、rustc 1.96.0。

VM自身のページ会計は、設計の定数である4 KiBページを使用しており、これは必ずしもホストのページサイズではありません。ベンチマークはコミット `94dc7e3` で実行されました。

2つのバイナリ間でサンプリングが異なり、その読み取り方に影響します。
`mezclas` は各ミックスを内部で3回実行し、**\*\*最悪値\*\***を報告します。これは単純な保守的なルールであり、統計的な最悪ケースを主張するものではありません。`conjunto` は**\*\*そうではありません\*\***。ワーキングセットのスイープにおける各ポイントは1回のパスであり、これは後述の実行ごとのばらつきを読む前に知っておくべきことです。CPU周波数、熱状態、バックグラウンド負荷は計測していません。

**\## 固定ステップ数での命令ミックス**

7つのミックスはそれぞれ、正確なステップ数で停止する無限ループです。参照負荷はML-DSA-44署名検証であり、この特定の予算が価格設定のために設計されたワークロードです。

| mix | M steps/s | vs ML-DSA-44 |
|---|---:|---:|
| `mul` | 326.6 | 1.23 |
| ランダムな算術演算 (8オペコード) | 325.4 | 1.22 |
| `addi` uniform | 322.7 | 1.21 |
| **\*\*ML-DSA-44 (参照負荷)\*\*** | **\*\*266.2\*\*** | **\*\*1.00\*\*** |
| `divu` | 197.7 | 0.74 |
| `lw` シーケンシャル (2 KiB、L1に収まる) | 186.3 | 0.70 |
| `lw` ポインターチェイス (96ページ) | 82.1 | 0.31 |
| `lw` ポインターチェイス、ページ上限引き上げ | **\*\*11.3\*\*** | **\*\*0.04\*\*** |

同じ7,000,000ステップの上限で、ポインターチェイスのミックスは、このマシンでML-DSA-44ミックスよりも約**23倍遅い**です。26ミリ秒に対し619ミリ秒です。これは正しさの違いではありません。どちらの実行も決定論的であり、同じステップ数で停止します。遅い実行に無効な点はありません。

**\*\*最後の行の再現性に関する注意。\*\*** 出荷されているハーネスは11.3を報告しません。96の異なるページ上限がそのケースを最初に終了させるため、`mezclas` はレートではなく `cortada` を出力します。この1回の測定のためにのみ上限を引き上げました（`mezclas.rs:269`、`m.techo_paginas`、デフォルトは `u32::MAX`）。テーブルの他のすべての数値は、変更されていないハーネスからのものです。

**\## オペコードの同一性だけでは不十分な理由**

6行目と7行目を比較してください。シーケンシャルな `lw` は186.3で実行され、ポインターチェイスの `lw` は82.1で実行されますが、**\*\*`lw`レベルではオペコードストリームは同一です\*\***。静的なオペコードごとの重みでは、これら2つの実行を区別できません。なぜなら、異なるのは命令の同一性ではなく、メモリアクセス挙動だからです。安全性を保ちたいモデルは、オペコード自体を超えた情報が必要になります。

この主張の規模を明確にするために言えば、**\*\*これは静的計測 (static metering) が不可能であるという証拠ではありません。\*\*** これは、オペコードの同一性だけでは、私が観測した実行コストのすべてのばらつきを捉えられないという証拠です。私が知る限り最も注意深いオペコードごとの作業は、[Measuring Per-Opcode Proving Time](https://ethresear.ch/t/measuring-per-opcode-proving-time/23955) であり、各操作の限界貢献 (marginal contribution) を正確に分離することで、安価な操作も測定可能になります。この問題は、他のすべてを等しく保つという前提で提起されており、6行目と7行目は「他のすべて」が変動するケースです。この仮定は、[[glossary/EVM|EVM]]の計測設計](https://github.com/ewasm/design/blob/8ecee83f9ac58aa5f81b01498bc729789535bc29/metering.md)で最も明確に述べられており、オペコードごとのコストテーブルを合計し、その合計が「計算時間の推定値として機能する」と述べています。

**\## 第二の軸、これは最初のものよりも私を驚かせました**

2つのマシンが異なるのはメモリだけではありません。単一オペコードのループと、予測不可能な順序で8つのオペコードを実行するミックスを比較してください。同じステップ数で、どちらもメモリトラフィックはありません。

| mix | 電話 (aarch64) | i5-9400 |
|---|---:|---:|
| `addi` uniform | 322.7 | 413.0 |
| ランダムな算術演算 (8オペコード) | 325.4 | 156.1 |
| **\*\*スループット比、`addi` ÷ ランダム\*\*** | **\*\*0.99x\*\*** | **\*\*2.65x\*\*** |

電話では、2つのミックスは実質的に同等です。デスクトップでは、`addi` がランダムミックスの2.65倍で実行されます。同じマシン内比較で、2つのマシン間で約1から2.65に変化しています。メカニズムについては注意深く考える必要があります。2つのミックスはオペコードの構成と順序の予測可能性の両方で異なるため、これはインタプリタのディスパッチ予測が原因であると**\*\*特定するものではありません\*\***。しかし、同じペアのミックスが2つのマシンで異なる順位になることを示しており、どちらもメモリトラフィックは関与していません。これは、相対コストがプログラムの特性ではない第二の場所です。両方の数値は、各マシンで1回の `mezclas` 呼び出しからの3回実行の最悪値です。これに頼るには、より多くのマシンで検証したいところです。

**\## ワーキングセット**

実行時にカウントできるのは、アクセスされた異なるページ数です。これは実行中に観測可能で決定論的であり、命令数では見えないばらつきを露呈します。私が主張するのはこれだけです。これはコスト関数ではなく、スイープもまたコスト関数でなくなる点です。

| ワーキングセット | 4 KiBページ | M steps/s |
|---:|---:|---:|
| 16 KiB | 4 | 163.6 |
| 64 KiB | 16 | 125.5 |
| 128 KiB | 32 | 101.1 |
| 192 KiB | 48 | 86.2 |
| 384 KiB | 96 | 80.8 |
| 1 MiB | 256 | 79.3 |
| 2 MiB | 512 | 77.6 |
| 4 MiB | 1024 | **\*\*10.9\*\*** |

このマシンでは、曲線は384 KiBから2 MiBの間で比較的平坦になり、その後4 MiBで急激に低下します。ワーキングセットが2倍になると、7倍の低下です。ステップ数だけで表現される予算では、これらを一切表現できません。しかし、同じ形状が軸にも反しています。平坦な領域では、アクセスされたページ数で課金すると過剰に課金され、コストが実際に変動する唯一の場所は、ページ数では特定できない不連続点です。軸はばらつきを露呈しますが、価格設定はしません。

この低下は固定サイズではありません。i5-9400では、同じスイープが4 MiBでも50 M steps/sを超えており、16 MiB（15.6）で初めて崩壊します。このマシンには9 MBのL3キャッシュがあります。4 MiBは収まりますが、16 MiBは収まらず、崩壊はその間に発生します。これは、プログラムの固有の特性ではなく、ホストのメモリ階層が急落を引き起こしていることと一致しています。一致しているだけで、証明ではありません。

**\## 予想外だった部分**

予算が頼りにしなければならないのは最も弱いハードウェアであるため、それが最悪のケースになると私は仮定していました。しかし、ワーキングセットが大きくなると、これら2台のマシンでは私が測定した結果はそうではありませんでした。

| ワーキングセット | 電話 (aarch64) | i5-9400, 実行A | i5-9400, 実行B |
|---:|---:|---:|---:|
| 192 KiB | 86.2 | 122.2 | 138.3 |
| 384 KiB | 80.8 | 78.9 | 88.3 |
| 2 MiB | **\*\*77.6\*\*** | **\*\*40.6\*\*** | **\*\*55.5\*\*** |

小さなワーキングセットでは、予想通り電話の方が遅いです。2 MiBでは、デスクトップの方が両方の実行で遅くなっています。これは、デスクトップハードウェアが一般的に遅いという証拠として**\*\*扱っていません\*\***。ワーキングセットが大きくなると、2台のマシンサンプルだけでは、どちらのマシンが最悪のケースであるかは明らかではないという証拠です。

また、クロスオーバーポイントも示していません。なぜなら、特定できないからです。384 KiBでは、**\*\*同じデスクトップ\*\***の2回の実行が電話の反対側に位置しています。実行Bはアクティブなインタラクティブセッションのあるマシンで取得されました。電話の同じ測定でのばらつきは1.6%でしたが、デスクトップは40から88 M steps/sでした。実行ごとのばらつきはそれ自体で調査する価値があります。なぜなら、単一のキャリブレーション実行が必ずしも安定しているとは限らないことを意味するからです。しかし、その原因は特定しておらず、CPU周波数、ターボブースト、熱状態、スケジューリング、バックグラウンド負荷はすべてここでは制御されていません。

**\## 実行方法**

Rustツールチェーン以外の依存関係はありません。

```bash
git clone https://github.com/cristiandkzk/deterministic-succession
cd deterministic-succession/genesis/predicado/vm
cargo run --release --bin mezclas # 命令ミックスのテーブル
cargo run --release --bin conjunto # ワーキングセットのスイープ
```

いずれかのベンチマークを実行した場合は、その出力と実行したCPUモデルおよびアーキテクチャを投稿してください。OSとRAMも役立ちます。

特に、絶対的なスループットではなく、**\*\*マシン間で相対的な順序が変化する\*\***ケースに興味があります。これは上記の2つのセクションの主題であり、2台目のマシンで安価に反証できる部分です。

最悪のケースのハードウェアベースラインを確立するには、2台のマシンでは不十分です。目標は、異なるCPU間で測定値を収集し、安定した関係が出現するかどうかを確認することです。もしあなたの結果が「デスクトップの方が遅い」という結果を再現しなかった場合、それは特に有用です。

**\## これが示さないこと**

これは、オペコード計測 (opcode metering) が役に立たないこと、RISC-Vが[[glossary/Layer-1|L1]]実行ターゲットとして不適切であること、WASMが良いか悪いか、あるいは23倍のギャップが今日のイーサリアムで悪用可能であること、を示すものではありません。これはより狭いことを示しています。この決定論的インタプリタでは、同じステップ数が実質的に異なる実行時間に対応する可能性があり、その違いは命令ミックス、実行時のメモリ局所性挙動、およびホストに依存します。

決定論的実行は、決定論的なセマンティクスと決定論的なステップ数をもたらします。この証拠によれば、それ自体では物理的な実行コストに対する厳密でハードウェアに依存しない制約は得られません。

**\## 質問**

1.  割り当てられたページや増加したページではなく、**\*\*実際にアクセスされた\*\***ページに対して課金することを、特に実行コストの会計のために検討した人はいますか？私が見つけた最も近い先行研究は、eWASMのメモリ計測であり、初期のページ数とすべての `grow_memory`（割り当てられた軸）に対して課金します。私のミックスは同じメモリを割り当てますが、そのアクセス方法によって2.3倍の違いがあります。これをパフォーマンス分析のメトリックとしてではなく、プロトコルリソースとして扱う研究に特に興味があります。

2.  上記のオペコードごとのスレッドで、@jochem-brouwer は、ModExpを手作業で行った後、クライアントごとに最悪の入力を見つける方法を尋ねています。もし上記の結論が成り立つなら、答えの一部は不快なものです。最悪の実時間 (wall clock) はプログラム/入力ペアだけでは決定されず、ホスト実行状態とマイクロアーキテクチャの挙動にも依存します。これは、[[glossary/repricing|再価格設定]]ベンチマークが示してきたことと一致しますか？

3.  [RISC-V vs WASMデリバリーISAスレッド](https://ethresear.ch/t/why-risc-v-is-not-a-good-choice-for-an-l1-delivery-isa-and-why-wasm-is-a-better-one/23491)は、計測がどれだけきれいに**\*\*注入できるか\*\***という点で、選択を実質的に議論しています。構造化された制御フローはプログラムがジャンプできる場所を制約しますが、ロードのアドレスは依然として計算され、WASMのリニアメモリの制約は宣言された最大ページ数であり、これもまた割り当てられた軸です。したがって、それぞれのメモリと実行の制約を考慮した場合、敵対的プログラム (adversarial program) は、どちらのデリバリーISAの下でも同等の実行コストギャップを再現できるでしょうか？

4.  上記3つの質問の根底にあるもの：実時間コストが計算と実行時のメモリ局所性の両方に依存する場合、プロトコルレベルで計測すべき適切なリソースは何でしょうか？
