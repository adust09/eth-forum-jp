**概要。** AIFPは、[[AI-agents|AIエージェント]]間の情報層のためのフレームワーク[[ERC|Ethereum Request for Comments (ERC)]]です。これは、インタラクションコンテキストのコンテンツアドレス指定され、バージョン管理された記述としてフローパラダイムを定義します。このパラダイムは、どのキャリア（アドレス指定された配信、共有オブジェクト）と構造的オペレーター（ファンアウト、ファンイン、フィードバック、nパーティ、選択、転送、派生、マージ）を使用するか、および13の個別に宣言されたルールディメンション（発見、観測、貢献、管理、再配布、履歴、時間、開示タイミング、貢献者可視性、承認基準、表現、オブジェクト関係、順序付け）がどのように設定されるかを定めます。チャネルは任意の時点において、正確に1つのパラダイムバージョンを採用します。参加は、スコープ、基準、有効期間、および付与されたルールバージョンを持つ、個別にアドレス指定可能なロールバインディングとして記録されます。ロールの取得は、4つの結果（satisfied、not satisfied、undeterminable、verifier error）のいずれかを返す構成可能な述語によってチェックされます。

**ステータス。** ドラフト。ethereum/ERCs PR [#2152](https://github.com/ethereum/ERCs/pull/2152) として提出されました。[[EIP-Editor|EIPエディター]]は2026年11月9日に[[ERC|Ethereum Request for Comments (ERC)]]-8489の番号を割り当てました（`ERCS/erc-8489.md`、アセットは`assets/erc-8489/`以下）。Foundryスイート、カノニカルバリデータ、およびベクトルを含む参照リポジトリ: [garyyang-finchip/aif-paradigm](https://github.com/garyyang-finchip/aif-paradigm)。参照スタックは[[Sepolia|Sepolia (テストネット)]]にデプロイされており、境界ケースの証拠実行が記録されています（以下のセクションを参照）。

**リンク。** 提出された[[ERC|Ethereum Request for Comments (ERC)]]テキスト: [ERCS/erc-8489.md](https://github.com/garyyang-finchip/ERCs/blob/add-erc-aif-paradigm/ERCS/erc-8489.md) (ethereum/ERCs プルリクエスト [#2152](https://github.com/ethereum/ERCs/pull/2152)) - 参照リポジトリ: [garyyang-finchip/aif-paradigm](https://github.com/garyyang-finchip/aif-paradigm) - [[Sepolia|Sepolia (テストネット)]]証拠: [docs/sepolia-evidence.md](https://github.com/garyyang-finchip/aif-paradigm/blob/main/docs/sepolia-evidence.md)。

**既存システムに対する新規性。** [[AI-agents|AIエージェント]]タスクプロトコル、ツールプロトコル、マトリックススタイルのルーム、フェデレーテッドアクティビティフィード、署名済みイベントリレー、暗号化グループ、オンチェーンイベントはそれぞれ、誰が読み書きし、再配布できるかについて独自の概念を定めています。AIFPはそれらのどれも置き換えるものではありません。トランスポートは、ケイパビリティビットを持つ宣言されたバインディングを介して接続されます。AIFPが追加するのは、実装をまたいで、あるコンテキストに関する5つの質問（このアクターは観測できるか、貢献できるか、他の場所で読んだものを公開できるか、どのルールバージョンが決定するか、どの条件が検証できないか）に対する検証可能な単一の回答です。

## 提案の構造

| レイヤー | オブジェクト | オンチェーン記録 |
| --- | --- | --- |
| パラダイム | コンテンツアドレス指定された記述子: キャリア、オペレーター、13のルールディメンション、ラベル、ロールごとの述語 | IAIFPParadigmRegistry: `paradigmId` = [[keccak256-hash|Keccak-256ハッシュ]](JCSカノニカル記述子)、ファミリーと継承、ラベルID、述語コミットメント |
| チャネル | 任意の時点において1つのパラダイムバージョンを採用するインタラクションコンテキスト | IAIFPChannelRegistry: `effectiveAt`を持つ追記専用の採用記録、ケイパビリティビットを持つトランスポート/ガバナンス/経済的バインディング、追記専用の開示記録、ステート |
| 参加 | スコープ、基準、期間、ルールバージョンを持つ個別にアドレス指定可能なロールバインディング | IAIFPParticipationRegistry: 付与（マネージャーパス）と承認（述語パス）、一時停止/取り消し/再承認履歴、`evaluate(channel, subject, role, scope, timepoint)` |
| 検証 | 構成可能な述語ツリー、4つの結果 | IAIFPPredicateVerifierと複合検証者: 固定された優先順位を持つ`allOf` / `anyOf`。未知の種類やリバートする検証者は「not satisfied」として記録されることはありません。 |
| プロファイル | イベントアンカリング、異議申し立てウィンドウ | IAIFPEventAnchor（オプション）、異議申し立てウィンドウコンパニオン（事前合意されたウィンドウ内でのみ不在セマンティクス） |

ドラフトで固定されたエンコーディング: `eip155-address`、`erc8004`、`did`、`ext`のサブジェクト（小文字アドレス、左パディングなし）に対する1つのサブジェクト参照 `[[keccak256-hash|Keccak-256ハッシュ]]("<scheme>:<domain>:<identifier>")`。幅優先の子割り当てと9つのリーフおよび複合種類を持つ`abi.encode(Node[])`としての述語ツリー。11ビットのロールマスク。[[ERC-165-discoverable|ERC-165]]インターフェースIDと[[ERC-6372|ERC-6372]]クロック。トランスポートは設計上スコープ外です。`requires: 165, 6372`のみ。アイデンティティ、クレデンシャル、決定、発見、スウォーム、安全性、紛争、テンダー、経済ユニットのレジストリは述語リーフとバインディングを介して接続され、必須ではありません。

**注目すべき設計点。**

-   馴染みのある人間向けの形式（ブロードキャスト、パネル、アセンブリ、会議、3種類のピアツーピア）は、バリデータによってチェックされる決定可能な識別条件を持つ構成上のラベルであり、[[AI-agents|AIエージェント]]ネイティブの形式（インテーク、ブラックボード、ディスパッチ、フォワード、派生）がそれらに並んでいます。完全性は、閉包、互換性ルール、反例、およびオープンな拡張ネームスペースによって議論され、カルテシアン積によってではありません。
-   すべての付与は`bindingId`を生成します。`evaluate(channel, subject, role, scope, timepoint)`は、レジストリ履歴（一時停止期間、再承認エポック）の純粋関数です。一時停止は、それを課した当事者によってのみ解除されます。
-   4値検証: 未知の必須拡張機能、不足している証明、またはリバートする検証者は「not satisfied」として記録されることはありません。承認パスは、取得した結果とともにリバートします。
-   履歴的有効性と承認: 受理されたイベントは、遅れて配信された場合でも有効性を保持します。初回承認はレジストリの[[ERC-6372|ERC-6372]]クロックを使用し、送信者が主張するタイムポイントは決して使用しません。
-   開示の単調性（履歴に関する事実として）: 開示記録は追記専用です。将来の提供は、`RESTRICTED`記録を介して（既存のオブジェクトについても）契約を縮小する可能性がありますが、これは読み取りも削除も証明しません。
-   事前合意された異議申し立てウィンドウ内でのみ、整合性条件を持つ不在セマンティクス。デフォルトの結果は合意された条件を証明し、決して同意を証明しません。

## 説明的な解釈: [[AI-agents|AIエージェント]]通信語彙におけるAIFP用語

このセクションは読解の助けとなるものであり、再定義ではありません。AIFPは、上記で定義されたフローパラダイム、チャネル、参加、および検証を標準化します。メッセージングおよび[[AI-agents|AIエージェント]]通信プロトコルに精通している読者のために、この表は各AIFPの概念を彼らがすでに使用している語彙にマッピングします。通信プロトコルはメッセージを運びます。AIFPは、特定のコンテキストが読み書きされ、再配布される際のルールを記録し、プロトコルはトランスポートバインディングとしてチャネルに接続されます。

| AIFP用語 | 通信用語では、次のように読めます |
| --- | --- |
| パラダイム | 適用されているパターン: ブロードキャスト、パネル、クローズドグループ、会議、ピアツーピア、インテーク、ブラックボード、ディスパッチ、フォワード、派生 |
| チャネル | 1つのコンテキスト: フィード、ルーム、スレッド、トピック、共有ドキュメント、イベントストリーム |
| キャリア（アドレス指定された配信 / 共有オブジェクト） | メッセージパッシング対、参加者が読み書きする共有ステート |
| 構造的オペレーター | 交換が取りうる形状: 1対多、多対1、返信、グループ、ルーティング、リレー、要約、結合 |
| ルールディメンション | 誰がコンテキストを見つけ、読み、貢献し、管理し、そこから転送し、その履歴をいつ見ることができるか |
| ロールバインディング（OBSERVE、SUBMIT、RESPOND、REDISTRIBUTE、MANAGE_*） | 1つのコンテキストにおける1つの[[AI-agents|AIエージェント]]のリスナー、スピーカー、返信者、転送者、モデレーターのパーミッション |
| 述語検証、4値 | [[AI-agents|AIエージェント]]が観測または貢献する前に通過する承認チェックで、「検証不能」は「拒否」とは区別されます。 |
| `effectiveAt`を持つ採用 | すべての参加者が予見できるスケジュールされたルール変更 |
| 開示記録（DISCLOSED / RESTRICTED） | コンテキストが何に対して開示されたか、または閉鎖されたかの追記専用ログ |
| ケイパビリティビットを持つトランスポートバインディング | 具体的なプロトコル（ルーム、フィード、リレー、グループ、イベントログ）がチャネルにどのように接続されるか |
| イベントアンカー | メッセージ、転送、派生、または撤回がチャネル内で発生したことの検証可能なコミットメント |

2つの実用的な結果が導かれます。1つは、[[AI-agents|AIエージェント]]が自身のプロトコルを保持し、それをトランスポートバインディングとして宣言し、レジストリから承認、再配布、およびルールバージョンの回答を読み取ることです。もう1つは、異なるプロトコル上の2つの[[AI-agents|AIエージェント]]が共有コンテキストで誰が読み書きし、転送できるかについて合意できることです。なぜなら、その記録はトランスポートではなくチャネルが保持しているからです。

## 参照資料と[[Sepolia|Sepolia (テストネット)]]証拠

3つのレジストリ（パラダイム、チャネル、参加）、複合検証者、オプションのイベントアンカープロファイル、および異議申し立てウィンドウコンパニオン。カノニカルバリデータ（JCS + [[keccak256-hash|Keccak-256ハッシュ]]、ラベル条件、述語エンコーディング）。17の例示記述子（11の命名パラダイム、6つの複合）と4つの意図的に無効な記述子。ベクトル。3人の参加者を含む12の境界ケース（見知らぬ人同士の握手、クレデンシャル入力、ソース+アーカイブ、パネルからクラブへの移行、封印入札、ブラックボード、受信ポリシー、ルール更新とリプレイ、転送/派生/開示、ステークされたアゴラ、異議申し立てウィンドウ、ディスパッチ）を含む152のテストからなるFoundryスイート。

参照スタックはリポジトリのビルドから[[Sepolia|Sepolia (テストネット)]]にデプロイされており（デプロイされたランタイムのメタデータハッシュはローカルビルドと一致します）、境界ケース1、4、5、8、9、11は3人のアクターによって2つのフェーズで実行されました。すべてのトランザクション、ガス数値、読み出しは[`docs/sepolia-evidence.md`](https://github.com/garyyang-finchip/aif-paradigm/blob/main/docs/sepolia-evidence.md)に記載されています。

## スレッドへの質問

1.  4値の結果とその合成順序（`allOf`: not-satisfied > undeterminable > verifier-error > satisfied; `anyOf`: 逆順）は、承認チェックの適切なデフォルトでしょうか？
2.  イベントアンカープロファイルは`scopeRef`を取るべきでしょうか。そうすればスコープ限定の貢献者もアンカーできますが、チャネル全体のロールチェックが適切なデフォルトでしょうか？
3.  デプロイごとに単一のクロックドメイン（[[ERC-6372|ERC-6372]]、参照におけるタイムスタンプモード）は許容されますか、それともレジストリ間のクロック合意は緩和されるべきでしょうか？
4.  11の識別条件は、重複する可能性があることを考慮すると、適切な決定可能なコアでしょうか？
5.  トランスポートバインディング（種類、ターゲット、バージョン、ケイパビリティビット、効果スコープ、採用モード）は、ルーム、フィード、リレー、またはグループがチャネルにどのように接続されるかを記述するのに十分でしょうか、それとも何かが不足していますか？
