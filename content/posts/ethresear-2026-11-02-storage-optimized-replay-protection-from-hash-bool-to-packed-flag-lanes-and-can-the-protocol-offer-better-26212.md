# ストレージ最適化されたリプレイ保護: ハッシュからブール値への変換から、パックされたフラグレーン、そしてプロトコルはより良いものを提供できるか？

増え続けるプロトコルのクラスでは、イベントごとに小さな事実を永続的に保持する必要があります。例えば、この[[glossary/nullifier|ナリファイア]]は使用済み、このノンスは使用済み、このセッションシェアは決済済み、といった具合です。プライバシープールは引き出しごとに[[glossary/nullifier|ナリファイア]]を書き込みます。順序付けされていないノンススキーム（Permit2の`nonceBitmap`、[[glossary/EIP-4337|EIP-4337]]スタイルの二次元ノンス）は、シーケンスされたノンスを保証できないため、リプレイフラグを書き込みます。マシン規模の決済（DePINの接続性、帯域幅、計算）は、決済されたセッションごとにマークを書き込みます。これらすべてを、あるがままに呼びましょう。それはリプレイ保護であり、そのコストは純粋なストレージです。ZKバッチ処理は計算側をほぼ無料にしました。1つの証明が、数千の署名やメンバーシップチェックを一定のコストで検証します。もはや圧縮されないのはフラグです。

**すべてのプロトコルが再発見する進歩。**

最悪のケースであり、依然として最も一般的な形式です。

```
mapping(bytes32 => bool) used;   // one flag, one slot
// every flag: ~22,100 gas (20,000 zero-to-nonzero + 2,100 cold access), state forever
```

これは[[glossary/nullifier|ナリファイア]]セットがどのように見えるかです。キーはハッシュなので、2つのフラグが同じスロットを共有することはなく、何も償却されません。

最初の最適化、フラグIDが密な場合、ワードごとに256個のフラグ。

```
mapping(uint256 => uint256) bitmap;   // key = flagId >> 8, bit = flagId & 255
// first flag in a word: ~22,100; each later flag: ~5,000 (2,100 access + 2,900 reset, own tx)
```

これはPermit2の`nonceBitmap`と[[glossary/EIP-4337|EIP-4337]]パターンです。

2番目の最適化は、1つの操作に複数の関係者が関与する場合に、ワードをレーンに分割することです。キー => u256を4つのu64ページ（または8つのu32、ジオメトリはデプロイ時の選択）に分割し、操作ごとに1つのレーン、関係者ごとに1つのビットを使用します。具体的な形式は次のとおりです。約15分間続く接続セッションが8つの独立したオペレーターを介して中継され、各オペレーターが自身のシェアを決済し、二重決済を防ぐ必要があります。

```
one u256 storage slot, key = H(entity, seq >> 2)

 seq:      4k+3         4k+2         4k+1         4k
        |-- lane 3 --|-- lane 2 --|-- lane 1 --|-- lane 0 --|
 bits:  | 63 ...... 0| 63 ...... 0| 63 ...... 0| 63 ...... 0|
                                                      ^
                                     bit i = operator i settled
                                     its share of session 4k

 example: session 4k settled by operators 0, 2 and 5 so far:
        |000...000   |000...000   |000...000   |000..100101 |
```

```solidity
contract SessionFlags {
    // 4 sessions per word; each session owns a 64-bit lane;
    // operator i on the session's path owns bit i of its lane
    mapping(bytes32 => uint256) private words;

    error AlreadySettled();

    function markSettled(uint64 entity, uint64 seq, uint8 opIndex) internal {
        require(opIndex < 64);
        bytes32 key  = keccak256(abi.encodePacked(entity, seq >> 2));
        uint256 bit  = uint256(1) << ((seq % 4) * 64 + opIndex);
        uint256 word = words[key];
        if (word & bit != 0) revert AlreadySettled();
        words[key] = word | bit;  // first bit in a word ~22,100 gas; every later bit ~5,000
    }
}
```

この進捗における算術では、4セッション x 8オペレーター = 32フラグの場合、素朴な`hash => bool`は32 x 22,100 = 約707,200ガスかかります。レーンレイアウトでは、1回の新規書き込みと31回の安価な書き込みで、約22,100 + 31 x 5,000 = 約177,100となり、1セッションあたり約44,300で、約75%削減されます。密な単一関係者ビットマップはその中間に位置します。

用語を明確にするために説明します。`entity`はクライアントです。`seq`はそのクライアントの操作カウンターであり、`entity + seq`が1つの操作を指します。オペレーターインデックスは、それを処理することに参加した関係者です。DePINオペレーター、リレイヤーなど、特定のプロトコルのサービス提供側がどのようなものであれです。上記のセッション図は、この問題が提起されている理由を視覚的に示したものにすぎず、パターン自体は一般的です。正直な注意点として、`seq`は順序付けが保証されているわけではありません。通常はきれいに増加しますが、ギャップが発生することもあり、ギャップはレーンビットを孤立させるため、ずさんなシーケンス処理によって節約効果が低下します。これは欠陥というよりも実用的なトレードオフです。無秩序にスキップするクライアントには価格を設定したり、評判に基づいて重み付けしたり、単にサービスを提供しないようにしたりできます。クライアントが適切に増加する場合、同じクライアントにサービスを提供するすべての参加者が同じワードに収まり、それらすべてにわたって節約効果が複合的に作用します。

しかし、この進捗がどこで止まるかに注目してください。ジオメトリはデプロイ時に固定されます。64ビットレーンを選択すると、70オペレーターのセッションは収まらず、8オペレーターのセッションでは56ビットが無駄になります。ハッシュ化されたキーは散らばるため、共存はIDが構造的に連続している場合にのみ機能しますが、これは[[glossary/nullifier|ナリファイア]]では決して不可能です。そして、どのようなレイアウトであっても、最初のフラグ以降のすべてのフラグは、すでに存在するワード内の事前に割り当てられた追記専用ビットを1つ反転させるのに約5,000ガスかかり、最初のフラグは常に完全な新規スロットを占有します。固定レーンよりも優れたレイアウトが存在することは確かですが、パッキングジオメトリはそれら2つの下限に近づくことしかできず、下回ることはできません。スケジューリングだけが可能です。

**状況は改善するどころか悪化しようとしています。** ステート成長に関する議論は、新しいステートの価格を高く設定する方向に向かっており（そして[[glossary/EIP-4762|EIP-4762]]の方向にあるステートレスツリーのガスモデルは、証人（witness）の観点から新規タッチコストを上昇させます）。上記のすべての設計は、まさに価格が上昇している料金に依存しています。アプリケーションはより厳密にパッキングし続けることができますが、上限は1ワードであり、それを超えると、多くのユーザーにわたってバッチ処理を行う大規模なアグリゲーターにフラグ書き込みを委ねるしかありません。これは、サマライザーを必要としないように構築されたシステムに、信頼できるサマライザーを密かに再導入することになります。

**一般的な回答と、それがギャップを埋められない理由。** 「フラグはオフチェーンに保ち、ルートを投稿する。」しかし、ルートは決済ではありません。それは後で請求されなければならない約束です。ルートに対する請求は、請求時にメンバーシップまたは非メンバーシップを証明することを意味し、その証明の生成、[[glossary/calldata|コールデータ]]、および検証ガスは、同じプロトコルのユーザーに、後で請求パス上で発生します。節約したストレージ書き込みは請求側のコストとして再出現するため、プロトコル全体のライフサイクルガスが明らかに低くなるとは限りません。そして、ルートの背後にあるセットを維持する者は、この種のシステムが不要としようとしているサマライザーそのものになります。ルートはコストを移動させるだけであり、より良い価格設定の書き込みはコストを削除するでしょう。

**要望: このユースケースのために提供されるストレージ。** [[glossary/EVM|EVM (イーサリアム仮想マシン)]]は、リプレイフラグをその性質に見合った価格で直接サポートできるでしょうか？これは[[glossary/Layer-1|L1]]の問題ではなく、[[glossary/EVM|EVM]]の問題です。スケジュールとステートモデルはほとんどの[[glossary/Layer-2|L2]]とL3に継承されるため、ここでの実行レイヤーの改善は、[[glossary/EVM|EVM]]を実行するすべてのレイヤーに一度に適用されます。考えられる形式は次のとおりです。

1.  *プリミティブとしての共有フラグワード。* 追記専用ビットセット型。既存のワード内の以前ゼロだったビットを設定する際の価格が、一般的な[[glossary/SSTORE|SSTORE (オペコード)]]としてではなく、その限界費用に近い価格で設定されます。上記の5,000ガスビットフリップが目標です。
2.  *スパン割り当て。* コントラクトがN個の連続したスロットの領域を宣言します。割り当てはブランチコストを1回支払い、内部の書き込みはリーフコストを支払います。[[glossary/Verkle-Trees|Verkleツリー]]形式やバイナリツリーのステム/ページ構造は、隣接するリーフを共有ブランチの下にすでにグループ化しているため、構造的割引は存在します。これは、証人（witness）価格設定の実装詳細として残すのではなく、意図的に公開するものです。
3.  *一括アクセス。* 1回のアクセス料金で1つのステムの下にk個の値を書き込む[[glossary/SSTORE|SSTORE (オペコード)]]/[[glossary/SLOAD|SLOAD (オペコード)]]のバリアントまたは[[glossary/Precompile|プリコンパイル]]。
4.  *制限されたセマンティクスに基づく一般的な価格設定。* 追記専用ビットマップ、単調増加カウンター、挿入専用セットなど、境界があり予測可能な状態遷移であり、一般的な読み取り・変更・書き込みではありません。[[glossary/calldata|コールデータ]]と[[glossary/blob|ブロブ]]は、そのセマンティクスが制限されているため、ステートよりも低い価格で設定されています。同じ議論がここでも可能でしょうか？[[glossary/nullifier|ナリファイア]]は難しいケースであることに注意してください。ランダムなハッシュは局所性やワード共有から何も得られませんが、挿入専用セットプリミティブはそれらを直接処理するでしょう。

**質問。**

1.  1つのワード内で、固定レーンよりも優れたものはありますか？関係者数が変動しても無駄なビットが少なく、デプロイ時にジオメトリが固定されない、可変幅ページ、ランク/セレクト形式のインデックス、またはその他のレイアウトはありますか？
2.  [[glossary/EIP-4762|EIP-4762]]形式の価格設定の下で、ステム境界を中心にストレージレイアウトを設計することは健全な戦略ですか、それとも実装詳細の悪用ですか？
3.  制限されたセマンティクスに基づく書き込みは、一般的な[[glossary/SSTORE|SSTORE (オペコード)]]よりも低い価格で正当化できますか、それともより安価な永続書き込みパスはステート成長の再価格設定と真っ向から対立しますか？
4.  どの[[glossary/EVM|EVM]]チェーン（[[glossary/Layer-2|L2]]またはL3）も、この点に関して[[glossary/mainnet|メインネット]]よりも速く動くことができます。それらのいずれかがすでにストレージの局所性を価格設定しているか、一括または追記専用ストレージ操作を提供しているか、そしてそこから何を学んだでしょうか？
5.  このようなものがなくステートの再価格設定が行われた場合、イベントごとのフラグは単純に[[glossary/EVM|EVM]]ステートに属さないという正直な結論になるのでしょうか？もしそうなら、信頼できるサマライザーに行き着かない場所で、それらはどこに属するのでしょうか？

賭け金は、誰がバッチ処理を行うかです。証明は誰もが検証を安価にできるようにしましたが、フラグストレージは、ワードあたり最も多くのユーザーを集約する者だけが償却を得られるように価格設定されています。小さなオペレーターが巨大なオペレーターと同じ限界費用でフラグをパッキングできるプリミティブは、どのレイヤーで出荷されても、この最適化の分散化を維持するバージョンです。
