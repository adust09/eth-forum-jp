> [Letting the base fee be a midpoint: a temporal liquidity authorization for EIP-1559](https://ethresear.ch/t/letting-the-base-fee-be-a-midpoint-a-temporal-liquidity-authorization-for-eip-1559/25958) — DanGuo (2026-09-10)

日付: 2026年9月9日

[[glossary/EIP-1559|EIP-1559]]では、[[glossary/base-fee|ベースフィー]]がフロア（下限）となっている。含まれるすべてのトランザクションは、1ガスあたり少なくとも`base_fee`を支払い、送信者はより少ない支払いの代わりに後続のポジションを取ることを提案できない。また、`max_fee`がベースフィーを下回るトランザクションは、ブロックに到達する前に無効となる。

プロトコルは、時間的な優先度ではなく、支払い意思を観測する。数秒以内に価値を失う清算と、3ブロック後でも同等に良い財務転送は、同じ入札を提出でき、両者を区別するものはない。後者には、その意思を表明する方法も、表明したことに対して報酬を得る方法もない。

この投稿では、両方の事実を変更する1つのフィールドについて、私が発見できた最小のスコープで説明する。それは、1ブロック、新しいプロトコル状態なし、後続のスロットへの延期なしというものである。これはメカニズムのスケッチであり、[[glossary/EIP|EIP（Ethereum 改善提案）]]ではない。このアイデアの元となる一般的な考え方は、[RN-12](https://github.com/TLM-Research/TLM/blob/2e51f408042f6c0da23550a75d7e20b0cd358832/docs/Research-Notes/RN-12_Temporal_Liquidity_Market_Mechanism_Design.md)に記載されており、時間的柔軟性を、中立的なベースラインに対して供給、需要、検証、決済できるものとして扱っている。

## 需要の証拠とは何か、そうでないものとは何か

アクティビティの構成は、速度だけでは説明しにくい形でチェーン間で異なっている。[RN-14](https://github.com/TLM-Research/TLM/blob/2e51f408042f6c0da23550a75d7e20b0cd358832/docs/Research-Notes/RN-14_The_Demand_Ethereum_Does_Not_Serve.md)が使用するスナップショットでは、SolanaのDEX（分散型取引所）ボリュームは、TVL（預かり資産総額）の約12分の1でEthereumを上回っている一方、TronはSolanaのDEXボリュームの約57分の1で、Solanaの1.43倍のアクティブアドレスを抱えている。これは、取引が一方のチェーンに集中し、支払いのような転送が他方のチェーンに集中していることと一致する。

RN-14は観測的なものである。以下のメカニズムはそれに依存しない。手数料レベルはフローを動かし、最も単純な競合する説明である。分布、インセンティブ、規制の地理、およびEthereumの[[glossary/Rollup|ロールアップ]]戦略も他の説明である。

## メカニズム

[RN-15](https://github.com/TLM-Research/TLM/blob/2e51f408042f6c0da23550a75d7e20b0cd358832/docs/Research-Notes/RN-15_A_Temporal_Liquidity_Authorization_for_EIP-1559.md)は、符号付きフィールドである**時間的流動性承認 (Temporal Liquidity Authorization)** を追加する。

```
TLA > 0    funding leg: authorize a payment, seek an earlier intra-block band
TLA = 0    neither leg: ordinary EIP-1559 treatment, unchanged
TLA < 0    supply leg: commit to a later band, become eligible for funding
```

符号は、トランザクションが交換のどちらの側にあるかを選択する。正のTLAは**時間的流動性資金調達側 (temporal liquidity funding leg)**、負のTLAは**時間的流動性供給側 (temporal liquidity supply leg)** である。これらは取引の反対側であり、単一の量の正負の量ではない。これらは同じ単位ではなく、意味のある符号付き合計はなく、割り当てと決済を通じてのみ出会う。

**資金調達側は金銭である。** 1ガスあたりの手数料ではなく、[[glossary/wei|wei]]での最大一括承認額である。含まれる消費者はブロックローカルプールに資金を供給し、より早いバンドを受け取る。一括払いであるため、消費者の貢献は自身の実現ガス量に依存せず、消費者のガス不確実性を決済から排除する。

**供給側は金銭ではない。** それが供給するのは、実行容量ではなく、後続の処理を受け入れる意思である。その符号は、[[glossary/base-fee|ベースフィー]]を下回るトランザクションをプロバイダー処理にオプトインさせ、その大きさは、含まれた場合にトランザクションを後続のバンドにコミットさせる。補助金を明示したり上限を設けたりするものではない。より大きな負の数値は、より大きな割引ではなく、より後続のポジションを購入する。

プロバイダー処理には両方の条件が必要である。

```
TLA_i < 0
max_fee_i < base_fee
```

オプトインなしで[[glossary/base-fee|ベースフィー]]を下回るトランザクションは、引き続き不適格となる。[[glossary/base-fee|ベースフィー]]を支払えるトランザクションは、負のTLAに署名しても補助金を受け取らない。なぜなら、埋めるべき不足がないからである。

プロバイダー`i`の場合、ビルダーは送信者の承認範囲内で実効チップ`p_i`を選択して公開し、不足分は以下のようになる。

```
0 <= p_i <= min( max_priority_fee_i , max_fee_i )

s_i(p_i) = base_fee + p_i - max_fee_i
```

`p_i`は`max_priority_fee`の全額またはそれ以下である場合がある。チップが高いほどプロバイダーの不足分、ひいてはプールに対する請求額が増加する。プールは[[glossary/gas-limit|ガス制限]]で消費される一方、ビルダーは実現ガス量で収益を得るため、収益最大化を目指すビルダーが常に最大値を取るとは限らない。この選択がビルダーに委ねられるべきか、プロトコルルール、プロポーザースコアリング、またはクリアされたレートに従うべきかは、RN-15のセクション8で検討されている。

プロバイダーは、実現ガス1単位あたり自身の`max_fee`を支払う。消費者プールが不足分を供給し、バーンと選択されたチップを完了する。**プロバイダーは送金を受け取らない。** その利益は、ブロックの[[glossary/base-fee|ベースフィー]]を下回る条件付きインクルージョンであり、これは現在の[[glossary/EIP-1559|EIP-1559]]では禁止されている。

だからこそ、割引はチップの中に留まるのではなく、[[glossary/base-fee|ベースフィー]]を下回る必要がある。混雑時の低価値転送にとっての障壁はバーンであり、優先手数料のみを再分配してもその障壁は残る。

## 予約、決済、および順序付け

[[glossary/Block-Building|ブロック構築]]中、実現ガス量は不明である。RN-15はそれを推定しない。[[glossary/gas-limit|ガス制限]]`L_i`に対して予約し、プロトコルで計測されたガス`g_i`に対して決済する。

```
reserve   R_i = L_i * s_i(p_i)
settle    S_i = g_i * s_i(p_i)
```

`g_i <= L_i`であるため、決済は予約を超えることはなく、推定値は[[glossary/consensus-rule|コンセンサスルール]]に入らない。未使用の予約は消費者の料金を減らし、返金され、他のスロットに持ち越されることはない。ガス切れのプロバイダーは予約額で決済し、何もリリースしないため、予約された以上の引き出しはできない。

資金調達順序と実行順序は別々である。

-   **プロバイダー資金調達**は、不足額`s_i(p_i)`の昇順を使用し、プールが各[[glossary/gas-limit|ガス制限]]予約をカバーすることを条件とする。
-   **実行順序付け**は、`band_i = floor(TLA_i / tla_tick)`を使用し、バンドが大きいほど早い。消費者は早いバンドを占め、TLAゼロのトランザクションはゼロ領域を占め、資金提供されたプロバイダーは遅いバンドを占める。

ビルダーはバンド内で順序付けの自由を保持し、バンドのメンバーが1つを共有する場合にバンドル隣接性が機能するようにする。

順序付けルールはオプションではない。もし正のTLAが支払いのみを変更し、ポジションを変更しない場合、消費者は既に持っているサービスに対してより多くを支払い、ゼロ承認が支配的になり、プールは空になり、プロバイダーは資金提供されなくなるだろう。バンドを迂回するプライベートなポジション販売も同じ崩壊を引き起こす。これには部分的なクレジットバージョンは存在しない。

## 変更されるもの、変更されないもの

RN-15は、[[glossary/gas-limit|ガス制限]]、ガススケジュール、またはガス単位が何を表すかを変更しない。変更されるのは**どのトランザクションが許容されるか**である。`max_fee < base_fee`のプロバイダーは現在無効であるが、消費者の承認がその不足分をカバーすると有効になる。

それが利益となるかどうかは、プロバイダーのガスが何を置き換えるかに依存し、2つの希少な量を区別する必要がある。物理的なガスはブロックが制限に達したときにのみ拘束され、[[glossary/base-fee|ベースフィー]]は使用量を目標（制限の半分）に維持するために存在するため、完全なブロックは通常のケースではなくバーストケースである。消費者プールは、承認された資金が許容されるプロバイダーの要求を下回ったときにいつでも拘束され、これは半分空のブロックでも発生しうる。

1.  **アイドル容量の許容。** プロバイダーは、ブロックが未使用のままにするはずだったガスを使用する。コントローラーが使用量を目標近くに維持している場合、これは通常のケースであるはずだ。
2.  **資金配分による除外。** 許容されるプロバイダーが使い切る前にプールが枯渇するため、ガスが残っていても一部のプロバイダーは資金提供されない。
3.  **ガス置換。** 制限に達した場合のみ。押し出されるのは、ビルダーの選択の限界にあるものであり、通常のトランザクションである必要はない。それは中立的なトランザクションであるか、不足額の順序付けで負けた別のプロバイダーである可能性がある。
4.  **順序付けのみ。** 含まれるセットは変更されず、ポジションのみが移動する。
5.  **誘発された需要。** メカニズムが存在すると、アプリケーションの動作が変化する。

[[glossary/mainnet|メインネット]]ブロックが実際に[[glossary/gas-limit|ガス制限]]に達する頻度は測定されていない。これらのケースは、トランザクション数、ガス、またはバーンによってランク付けすることはできない。[RN-13 Part II](https://github.com/TLM-Research/TLM/blob/2e51f408042f6c0da23550a75d7e20b0cd358832/docs/Research-Notes/RN-13-Part-II_Capacity_and_Welfare_in_Blockchain_Execution_Systems.md)は、クラス別の許容および置換された需要、時間的および配分的な厚生、実質資源コスト、支払いとバーン、ビルダーインセンティブ、公平性、および動的安定性というベンチマークを提示している。

## いくつかの注意点

追加のバーンは[[glossary/ETH|ETH]]を破壊するため、ホルダーの利益は純発行量を通じて拡散し、メカニズムを採用しなかった当事者とも共有される。また、より高い手数料は、社会的価値ではなく、個人の支払い意思を明らかにする。

このノートが提起するもう一つの疑問は、プロバイダーのガスは通常の需要と同じように[[glossary/base-fee|ベースフィー]]シグナルに計上されるべきか、という点である。プロバイダーは、消費者の資金が不足分をカバーしている間のみ許容されるため、そのガスは資金提供されていない需要とは異なり、自己制限的である。次のブロックにプールがない場合、それは含まれず、変更されていない[[glossary/base-fee|ベースフィー]]は既にそれを除外している。

RN-15は、その根拠に基づいて1つのソース認識ルールを提案し、それをシャドウコントローラー実験として扱っている。[[glossary/Ethereum-validator|イーサリアムバリデータ]]は引き続き完全な物理ガスを実行および計測するが、コントローラーの入力のみが変更される。そのルールと代替案はノートに記載されている。

文脈的有効性：[[glossary/base-fee|ベースフィー]]を下回るトランザクションは、十分な同一ブロック内資金提供がある場合にのみ有効となるため、包含可能性はブロック構成に依存する。

第二の承認：`max_fee`は引き続き[[glossary/EIP-1559|EIP-1559]]のガスコンポーネントに上限を設ける一方、正のTLAは時間的料金に別途上限を設ける。

## なぜこれがブロック境界で止まるのか

スコープは意図的である。RN-15は、現在の[[glossary/EIP-1559|EIP-1559]]との違いを、両面メカニズムが許容する最小限に抑えている。すなわち、1つのフィールド、1つのブロック、プロトコルが保持する残高なし、[[glossary/base-fee|ベースフィー]]ルールやバーンへの変更なしである。

両方の側は同じブロックに現れる必要があり、一方、1スロット離れて取引するはずだった消費者とプロバイダーは全く取引しない。どちらかを緩和するということは、時間的流動性がブロックを越えて持続することを許容することを意味し、プロトコルが保持する状態、所有権と引き出しルール、そして[[glossary/base-fee|ベースフィー]]と相互作用する第2のコントローラーが必要となる。[RN-16](https://github.com/TLM-Research/TLM/blob/e51f408042f6c0da23550a75d7e20b0cd358832/docs/Research-Notes/RN-16_A_Two-Leg_Temmporal_Liquidity_Reserve_for_EIP_1559.md)（作業ドラフト）は、隣接するスロットについてこれを扱っている。資金調達側は金銭であり、プロトコル状態として持ち越すことができる一方、供給側はビルダーローカルプール内の保留中のプロバイダートランザクションとなり、これは[[glossary/consensus-state|コンセンサス状態]]ではなく、すべてのビルダーで同じセットである必要はない。さらに、[RN-17](https://github.com/TLM-Research/TLM/blob/main/docs/Research-Notes/RN-17_Temporal_Service_Profiles_and_Future_Execution_Tickets.md)は、需要の単位がトランザクションではなくストリームである場合、つまり多くのスロットにわたるケイデンス、期限、または制限された遅延がある場合に何が起こるかを問いかけている。これは提案ではなく、研究課題である。

両者は境界を示すためだけに言及されている。ここでの内容はそれらに依存しない。

## レビューのための質問

1.  **符号付きTLA順序付けは、プライベートなポジション販売やバンドルに対して強制できるか？**
2.  **実効的なプロバイダーチップは誰が選択すべきか？** ビルダーの裁量、プロトコルによる上限、インクルージョンに対するプロポーザースコアリング、またはクリアされたレートか。最高入札プロポーザーオークションは、プロバイダー数や時間的厚生ではなく、収益化可能なブロック価値に報酬を与える。
3.  **条件付きで資金提供されたプロバイダーのガスは、通常の需要と同じように[[glossary/base-fee|ベースフィー]]シグナルに計上されるべきか？** もし割引されるべきなら、どのようなルールに基づくべきか？
4.  アイドル容量の使用、資金配分による除外、ガス置換、時間的価値、ビルダー収益、バーン、公平性を比較するための**適切なベンチマークは何か？** そして、[[glossary/mainnet|メインネット]]ブロックが[[glossary/gas-limit|ガス制限]]に達する頻度はどのくらいか。これは、そもそも置換が重要かどうかを決定する。
