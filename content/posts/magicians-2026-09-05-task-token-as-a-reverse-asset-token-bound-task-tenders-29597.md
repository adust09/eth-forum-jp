## この非対称性が解消するもの

エージェントエコノミーは、市場の一方の側面を構築してきました。

[[glossary/ERC-8338|ERC-8338 (トークン結合型実行可能スキル)]]は、*能力*をトークンにラップします。これは、価格設定、所有、転送、実行が可能なアーティファクトです。供給側です。「これが私ができることであり、これがあなたにかかる費用です」と答えます。

標準的なものは、その反対側、つまり「これが私が必要としていることであり、そのためにすでに資金が確保されています」という問いには答えていません。その側面は、バウンティプラットフォーム、調達ポータル、RFPボードといったアプリケーションのサイロに存在し、それぞれが独自の[[glossary/Agent-Escrow|エスクロー]]、独自の承認ルール、独自のレピュテーショングラフを持ち、それらのどれもが構成可能ではなく、すでに登録していない相手方からは検査できません。

変換として述べると、供給側は以下を実現します。

```
T( f(v), $ ) = ( $, v )

```

能力が実行可能な資産にラップされ、金銭と交換されます。需要側はその逆です。

```
T( v, f⁻¹($) ) = ( $, v )

```

金銭が*タスク*にラップされ、能力と交換されます。これらを組み合わせると、市場は双方向で完全になります。

```
T( f(v), f⁻¹($) ) = ( $, v )

```

両側がオンチェーンのアーティファクトとなり、間にプラットフォームを介さずに互いを見つけられるようになります。この提案は、2番目の変換を規定します。**完全なドラフト仕様テキストは、以下の最初の返信に続きます。**

各変換には2つのテンポがあり、完全性の主張は両側で両方がカバーされている場合にのみ成立します。

| | 供給側 ([[glossary/ERC-8338|ERC-8338]]) | 需要側 (この提案) |
| --- | --- | --- |
| 静的 — 1回の交換で完了 | 静的スキル[[glossary/Token|トークン]] | 静的[[glossary/Task-Token|タスクトークン]]：1つの[[glossary/Task-Tender|テンダー]]、1つの[[glossary/Vault|ボルト]]、作業が承認されたときに決済される |
| 連続 — 計測されたストリーム | APIコールトークン (呼び出しごと / 期間ごと / 計算ごと) | ファセット[[glossary/Task-Token|タスクトークン]]：ボルトが補充される限り、配達ごとに支払い続ける継続的な需要 |

ファセット[[glossary/Task-Token|タスクトークン]]は、2番目のメカニズムではありません。これは、[[glossary/Cadence|ケイデンス]]フィールドが設定された同じ[[glossary/Task-Tender|テンダー]]条件です。`rewardPerCompletion`はカウントで計測され、`epochLength`は時間で計測され、タスクパッケージ自身の「1回の完了」の定義は作業単位で計測されます。`fundTask`（誰でも、いつでも）でタップが開き、`cancelTask`で閉じられ、進行中のすべてのデリバリーは保護されます。4つの象限、1つのカーネル、モードフラグなし。

## タスクトークンとは

[[glossary/ERC-721|ERC-721]]の拡張です。トークンは[[glossary/Task-Tender|テンダー]]そのものです。そのIDはタスクであり、その残高はバウンティです。

**資金は文字通りトークンの中にあります。** 各[[glossary/Task-Token|タスクトークン]]は、個別の**ボルト**アカウントを所有します。誰でもエクスプローラーでその残高を検査できます。誰でも通常の転送で補充できます。所有者、発行者、審査員、[[glossary/ERC-721|ERC-721]]承認者を含め、誰一人として決済または返金以外でそこから引き出すことはできません。報酬が約束である[[glossary/Task-Tender|テンダー]]は願いです。報酬が確認できるアドレスにある[[glossary/Task-Tender|テンダー]]は信用証書であり、古典的な金融における債権や調達契約のように取引されます。資金提供された[[glossary/Task-Token|タスクトークン]]は、履行前に交渉可能です。

**3つの権限、3つのスロット。** 所有権、発行権限、そして*判断*権限は分離されており、個別に譲渡可能です。[[glossary/Task-Tender|テンダー]]を投稿する当事者が、作業が完了したかどうかを決定する当事者である必要はありません。この分離こそが、中立なインフラを可能にします。あるベンダーが承認したベンチマークはマーケティングですが、そのベンダーが多数決で覆せない委員会が承認したベンチマークはインフラです。

**1つのスロットが判断スペクトル全体をカバーします。** `acceptanceAuthority`はアドレスであり、アドレスは何でもあり得ます。

| N | スロットに入るもの | 誰が決定するか |
| --- | --- | --- |
| 0 | [[glossary/Verifier-contract|検証者コントラクト]] | 誰も決定しない — 証明がパーミッションレスに決済する |
| 1 | [[glossary/EOA|EOA]] | 1人の指名されたレビュー担当者 |
| >=2 | K-of-Nパネルコントラクト | 単一の当事者が制御できない委員会 |

カーネルは、それがどれであるかを知る必要がなく、知る必要もありません。判断ガバナンスは標準の外部に留まり、そこにあるべきです。単一の[[glossary/Signer|署名者]]からパネル、[[glossary/DAO|DAO]]へと進化させることは、1回の`setAcceptanceAuthority`呼び出しであり、標準の変更ではありません。

**3つのアンカー、1つの不変の基盤。** `tdHash`はプレーンテキストの主要ドキュメントを固定し、`taskHash`はタスクパッケージ全体の決定論的にエンコードされた[[glossary/DAG-CBOR|DAG-CBOR]]オブジェクトグラフを固定します。コントラクトによってインクリメントされる`version`は、改訂履歴を偽造不可能にします。改訂されたスコープは`tdHash`を一定に保ちながら`taskHash`を移動させます。そして、デリバリーは*どの改訂版に回答したか*を記録するため、「開始後に仕様を変更した」という主張は、議論ではなく検証可能なクレームになります。

`taskHash`の下にあるオブジェクトモデルは、[[glossary/ERC-8338|ERC-8338]]の[[glossary/SkillRoot|SkillRoot]]と意図的に**バイト互換**です。同一の決定論的[[glossary/DAG-CBOR|DAG-CBOR]]エンコーディング、同一の[[glossary/CID|CID]]リンク形式、同一のパスルール、同一の機密性記述子。1つのパッカー、1つの検証者、1つのメンタルモデルが市場の両側にサービスを提供します。そして、それ自体が実行可能なスキルパッケージである成果物は、`resultHash`をそのパッケージのハッシュにポイントすることでタスクを決済し、逆資産を順資産に変換します。

すべての履行形態は、3つのコードパスではなく2つの数値から導き出されます。排他的 (`maxCompletions = 1`)、複製 (`maxCompletions = N`、N個の独立した支払い)、共同 (`maxCompletions = 1`、記録上の履行者 = 分割コントラクト)、およびファセット[[glossary/Task-Token|タスクトークン]] (`epochLength != 0`、期間ごとにペースが設定され、自由に補充可能) です。

## 設計を形作った問題

需要側の資産には、供給側にはない非対称性があります。**需要者は、支払いをするかどうかを決定する前に作業を受け取ります。**

最初のバージョンではこれが間違っており、作成された作業例がそれを証明しました。出品者は、納品された結果を読み取り、[[glossary/Task-Tender|テンダー]]をキャンセルし、ボルト全体を回収することができました。履行者の費用で、無料で内容を確認できてしまうのです。

この問題を解決するのが、3つの相互に連動するルールであり、これがカーネルの核心です。

1.  **デリバリーは予約します。** 保留中の提出は、1つの完了スロットと1つの報酬を保持します。その資金はもはや分配できません。
    
2.  **キャンセルは保留中のデリバリーを追い越せません。** 作業が未決定の間は、ボルトから何も引き出されません。
    
3.  **沈黙は履行者に支払われます。** すべての提出には`judgmentWindow`が付随します。それを過ぎると、履行者がデフォルトで請求します。何も言わない審査員は「はい」と言ったことになります。拒否する権利も同時に失効するため、審査員は期間を過ぎてから拒否で請求を[[glossary/Front-running|フロントラン]]することはできません。
    

ルール3は、ルール2を人質状態ではなく、境界のあるものにするものです。すべての予約は時間とともに解決されるため、資金提供者は最終的に全額を取り戻すことができます。

## この標準が意図的に*行わない*こと

これらを明確に述べる方が、後で発見されるよりも良いでしょう。

-   **ここにあるものは、需要者がデリバリーを拒否し、それでもそれを使用することを止めません。** カーネルはオフチェーンで何が起こるかを監視できません。カーネルが行うのは、拒否を*名前付き、タイムスタンプ付き、拒否された正確な`resultHash`に固定する*ことです。これは、評判、仲裁、訴訟の生データであり、どのバウンティプラットフォームのプライベートデータベースも提供しないものです。
    
-   **スロット占有はポリシーの問題です。** 予約モデルでは、すべてのスロットをジャンクで埋めることはサービス拒否になります。ボンド、[[glossary/Allowlist|アローリスト]]、および[[glossary/Admission-hook|アドミッションフック]]は、カーネルではなくポリシー層に属します。（マシンパスでは、カーネルは対応する機能を提供します。期限を過ぎると、有効な証明を生成しなかった提出は、誰でも`releaseExpired`を介して解放できるため、ジャンクが検証者決済されたボルトを永遠に凍結することはありません。）
    
-   **機械決済は信頼を移動させますが、信頼を排除するわけではありません。** 検証者を操作する者が正しさを定義します。その利点は、その定義が誰でも読めるデプロイされたコントラクトであることであり、買い手の外部からは見えないQAプロセスではありません。
    
-   **カーネルには手数料モデルはありませんが、手数料を付加できる3つの強制可能な場所があります。** カーネルは1つの当事者に支払い、1つのクラスに返金します。その中に手数料があると、デリバリーも資金提供もしていない誰かに資金がボルトから流出する唯一の経路となります。資金がトークン*内*にあるため、手数料は資金提供の入り口（ルーターが`fundTask`をネットで呼び出す）、決済の出口（記録上の履行者が分割コントラクトである）、または判断スロット（独自の報酬[[glossary/Agent-Escrow|エスクロー]]を保持する委員会コントラクト）に付加され、それぞれが承認ポリシーによって強制可能であり、単なる助言ではありません。
    
-   **発見、入札、評判、紛争解決は一切行いません。** これらはすべてスコープ外であり、その上に構築可能です。
    

## 既存の技術と、これがそれらではない理由

[[glossary/ERC-1081|ERC-1081 (標準バウンティ)]]は最も近い祖先であり、これが単なる「またバウンティか」ではない理由です。バウンティは*投稿するコントラクト*ですが、[[glossary/Task-Token|タスクトークン]]は*所有する資産*です。この区別は具体的な違いを生み出します。共有コントラクトの混在する台帳ではなく、残高がどのエクスプローラーにも表示されるトークンごとのボルト。オフチェーンの文字列ではなく、バージョン管理されたコンテンツアドレス指定可能なオブジェクトグラフとしてのタスクID。発行者の特権ではなく、個別に譲渡可能な権限としての判断。発行者に資金を返すのではなく、沈黙時にワーカーに支払う期限。そして[[glossary/ERC-721|ERC-721]]の転送可能性により、資金提供された[[glossary/Task-Tender|テンダー]]は履行前に交渉可能です。

[[glossary/ERC-8183|ERC-8183 (エージェント型商取引)]]は、エージェントがどのように取引するか、つまり支払い承認とインテント実行を標準化します。これは直交的かつ補完的です。作業自体にID、バージョン履歴、[[glossary/Agent-Escrow|エスクロー]]された価格、または承認ルールを与えるものではありません。[[glossary/Task-Token|タスクトークン]]は、エージェント型商取引フローが*購入できる*ものです。

[[glossary/ERC-8338|ERC-8338 (トークン結合型実行可能スキル)]]は意図的な鏡像です。同じアーティファクト規律（コンテンツアドレス指定パッケージ、オンチェーンアンカー、機密性記述子、バイト互換パッカー）ですが、経済学は逆転しています。両者は意図的に分離されています。どちらも他方をインポートせず、それぞれが単独で有用です。両者が揃うことでループが閉じます。（リポジトリ名もこれに合わせています：`skill-token-standard` / `task-token-standard`。）

**そして、残りのエージェントスタックは、そこでの構成と同様にここで構成されます。** [[glossary/ERC-8338|ERC-8338]]スレッドで議論されたレジストリおよびディスカバリ層 — [[glossary/ERC-8338|ERC-8338]]スレッドで議論されたレジストリおよびディスカバリ層 — [[glossary/ERC-8239|ERC-8239 (エージェントスキルレジストリ)]]および[[glossary/ERC-8257|ERC-8257 (エージェントツールレジストリ)]]スタイルのインデックス — は、`TaskRef = (chainId, taskContract, taskTokenId)`をキーとして[[glossary/Task-Token|タスクトークン]]を同一にインデックス化できます。[[glossary/Attestation|アテステーション]]イベントは、正確なバージョン精度で`taskHash + version`を固定します。[[glossary/ERC-8004|ERC-8004]]スタイルのエージェントIDは、[[glossary/Task-Tender|テンダー]]の両側の当事者を命名します。そして、[@babyblueviper1](https://ethereum-magicians.org/u/babyblueviper1)が[[glossary/ERC-8299|ERC-8299 (WYRIWE)]]と[[glossary/ERC-8323|ERC-8323 (オンチェーンAIエージェントシステム)]]についてそこで明確にしたレイヤー化は、需要側に変更なく引き継がれます。この標準は、*どのバイトが要求され、どのコミットされた基準に対して何が決定されたか*を証明します。実行が実際に承認された結果を生成したかどうかは、[[glossary/Binding|バインディング]]の内部ではなく、その上にレイヤー化される[[glossary/Attestation|アテステーション]]作業です。判断実行[[glossary/Attestation|アテステーション]]コンパニオンは、`acceptanceAuthority`スロットが開放されたまさにその目的のためのものです。

## この標準がどのように強化されたかについて

この投稿の前に14の欠陥が発見され修正されました。3つは作業例の構築中に、11は3回の外部レビューを通じてです。これらを挙げる価値があるのは、需要側の資産が供給側の資産とは異なる方法で失敗するためです。

-   前述の**フリールック** — 作業を読んでからキャンセルする。
    
-   **マシンパスのブリック化**：ジャンクな提出が検証者決済された[[glossary/Task-Tender|テンダー]]を永遠にフリーズさせました。なぜなら、それらを拒否する審査員がいないからです。
    
-   **ペース設定のバイパス**：デフォルトの請求がエポック境界を無視し、継続的な[[glossary/Task-Tender|テンダー]]の予算全体を単一のエポックで使い果たしました。
    
-   **遅延拒否**：審査員が期間終了*後*に拒否でき、履行者の請求を[[glossary/Front-running|フロントラン]]できました。
    
-   **飛行中の権限スワップ**：作業を受け取った後、判断スロットをスワップして、どちらの方向でも期限を回避できました。これは、デリバリー時に決済モードをスナップショットすることで修正されました。
    
-   **永久的なボルトロック**：支払いを拒否する履行者が、その提出を`Pending`状態に永遠に固定し、その背後にあるすべての返金も同様に固定しました。これは、異常な受取人という些細な原因によるボルトの全損失です。これは遅延拒否の修正によって導入されたリグレッションでした。決済は現在、リバートする代わりにクレジットを付与します。
    
-   **到達不能なエスケープハッチ**：そのクレジットメカニズムは、プッシュパスとプルパスの両方でガスを少なすぎたため、クレジットが救済対象のコントラクトによって回収できませんでした。プッシュパスは境界がありますが、プルパスはそうではありません。
    
-   **返金の順序依存性と取り残されたダスト**、未チェックの`uint64`期限オーバーフロー、返金比率がすでにフリーズされた後に受け入れられた資金提供、および3つのパッカーの欠陥 — 大文字小文字を区別しないファイルシステムでタスクのソースを削除する可能性のあるものを含む。
    

これらすべては、バグがあったコードに対して失敗するテストでカバーされています。

さらに、我々自身が遭遇し、セキュリティ上の考慮事項に書き込んだハザードが1つあります。[[glossary/ERC-165|ERC-165]]識別子は関数*セレクター*のXORであるため、返される構造体の形状を変更すると（決済モードのスナップショットを追加したように）、`submissionOf`をデコードするすべてのコンシューマーが壊れ、識別子はそのまま残ります。戻り値の型が重要な場合は、識別子ではなく[[glossary/ABI|ABI]]またはバイトコードを固定してください。

## フォーラムの皆様のご意見を伺いたい点

フォーラムの皆様のご意見を伺いたい点です。

1.  **デフォルトの方向性。** 沈黙は履行者に支払われます。これは[[glossary/Agent-Escrow|エスクロー]]を境界のあるものにする選択ですが、買い手に監視の負担を課します。これは*需要側の*資産にとって正しいデフォルトでしょうか、それともカーネルは両方の方向性を提供し、発行者がミント時に選択できるようにすべきでしょうか？
    
2.  **予約と承認。** スロット占有は現在、ポリシーの問題です。バイトに見合うカーネルレベルのプリミティブ — 最小提出ボンド、[[glossary/Admission-hook|アドミッションフック]] — はあるでしょうか、それともそれは厳密に外部に属するべきでしょうか？
    
3.  **[[glossary/ERC-8338|ERC-8338]]との構成。** 2つの標準は意図的に分離されています。薄い、オプションのマッチングインターフェースのケースはあるでしょうか、それとも分離こそが機能でしょうか？
    
4.  **検証者向け`taskHash`の可視性。** 検証者は現在、ライブの[[glossary/Binding|バインディング]]のみを読み取ることができ、過去の[[glossary/Binding|バインディング]]は読み取れません。ビュー関数を設ける価値があるでしょうか、それともスコープクリープでしょうか？
    
5.  **審査員報酬を[[glossary/Task-Tender|テンダー]]条件として。** 第三者委員会には支払いが必要であり、今日その[[glossary/Agent-Escrow|エスクロー]]は委員会コントラクト内にあります。より狭いカーネル内形式も考えられます。発行者が設定する`judgmentFee`（デフォルトはゼロ）で、承認時にのみボルトから`acceptanceAuthority`に支払われるようにすることで、[[glossary/Task-Tender|テンダー]]の全価格がトークンとともに移動します。これはインターフェース識別子を変更するため、このドラフトには意図的に含まれていません。これはカーネルに属するべきでしょうか、それとも審査員に属するべきでしょうか？
