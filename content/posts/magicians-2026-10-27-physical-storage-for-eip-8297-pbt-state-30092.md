## 概要

[[glossary/EIP|EIP]]-8297は、ヘキサリMPTを[[glossary/Partitioned-Binary-Tree|パーティション化されたバイナリツリー (PBT)]]に置き換えます。キーにはゾーンプレフィックスが付与され、ノードはバイナリになり、パスは長くなります。[[glossary/mainnet|メインネット]]では、書き込まれたストレージリーフの上には45〜48個のブランチレコードがあり、アカウントリーフの上には32個あります。ストレージ層は、現在よりも更新あたりのレコード数が多くなり、ブロックごとに変更されるレコードと決して変更されないレコードとの間の分割が異なります。

私たちは、イーサリアム[[glossary/mainnet|メインネット]]の2つの異なる週のデータをPBTにリプレイし、そのステートをディスク上に配置する8つの方法を、すべて同じDRAM予算の下で評価しました。2つの方法は構築され、参照実装と同じステートルートを生成します。6つの方法は、同じリプレイによって供給されるモデルであり、その中には今日のクライアントが使用するレイアウトも含まれます。例えば、パスでキー付けされたトライノードのレベル化されたLSM（Pebble上のgeth、RocksDB上のNethermindとBesu）や、ページをコピーオンライトするB+tree（MDBX上のreth）などです。

これらのレイアウトは、書き込む単位（レコードまたは4KBページ）と、書き込み方法（インプレース、コピーオンライト、ログへの追記、ソート済みランによるマージ）が異なります。ストレージエンジンに16GBのDRAM予算、NVMe価格プロファイル、2つのウィンドウ（24.0M / 23.7M）でのブロックあたりのI/Oコスト（低いほど良い）は以下の通りです。

| 書き込み単位 | インプレース | コピーオンライト | ログに追記 | ソート済みラン (LSM) |
| --- | --- | --- | --- | --- |
| ページ | 17,438 / 17,160 (NOMTスタイルのページストア) | 64,378 / 63,648 (B+tree、MDBX上のrethと同様) | 12,834 / 12,624 (ページログ) | 54,624 / 54,942 (ページLSM) |
| レコード | 未構築 | 未構築 | 6,866–10,248 / 5,046–9,408 (ログ); 5,221–8,603 / 3,397–7,760 (より遅いコンパクションの場合) | 5,854–6,908 / 5,252–6,319 (パスでキー付けされたLSM、geth、Nethermind、Besuと同様); 5,602 / 5,358 (ページでキー付けされた場合) |

両方のウィンドウで3つの発見が確認されました。

1.  **16GB以上では、レコード書き込みがページ書き込みを上回ります。** 最も安価なページ書き込みレイアウトであるページログは、レコード書き込みレイアウトの1.3〜2.4倍のコストがかかります。インプレースページストアは1.7〜3.2倍、コピーオンライトB+treeは6〜12倍です。1つのブロックは約18,000個のレコードを約2,400個のマークルページに分散して変更し、書き込まれる各ページは数個のレコードを変更するために4KBを移動させます。
2.  **レコードレイアウトの中では、LSMとログは1.6倍の範囲内であり、どちらも勝者を決定する1.3倍の基準を満たしません。** geth、Nethermind、Besuが現在実行しているパスでキー付けされたLSMは、すでに最も安価なグループに属しています。キーをパスではなくページでキー付けすると、読み取りミスが半減します（16GBでブロックあたり972回に対し537回）が、コストの約70%はコンパクション書き込みであるため、合計は最大で4分の1しか変動しません。
3.  **16GB未満ではレコードレイアウトは収まらず、ページレイアウトが優位です。** ディスク上のインデックスは、メモリ内に7.5GB（ログ）または9.3GB（LSM）のフィルターとバッファを必要とします。4GBおよび8GBでは、ページログが両方のウィンドウで最も安価なレイアウトであり、NVMeではインプレースページストアの1.3倍、SATAクラスSSDではレコードログの3.3倍です。2GBでは、インプレースページストアが2.9倍で最も安価です。

クライアントチームにとって、これは次のように解釈されます。パスでキー付けされたLSMを使用するチームは、そのエンジンを維持します。ページアラインされたキーはわずかな利得であり、次のレバーはコンパクション増幅です。rethのコピーオンライトB+treeのページは、どの予算でも最もコストのかかるレイアウトであるため、PBTステートをそこから移動させることが、検討すべき最大の変更点です。NOMTスタイルのインプレースページストアは、4GB未満に収まる唯一のレイアウトであり、ログに追記されたものは4〜8GBで最も安価です。

[[glossary/EIP|EIP]]-7870は、[[glossary/full-node|フルノード]]に32GBのRAMを推奨しています。[[glossary/Consensus-Client|コンセンサスクライアント]]とOSがそのメモリを共有するため、ストレージエンジンの割り当てとして約半分、16GBを想定しています。上記の比率は最悪のケースです。各ストアのコストには範囲があり、比率は勝者にとって最も不利な各範囲の端で計算されます。

## レイアウト

2つのレイアウトが構築され、6つが同じリプレイからモデル化されています。モデル化された数値は、リプレイのレコードおよびページストリームと、測定されたキャッシュ動作から得られたものであり、Pebble、RocksDB、MDBXをストアとして実行した結果ではありません。1つのエンジン数値は測定されています。RocksDBにリプレイのレコードストリームを、一度はレコードのLSMとして、一度はログのインデックスとして供給し、各モデルの書き込み増幅を書き込まれたもの（Method）でスケーリングしてテーブルで使用しています。

ページを書き込むレイアウト：

-   **ページストア、インプレース**（構築済み）。NOMTのページ設計に従います。ブランチレコードは、それぞれ6つのツリーレベルを持つ4KBページにパックされ、インプレースで書き換えられます。値は別のBツリーに格納され、その内部ノードはメモリに常駐します。[[glossary/mainnet|メインネット]]のステートサイズで1GB未満の固定メモリを使用します。
-   **ページログ**（モデル化）。同じページをインプレースで書き換える代わりにログに追記し、DRAM内のページあたり16バイトのインデックス（[[glossary/mainnet|メインネット]]サイズで2.2GB）を介して検索します。ログの半分がガベージになったときにコンパクションされます。ランダム書き込みはありません。ブロックあたり2回の同期を行います。
-   **ページLSM**（モデル化）。同じページを、ページIDでキー付けされたレベル化されたLSMの4KB値として扱います。
-   **コピーオンライトB+tree**（モデル化）。レコードはキー順に4KBページに格納され、リーフあたり33個です。コミットは、変更されたすべてのリーフと内部ページを新しい場所にコピーし、2回同期します。これは、rethノードがMDBXの下でトライを保持するレイアウトです。

レコードを書き込むレイアウト：

-   **ログ**（構築済み）。変更されたすべてのレコードはログに追記されます。古いコピーはガベージとなり、コンパクションによって回収されます。各レコードをその位置にマッピングするインデックスは、[[glossary/mainnet|メインネット]]サイズ（50億レコード）でDRAMに72GBを必要とするため、書き込みバッファとエントリごとのフィルターをメモリに持つレベル化されたマージツリーとしてディスクに保持されます（7.5GB固定）。2つのコンパクション設定で報告されています。ログの半分がガベージになったとき（ディスク上のライブデータの最大2倍）または3分の2がガベージになったとき（最大3倍）にコンパクションします。
-   **パスでキー付けされたレコードのLSM**（モデル化）。すべてのレコードは、そのツリー位置でキー付けされたレベル化されたLSMの1つのエントリであり、geth（Pebble）、Nethermind、Besu（RocksDB）がトライを保持するレイアウトです。エンジン定数はログのインデックスと同じです。256MBの書き込みバッファ、レベルは10倍に成長し、メモリ内のエントリあたり1.85バイトのフィルター（9.3GB固定）です。2つのキャッシュバリアントがあります。レコードのキャッシュ（gethのクリーンキャッシュ）と4KB SSTブロックのキャッシュです。
-   **ページでキー付けされたレコードのLSM**（モデル化）。キーが（ページレベル、6レベルアラインされたパスプレフィックス、ページ内の位置）として配置された同じLSMで、1つの4KBデータブロックが1つのページのレコードを保持します。書き込みはパスでキー付けされたLSMと同様に行われ、読み取りはページストアと同様に行われます。

## 方法

-   データ：公開されているXatuデータセット（ethpandaops、CC BY 4.0）からのステート差分と実行読み取り。各ブロックの純変更は、作成、書き換え、削除に分類されます。ブロックが変更しないキーの読み取りは、実行読み取りとしてリプレイされます。
-   未変更ステート：リプレイはフルステートをロードしません。書き込まれたすべてのパスの横に、フルステートがキーを持つであろう場所にスタンドインリーフを配置し、パスが[[glossary/mainnet|メインネット]]の深さを持つようにします。それらの位置は、ステートサイズの統計と[[glossary/EIP|EIP]]-8297のハッシュ配置から導かれます。テストでは、縮小されたツリーがフルツリーと同じレコードを出力することを確認します。
-   キャッシュ：すべてのレイアウトは同じ総DRAMを受け取ります。固定部分（インデックス、フィルター、常駐ノード、バッファ）が最初に支払われ、残りはLRUキャッシュです。ミス数は、リプレイのスタック距離プロファイルから得られます。
-   コスト：ランダム読み取り、シーケンシャルバイト、ランダムページ書き込み、fsyncを、2つのデバイスプロファイルで価格設定します。NVMeプロファイルでは、ランダム4KB書き込みはシーケンシャル4KB書き込みの4倍、ランダム読み取りは3倍のコストがかかります。SATAクラスプロファイルでは、それぞれ16倍と10倍です。
-   書き込み増幅は、各マージツリーの1つのエンジンモデルを介したリプレイ自身の更新ストリームから得られ、そのサブツリーのスケール（5レベル、未変更ステートがコールドエントリとしてインターリーブされている）で、そのサブツリーの1つに対して同じストリームを供給されたRocksDB 11.8と比較してチェックされます。モデルは、ログのインデックスに対して更新あたり15.5を与えます。この場合、更新の半分はバッファが吸収しないコンパクション再配置です。RocksDBはそれの0.83を書き込み、再配置が少ないより遅いコンパクション設定では0.88を書き込んだため、テーブルでは12.9と9.8を使用します。レコードのLSMに対しては、レコード更新あたり5.5を与えます。これは再配置がありません。RocksDBはそれの1.01を書き込みました。ページLSMのページ更新あたり8.6はモデルのみです。チェックはフラッシュとコンパクションによって書き込まれたエントリをカウントします。バイト単位では、RocksDBはモデルの81Bに対してエントリあたり64Bと少なく書き込みます。これは、プレフィックス圧縮とSnappyがモデル化されていないためです。
-   評価：6つのファミリー（ページストア、ページログ、ページLSM、B+tree、ログ、LSM）があり、それぞれ最悪のケースで最も良いバリアントで表されます。あるファミリーが最も安価であると判断されるのは、両方の範囲の端で、そのファミリーにとって最も不利な場合でも、他のすべてのファミリーを1.3倍以上上回る場合のみです。
-   スケール：キー空間は4つのアドレスハッシュサブツリーに分割され、個別にリプレイされて結合されます。10,000ブロックのウィンドウでは、結合された結果は単一のフルリプレイと1%以内で一致します。

## 結果

1.3倍ルールによる最も安価なファミリー：4GBではページログ（ページストアに対して1.30倍/1.30倍）、8GBではページログ（1.35倍/1.34倍）。16GBではログとLSMの間で未決定（LSMが最大1.54倍/1.48倍先行、ログが最大1.07倍/1.58倍先行）、32GBでも未決定（2.01倍/1.89倍対1.46倍/1.39倍）。128GBではログがDRAMにインデックスを保持でき、ブロックあたり1,427–3,966 / 1,390–3,572となりますが、これはどの[[glossary/full-node|フルノード]]も持たない予算です。

SATAクラスSSDで16GBの場合：ページストア 68,460 / 67,470；ページログ 15,420 / 14,792；ログ 12,486–23,760 / 6,399–20,942、または3分の2でコンパクションされた場合 10,841–22,115 / 4,750–19,293；パスでキー付けされたLSMはレコードキャッシュで 10,241–13,753 / 8,446–12,004、ブロックキャッシュで 15,260 / 13,703；ページでキー付けされたLSM 9,400 / 8,802；ページLSM 57,028 / 56,902；B+tree 255,588 / 253,033。ここではランダム4KB書き込みがシーケンシャル書き込みの16倍のコストがかかるため、インプレースページストアとB+treeはさらに遅れをとり、ランダム書き込みのないページログはブロックキャッシュLSMの1.1倍以内に収まります。

観察：

-   ページストアとB+treeは、ブロックあたり約4,000回と15,000回のランダム書き込みによって制約されます。それらの読み取りはすべてのレイアウトの中で最も少なく、1つのページがツリーの6つのレベルを保持し、コールドパスがログの読み取りの5分の1のコストであるためです。
-   ログはミスあたり2回の読み取り（インデックスとレコードでそれぞれ1回）を支払い、その範囲は最も広いです。これは、リプレイ開始以来変更されていないレコードの読み取り（ブロックあたり約850回）が実際のノードでキャッシュされるかどうかによって変動するためです。これが書き込みではなく、LSMを上回ることを妨げています。ガベージの半分ではなく3分の2でコンパクションすると、書き込みはブロックあたり6.4MBに削減され、LSMの9.7MBを下回ります。
-   ガベージコレクションは両方のログにとってレバーとなります。16GBのNVMe（24.0M / 23.7M）では、レコードログはガベージの半分でコンパクションされた場合、ブロックあたり6,866–10,248 / 5,046–9,408のコストがかかりますが、3分の2では5,221–8,603 / 3,397–7,760、5分の4では4,298–7,680 / 2,466–6,829となります。ページログは12,834 / 12,624、その後9,904 / 9,702、その後8,439 / 8,241です。ディスク使用量はライブデータの2倍、3倍、5倍に増加します。
-   LSMの書き込み増幅率5.5が2番目の発見を決定します。モデルは、256MBのバッファの下でこのリプレイからそれを測定します。このバッファは、レコード更新の4分の3がレベルに到達する前に吸収し、同じレコードを供給されたRocksDBはそれの1.01倍を書き込みました。レベルごとに、エンジンは上部でより多く書き込みます。そこではメンテーブルがフラッシュされるまでエントリのすべてのバージョンを保持し、下部ではより少なく書き込みます。そこではモデルの11に対して移動されたエントリあたり7〜8エントリを書き換えます。この2つは相殺されます。増幅率が15の場合、パスでキー付けされたLSMは16GBでブロックあたり12,172–13,226 / 11,494–12,562のコストがかかり、ログに遅れをとります。30の場合、22,094–23,147 / 21,255–22,322のコストがかかり、ページログに遅れをとります。ログのインデックスの場合、RocksDBはモデルの15.5の0.83（ガベージの3分の2では0.88）を書き込んだため、ログの数値はモデル自身の3〜12%下回ります。この超過はより深いレベルにあり、モデルはエンジンよりも移動されたエントリあたりより多くのレベルを書き換えます。
-   実行読み取りは結果にほとんど影響を与えません。ブロックが読み取るほとんどのキーはすでにキャッシュされています。

## 時間計測I/O

モデルの背後にあるデバイスプロファイルをチェックするために、各レイアウトの特定のDRAMサイズでのブロックあたりのI/Oカウントを取得し、ページキャッシュをバイパスした400GBファイルに対して実行します（Linuxでは`O_DIRECT`、macOSでは`F_NOCACHE`）。これにより、レイアウトが発行するI/Oの時間が計測され、フルエンジンではありません。コミットI/Oは事前にわかっているため、32個ずつ発行されます。キャッシュミスした実行読み取りは、プリフェッチなしのクライアントと同様に、1つずつ発行されます（ログの場合はそれぞれ2つの依存読み取り、他の場合は1つ）。

| --- | --- | --- | --- |
| 8 GB | 72 / 55 | 90 / 99 | 286 / 61 |
| 16 GB | 69 / 30 | 89 / 36 | 188 / 52 |
| 32 GB | 66 / 30 | 88 / 36 | 160 / 46 |

16GB以上では、ログは3つのデバイスすべてでページストアよりも2.2〜3.6倍高速です。8GBでは順序がデバイスに依存します。ページストアの時間は、ブロックあたり4,000回のランダム4KB書き込みがほとんどであるため、デバイスのランダム書き込み速度に依存します。

MacBook SSD上の9つのレイアウトすべて、ブロックあたりのミリ秒、サンプル24.0M、範囲の最悪のケースの端：

| DRAM | ページストア | ページログ | ログ、GC 1/2時 | ログ、GC 2/3時 | LSMパスキー、レコードキャッシュ | LSMパスキー、ブロックキャッシュ | LSMページキー | ページLSM | B+tree |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 4 GB | 114 | 41 | - | - | - | - | - | 83 | 354 |
| 8 GB | 103 | 35 | 50 | 48 | - | - | - | 73 | 322 |
| 16 GB | 96 | 31 | 26 | 22 | 18 | 29 | 25 | 71 | 333 |
| 32 GB | 134 | 28 | 26 | 22 | 21 | 22 | 25 | 68 | 318 |

各セルは、コミットI/Oが32個ずつ発行され、ブロックの実行読み取りミスがこのデバイスのシリアル読み取りレイテンシ（116マイクロ秒、ログの場合はミスあたり2回読み取り）で1つずつ発行された100ブロックの中央値です。16GBでは、レコードレイアウトとページログはすべてブロックあたり18〜31ミリ秒の範囲に収まり、このデバイスでは区別できません。インプレースページストアは3〜5倍長くかかり、B+treeは10〜18倍かかります。このデバイスはAPFS上のラップトップSSDであり、同じページストアの組み合わせは以前の実行ではブロックあたり188ミリ秒かかりましたが、ここでは96ミリ秒でした。したがって、1回の実行内の順序は使用可能ですが、実行間の数値は使用できません。

## 制限

-   2つの1週間ウィンドウで、両方とも2025年後半のものです。
-   16GBの予算は、[[glossary/full-node|フルノード]]が32GBをどのように分割するかについての仮定です。
-   8つのレイアウトのうち6つはモデルです。LSMとログのインデックスは1つのエンジンモデルを共有します。キャッシュミスしたルックアップごとに1回のディスク読み取り、フィルターは完全に常駐（レコードのLSMで9.3GB）、コンパクションによるキャッシュ無効化なし、2番目のレベル以下のレベルは外挿されます。B+treeは静的ページマップを使用し、フィル0.8、ファンアウト60、コミットごとに2回の同期を行います。ページログとページLSMはページストアのキャッシュプロファイルを再利用します。これは、ページ全体が書き込まれた場合、読み取りなしでキャッシュされたものとしてカウントします。ログまたはLSMブロックキャッシュはそうではありません。ページキーLSMも同様です。
-   書き込み増幅は、1つのウィンドウの1つのサブツリーに対して、書き込みのみでRocksDBでチェックされました。フラッシュとコンパクションによって書き込まれたエントリであり、バイト数ではありません（RocksDBはモデルの81Bに対してエントリあたり64Bを書き込みます。これは、プレフィックス圧縮とSnappyがモデル化されていないためです）。また、ミスあたりの読み取りI/Oもチェックされず、モデルの1ブロックのままです。ページLSMの8.6はモデルのみです。
-   コード読み取りはデータセットに含まれておらず、リプレイされません。
-   テーブルはカウントモデルから得られています。時間計測実行は、そのI/Oカウントを3つのデバイスでリプレイします。そのうち2つはインスタンスごとのIOPS制限がある小規模なクラウドインスタンスであり、1つはAPFS上のラップトップSSDです。一般的なノードのLinux上のNVMeはまだ測定されていません。
-   4つのサブツリー分割は、各サブツリーに共有キャッシュの代わりにキャッシュの4分の1を与えます。

## 次のステップ

-   実際のエンジンでの読み取りI/O：モデルは、フィルターが常駐している状態でキャッシュミスしたルックアップごとに1ブロックの読み取りを課します。書き込み増幅をチェックしたRocksDBの実行は、同じ方法で読み取りを測定できます。
-   そのエンジンでのキーエンコーディング実験：パスでキー付けされたレコードとページでキー付けされたレコードの比較。
-   4〜8GBの領域：ページログと、より小さなフィルターを持つレコードレイアウトの比較。
-   ログのインデックスに対する階層型コンパクション。これにより、各エントリが約10回ではなく、レベルあたり約1回書き換えられます。
-   Linux上の市販のNVMeドライブでの時間計測I/O。

リプレイツールとウィンドウごとの結果は、[GitHub - cocoyoon/eip8297-storage-research: Mainnet replay of EIP-8297 PBT on-disk layouts · GitHub](https://github.com/cocoyoon/eip8297-storage-research)（MIT）にあります。入力データは公開されているXatuデータセットです。上記のブロック範囲は、それをフェッチするのに十分です。1つのウィンドウは、リポジトリのツールで次のように再現されます。そのREADMEには、RocksDBチェックを含む完全なコマンドが記載されています。

```
tools/mainnet/fetch.sh DATA 24000000 50 reads
uv run tools/mainnet/export_diffs.py --data DATA --out DIFFS --reads
for q in 0 1 2 3; do
  pbt-char bench --mainnet-diffs DIFFS --mainnet-slot-counts tools/mainnet/data/slot_counts_2025-12-13.csv \
    --resident-levels 2 --blocks 1000 --warmup-blocks 49000 \
    --mainnet-sample-bits 2 --mainnet-sample-part $q --out results --label replay_p$q
done
uv run tools/mainnet/combine_parts.py --out results/replay_combined.md results/replay_p{0,1,2,3}.md
```

いずれかの部分に`--mainnet-record-stream STREAM`を追加すると、`pbt-char lsm-validate`（`--features rocksdb`でビルド）がRocksDBに供給するレコードストリームが書き込まれます。
