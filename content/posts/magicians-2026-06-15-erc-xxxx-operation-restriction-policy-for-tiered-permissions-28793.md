## **要約**

この提案は、スマートコントラクトにおける階層型操作制限ポリシーのための標準化されたインターフェースを定義します。既存の[[glossary/EIP|EIP（Ethereum 改善提案）]]エコシステムには根本的な非対称性があります。複数の標準がアイデンティティベースのパーミッション（「誰が行動できるか」）に対処しており、これには[[glossary/ERC-5982|ERC-5982]]（ロールベースのアクセス制御）、[[glossary/ERC-6366|ERC-6366]]（パーミッショントークン）、[[glossary/ERC-7820|ERC-7820]]（アクセス制御レジストリ）、[[glossary/ERC-8063|ERC-8063]]（グループメンバーシップトークン）が含まれます。また、検証インフラストラクチャ（「どのようにチェックするか」）に対処する標準として、[[glossary/ERC-7746|ERC-7746]]（コンポーザブルセキュリティミドルウェアフック）や[[glossary/ERC-7710|ERC-7710]]（スマートコントラクト委任）がありますが、**操作レベルの制限（「どのような制約が適用されるか」）に対処する標準は存在しません**。

この提案は、`IPermissionPolicy`インターフェース（`canExecute()`チェックパターンとティアごとの`TierConfig`構造体を含む）、ロールシステムを操作制限ティアにマッピングする[[glossary/IRoleTier|IRoleTier]]ブリッジインターフェース、プロトコル固有の拡張スロットを持つ固定の4層セマンティック基盤（Tier-0: オブザーバー/読み取り専用、Tier-1: 制限付き、Tier-2: 標準、Tier-3: 管理者）、および4つのコア制限タイプ（`RATE_LIMIT`：時間枠内の操作回数、`VALUE_CAP`：最大トランザクション値、`TIME_WINDOW`：有効な操作時間/曜日、`FUNCTION_WHITELIST`：ティアごとの許可された関数セレクター）を導入することで、この意味的なギャップを埋めます。このインターフェースは[[glossary/ERC-7746|ERC-7746]]ミドルウェアフックとクリーンに構成され、イーサリアムエコシステム全体で相互運用可能な制限ポリシーを可能にします。

> 注：この標準におけるロールと制限ティアのマッピングは、EIP-Contract Role Naming StandardおよびEIP-Contract Role Semantics Standardによって定義されたティア導出に依存しています。これら2つの標準は現在ドラフトステータスであり、まだEIP番号が割り当てられていません。参照は割り当てられ次第更新されます。

## **動機**

現在の[[glossary/EIP|EIP（Ethereum 改善提案）]]エコシステムには根本的な非対称性があります。標準はアイデンティティベースのパーミッション（「誰が行動できるか」）と検証インフラストラクチャ（「どのようにチェックするか」）をカバーしていますが、操作レベルの制限（「どのような制約が適用されるか」）は全く標準化されていません。

さらに重要なことに、オフチェーンの制限にはオンチェーンでの強制力がありません。攻撃者がオフチェーンのコントロールをバイパスすると、コントラクト自体は不正な操作を拒否できません。主要なセキュリティインシデント（2022-2025年、例：Ronin Bridge、Wormhole、Bybit）の根本原因の一つは、オンチェーンの操作レベルの制限の欠如でした。キーの侵害後、攻撃者は頻度、値、時間の制約なしに、単一のトランザクションで金庫全体を枯渇させました。

このギャップは次のように現れます。

-   **断片化された実装**: 各[[glossary/DeFi|DeFi]]プロトコルは、レート制限、値上限、時間枠、関数ホワイトリストを共有インターフェースなしに個別に実装しています。
    
-   **オフチェーン ≠ オンチェーンセキュリティ**: オンチェーンの制限がないため、攻撃対象領域が「オフチェーンコントロールの侵害」から「任意のキー = 無制限の操作」に拡大します。
    
-   **プロトコル間の相互運用性がない**: あるプロトコルで制限されたオペレーターは、別のプロトコルとは意味的な関係がありません。
    
-   **繰り返される監査**: 類似の制限ロジックが、共有セキュリティプリミティブなしにプロトコルごとに監査されています。
    

[[glossary/ERC-7746|ERC-7746]]はフックインフラストラクチャを提供し、「レート制限、使用状況追跡」を用途として挙げていますが、制限ポリシー自体は標準化していません。[[glossary/ERC-5982|ERC-5982]]はロールを介したメソッドレベルのパーミッションを定義しますが、これはブール値の機能チェックであり、制限ポリシーフレームワークではありません。

## **仕様**

このドキュメントにおけるキーワード「MUST」、「MUST NOT」、「REQUIRED」、「SHOULD」、「SHOULD NOT」、「RECOMMENDED」、「NOT RECOMMENDED」、「MAY」、「OPTIONAL」は、RFC 2119およびRFC 8174に記述されている通りに解釈されます。

### **依存関係**

この標準は、EIP-Contract Role Naming StandardおよびEIP-Contract Role Semantics Standardによって定義された以下の概念に依存します。

-   ロール命名構文 `role.{category}.{action}`
    
-   ロールハッシュ導出 `keccak256(roleName)`
    
-   ロールティア導出 (Tier-0 root / Tier-1 grantor / Tier-2 atomic/scope)
    
-   `IERCRoleSemantics` インターフェースの `getRoleTier(bytes32)` 関数
    

この標準の[[glossary/IRoleTier|IRoleTier]]インターフェースの実装は、EIP-Contract Role Semantics Standardのティア導出ルールに**SHOULD**準拠すべきです。

### **コアインターフェース**

```
interface IPermissionPolicy {
    /// @dev Fixed semantic tiers, with protocol-specific extension slots.
    enum Tier {
        TIER_0_OBSERVER,   // Read-only access; MUST NOT modify state
        TIER_1_RESTRICTED, // Low-frequency, small-value
        TIER_2_STANDARD,   // Moderate operations, restrictions configurable
        TIER_3_ADMIN       // Unrestricted operations; SHOULD require multisig
    }

    /// @dev Core restriction types.
    enum RestrictionType {
        NONE,               // No restriction (check passed)
        RATE_LIMIT,         // Operation count within time window
        VALUE_CAP,          // Maximum transaction value
        TIME_WINDOW,        // Valid operation hours/days
        FUNCTION_WHITELIST  // Allowed function selectors
    }

    /// @dev Rate limit parameters.
    struct RateLimitParams {
        uint256 maxOps;        // Max operations within window
        uint256 windowSeconds; // Window duration in seconds
    }

    /// @dev Value cap parameters.
    struct ValueCapParams {
        uint256 maxValue;      // Max value per operation
        address token;         // Token address; MUST NOT be address(0)
    }

    /// @dev Time window parameters.
    struct TimeWindowParams {
        uint256 startHour;    // Start hour (UTC, 0-23)
        uint256 endHour;      // End hour (UTC, 0-23)
        uint256 validDays;    // Valid days bitmask (bit 0=Sunday, bit 6=Saturday)
    }

    /// @dev Function whitelist parameters.
    struct FunctionWhitelistParams {
        bytes4[] allowedSelectors; // Allowed function selectors
    }

    /// @dev Per-tier restriction config. Each type has its own field and toggle.
    ///      More intuitive and gas-efficient than generic bytes params + dynamic array.
    struct TierConfig {
        RateLimitParams rateLimit;
        ValueCapParams valueCap;
        TimeWindowParams timeWindow;
        FunctionWhitelistParams funcWhitelist;
        bool rateLimitEnabled;
        bool valueCapEnabled;
        bool timeWindowEnabled;
        bool funcWhitelistEnabled;
    }

    /// @notice Check whether a caller can execute a specific operation.
    /// @dev For native ETH VALUE_CAP, this view function cannot access msg.value;
    ///      actual enforcement relies on beforeCall().
    function canExecute(
        address caller,
        address /* target */,      // Reserved for ERC-7746 ILayer compatibility
        bytes4 selector,
        bytes calldata /* data */  // Reserved for ERC-7746 ILayer compatibility
    ) external view returns (bool);

    /// @notice Get the complete restriction config for a tier.
    function getTierConfig(Tier tier) external view returns (TierConfig memory);

    /// @notice Configure restrictions for a tier.
    function setTierConfig(Tier tier, TierConfig calldata config) external;

    /// @dev Emitted when tier config is updated.
    event TierConfigUpdated(Tier indexed tier, TierConfig config);

    /// @dev Emitted when an operation is denied due to a restriction violation.
    event OperationDenied(
        address indexed caller,
        Tier tier,
        RestrictionType restrictionType,  // MUST NOT be NONE in denial events
        bytes4 selector
    );

    /// @dev Reverted when an operation is denied due to a restriction violation.
    error OperationDeniedError(Tier tier, RestrictionType restrictionType, bytes4 selector);

    /// @dev Invalid tier configuration provided.
    error InvalidTierConfig(string reason);
}
```

### **ティア解決インターフェース**

コントラクトは、外部のロールシステムに[[glossary/IRoleTier|IRoleTier]]を介して「この呼び出し元はどの制限ティアに属しているか」を問い合わせ、それによって「誰がどのティアに属しているか」と「ティアごとにどのような制限が適用されるか」を分離します。

```
interface IRoleTier {
    /// @notice Resolve the operation restriction tier for an account.
    /// @dev Implementations MAY delegate to IERCRoleSemantics.getRoleTier(bytes32)
    ///      or use protocol-specific logic.
    function getRoleTier(address account) external view returns (IPermissionPolicy.Tier);
}
```

実装は、呼び出し元のティアを決定するために、制限を評価する前に`IRoleTier.getRoleTier()`を**MUST**呼び出す必要があります。ティアの割り当て（付与、取り消し）はロールシステムの責任であり、パーミッションポリシーコントラクトの責任では**ありません**。

実装は、[[glossary/ERC-165|ERC-165]]の`supportsInterface()`を介してインターフェースを宣言**SHOULD**すべきです。インターフェースID：

-   `IPermissionPolicy`: `0x1dda14b5` (構造体レイアウトが変更された場合は**MUST**再計算されます)
    
-   [[glossary/ILayer|ILayer]]: `0x092f683e`
    
-   [[glossary/IRoleTier|IRoleTier]]: `0x21e584a2`
    

ロールを持たないアカウントの場合、`IRoleTier.getRoleTier()`は`TIER_0_OBSERVER`（デフォルトの読み取り専用アクセス）を**MUST**返すべきです。

### **ロール命名から制限ティアへのマッピング**

EIP-Contract Role Naming StandardおよびEIP-Contract Role Semantics Standardと統合する場合、実装はロール認証ティアを操作制限ティアに次のようにマッピング**SHOULD**すべきです。

| ロール命名ティア | ロールタイプ | ロール例 | 制限ティア | 直感 |
| :---------- | :------- | :----------- | :--------- | :------- |
| ロールなし | — | 未認証アカウント | Tier-0 (オブザーバー) | アイデンティティなし → 読み取り専用 |
| 2 (アトミック) | アトミック | `role.token.mint` | Tier-1 (制限付き) | オペレーター → 制限付き |
| 2 (スコープ) | スコープ | スコープ付き権限ロール (予約済み) | Tier-1 (制限付き) | スコープ付き権限 → 制限付き |
| 1 (グラントール) | グラントール | `role.token.grant` | Tier-2 (標準) | マネージャー → 通常操作 |
| 0 (ルート) | ルート | `role.admin.root` | Tier-3 (管理者) | ボス → 無制限 |

**マッピングの方向**: ロールティアは「どの程度の権限があるか」（Tier-0 = 最も権限が高い）を表現するのに対し、制限ティアは「どの程度の自由があるか」（Tier-0 = 最も自由が少ない）を表現します。マッピングは逆であり、権限が高いほど制限が少なくなります。

**複数ロールの場合、最も制限の少ないものが適用される**: `role.admin.root`と`role.token.mint`の両方を持つアカウントはTier-3で操作します（最も制限の少ないティアが優先されます）。

**デフォルトティア**: EIP-Contract Role Naming Standardで定義されたロールを持たないアカウントは、Tier-0（オブザーバー）に**MUST**マッピングされます。

プロトコルはカスタムマッピングロジックを定義**MAY**してもよいです。EIP-Contract Role Naming Standardと統合する場合、上記のマップをデフォルトとして**SHOULD**使用すべきです。

-   **断片化された実装（Fragmented implementations）**: 各[[glossary/DeFi|DeFi]]プロトコルは、レート制限（rate limits）、値上限（value caps）、時間枠（time windows）、関数ホワイトリスト（function whitelists）を共有インターフェースなしに個別に実装しています。

-   **繰り返される監査（Repeated audits）**: 類似の制限ロジックが、共有セキュリティプリミティブ（shared security primitives）なしにプロトコルごとに監査されています。

```
interface IPermissionPolicy {
    /// @dev Fixed semantic tiers, with protocol-specific extension slots.
    enum Tier {
        TIER_0_OBSERVER,   // Read-only access; MUST NOT modify state
        TIER_1_RESTRICTED, // Low-frequency, small-value
        TIER_2_STANDARD,   // Moderate operations, restrictions configurable
        TIER_3_ADMIN       // Unrestricted operations; SHOULD require multisig
    }

    /// @dev Core restriction types.
    enum RestrictionType {
        NONE,               // No restriction (check passed)
        RATE_LIMIT,         // Operation count within time window
        VALUE_CAP,          // Maximum transaction value
        TIME_WINDOW,        // Valid operation hours/days
        FUNCTION_WHITELIST  // Allowed function selectors
    }

    /// @dev Rate limit parameters.
    struct RateLimitParams {
        uint256 maxOps;        // Max operations within window
        uint256 windowSeconds; // Window duration in seconds
    }

    /// @dev Value cap parameters.
    struct ValueCapParams {
        uint256 maxValue;      // Max value per operation
        address token;         // Token address; MUST NOT be address(0)
    }

    /// @dev Time window parameters.
    struct TimeWindowParams {
        uint256 startHour;    // Start hour (UTC, 0-23)
        uint256 endHour;      // End hour (UTC, 0-23)
        uint256 validDays;    // Valid days bitmask (bit 0=Sunday, bit 6=Saturday)
    }

    /// @dev Function whitelist parameters.
    struct FunctionWhitelistParams {
        bytes4[] allowedSelectors; // Allowed function selectors
    }

    /// @dev Per-tier restriction config. Each type has its own field and toggle.
    ///      More intuitive and gas-efficient than generic bytes params + dynamic array.
    struct TierConfig {
        RateLimitParams rateLimit;
        ValueCapParams valueCap;
        TimeWindowParams timeWindow;
        FunctionWhitelistParams funcWhitelist;
        bool rateLimitEnabled;
        bool valueCapEnabled;
        bool timeWindowEnabled;
        bool funcWhitelistEnabled;
    }

    /// @notice Check whether a caller can execute a specific operation.
    /// @dev For native ETH VALUE_CAP, this view function cannot access msg.value;
    ///      actual enforcement relies on beforeCall().
    function canExecute(
        address caller,
        address /* target */,      // Reserved for ERC-7746 ILayer compatibility
        bytes4 selector,
        bytes calldata /* data */  // Reserved for ERC-7746 ILayer compatibility
    ) external view returns (bool);

    /// @notice Get the complete restriction config for a tier.
    function getTierConfig(Tier tier) external view returns (TierConfig memory);

    /// @notice Configure restrictions for a tier.
    function setTierConfig(Tier tier, TierConfig calldata config) external;

    /// @dev Emitted when tier config is updated.
    event TierConfigUpdated(Tier indexed tier, TierConfig config);

    /// @dev Emitted when an operation is denied due to a restriction violation.
    event OperationDenied(
        address indexed caller,
        Tier tier,
        RestrictionType restrictionType,  // MUST NOT be NONE in denial events
        bytes4 selector
    );

    /// @dev Reverted when an operation is denied due to a restriction violation.
    error OperationDeniedError(Tier tier, RestrictionType restrictionType, bytes4 selector);

    /// @dev Invalid tier configuration provided.
    error InvalidTierConfig(string reason);
}
```

### **ティア解決インターフェース**

コントラクトは、外部のロールシステムに[[glossary/IRoleTier|IRoleTier]]を介して「この呼び出し元はどの制限ティアに属しているか」を問い合わせ、それによって「誰がどのティアに属しているか」と「ティアごとにどのような制限が適用されるか」を分離します。

```
interface IRoleTier {
    /// @notice Resolve the operation restriction tier for an account.
    /// @dev Implementations MAY delegate to IERCRoleSemantics.getRoleTier(bytes32)
    ///      or use protocol-specific logic.
    function getRoleTier(address account) external view returns (IPermissionPolicy.Tier);
}
```

実装は、呼び出し元のティアを決定するために、制限を評価する前に`IRoleTier.getRoleTier()`を**MUST**呼び出す必要があります。ティアの割り当て（付与、取り消し）はロールシステムの責任であり、パーミッションポリシーコントラクトの責任では**ありません**。

実装は、[[glossary/ERC-165|ERC-165]]の`supportsInterface()`を介してインターフェースを宣言**SHOULD**すべきです。インターフェースID：

-   `IPermissionPolicy`: `0x1dda14b5` (構造体レイアウトが変更された場合は**MUST**再計算されます)
    
-   [[glossary/ILayer|ILayer]]: `0x092f683e`
    
-   [[glossary/IRoleTier|IRoleTier]]: `0x21e584a2`
    

ロールを持たないアカウントの場合、`IRoleTier.getRoleTier()`は`TIER_0_OBSERVER`（デフォルトの読み取り専用アクセス）を**MUST**返すべきです。

### **ロール命名から制限ティアへのマッピング**

EIP-Contract Role Naming StandardおよびEIP-Contract Role Semantics Standardと統合する場合、実装はロール認証ティアを操作制限ティアに次のようにマッピング**SHOULD**すべきです。

| ロール命名ティア | ロールタイプ | ロール例 | 制限ティア | 直感 |
| :---------- | :------- | :----------- | :--------- | :------- |
| ロールなし | — | 未認証アカウント | Tier-0 (オブザーバー) | アイデンティティなし → 読み取り専用 |
| 2 (アトミック) | アトミック | `role.token.mint` | Tier-1 (制限付き) | オペレーター → 制限付き |
| 2 (スコープ) | スコープ | スコープ付き権限ロール (予約済み) | Tier-1 (制限付き) | スコープ付き権限 → 制限付き |
| 1 (グラントール) | グラントール | `role.token.grant` | Tier-2 (標準) | マネージャー → 通常操作 |
| 0 (ルート) | ルート | `role.admin.root` | Tier-3 (管理者) | ボス → 無制限 |

**マッピングの方向**: ロールティアは「どの程度の権限があるか」（Tier-0 = 最も権限が高い）を表現するのに対し、制限ティアは「どの程度の自由があるか」（Tier-0 = 最も自由が少ない）を表現します。マッピングは逆であり、権限が高いほど制限が少なくなります。

**複数ロールの場合、最も制限の少ないものが適用される**: `role.admin.root`と`role.token.mint`の両方を持つアカウントはTier-3で操作します（最も制限の少ないティアが優先されます）。

**デフォルトティア**: EIP-Contract Role Naming Standardで定義されたロールを持たないアカウントは、Tier-0（オブザーバー）に**MUST**マッピングされます。

プロトコルはカスタムマッピングロジックを定義**MAY**してもよいです。EIP-Contract Role Naming Standardと統合する場合、上記のマップをデフォルトとして**SHOULD**使用すべきです。
