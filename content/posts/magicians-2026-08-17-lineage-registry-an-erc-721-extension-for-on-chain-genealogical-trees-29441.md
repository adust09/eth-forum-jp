> **TL;DR** — 私は**分散型系図ツリーレジストリ**の標準を提案しています。これは主に血統を検証するための系図追跡に使用されます。提案されている標準はこのコントラクトです: [`LineageRegistry.sol`](https://github.com/henriquelalvim/genealogicalRegistryBlockchain/blob/v0.1.0/contracts/LineageRegistry.sol)。
>
> [[glossary/ERC-721|ERC-721]]トークンは*性別付きDAG (有向非巡回グラフ)*を形成します。各トークンは性別と生年月日を持ち、創始者であるか、または正確に1人の父と1人の母を持ちます。6つのルールは必須であり、4つの拡張は[[glossary/ERC-165|ERC-165]]の背後でオプトインです。そして**非巡回性はサイクルチェックを全く必要としません** — これは単調増加するトークンIDから自然に導かれます。
>
> 最後の未解決の質問が、私が実際にフィードバックを求めている点です。

## 実際に解決しようとしている問題

血統動物にとって、血統は価値の大部分を占めます。同じ品質の動物でも、文書化されているか否かによる価値の差は誤差の範囲ではなく、しばしば価格の大部分を占めます。

その記録は**血統登録簿 (studbook)** に存在します。これは品種協会によって運営されるプライベートなデータベースです。購入者が受け取るのはPDFであり、それを検証することはできません。購入者は協会を信頼し、ひいてはこれまで入力作業を行ったすべての事務員を信頼していることになります。

これにより、業界の誰もが認識する3つの問題が発生します。

-   **主張を検証する**ことはできず、受け取るだけです。
-   **協会間で同じ動物について意見が食い違う**ことがあり、それらを調整するメカニズムがありません — 同じ馬が2つの名前、2つの血統で2回存在します。
-   **協会が破綻すると、血統も共に失われます。** 登録簿は倒産、戦争、火災、そして単純な怠慢によって失われてきました。動物は記録よりも長生きします。

## [[glossary/ERC-721|ERC-721]]単独では解決できない理由

今日でもトークンのメタデータに`"sire": 42`と記述することは可能です。しかし、メタデータは*主張*であり、何もそれをチェックしません。具体的には、以下のことを防ぐことはできません。

-   親が子孫の**後に**生まれたと記録されること。
-   **サイクル** — ある動物が推移的に自身の祖先となること。
-   あなたのチャンピオン種牡馬を、あなたに尋ねることなく、私の仔馬の父として命名すること。
-   **片方の**親だけが記録され、もう片方が静かに欠落していること。これは、全く血統が不明な動物と区別できません。

これらはそれぞれ、実際の血統登録簿で起こる現実の事柄です。

したがって、目標は血統をオンチェーンに置くことではありません — それは今日誰でもできます。目標は、プライベートな血統登録簿を**分散型血統登録簿**に置き換えることです。これは、構造ルールが書き込み時に、コントラクトによって、すべての登録に対して強制される有向非巡回グラフです。どの協会もそれを所有せず、どの事務員もそれを書き換えることはできません。そして、読み手はそれが一貫していることを信頼する必要はありません — それ以外のものであり得ないからです。

## トークンの外観

**性別付き有向非巡回グラフを形成する[[glossary/ERC-721|ERC-721]]トークン:** すべてのトークンは自身の性別と生年月日を持ち、*創始者*であるか、または正確に1人の**父**（雄トークン）と1人の**母**（雌トークン）から派生します。

```solidity
struct Node {
    uint256 sireId;         // the father — a male token, or 0
    uint256 damId;          // the mother — a female token, or 0
    uint64  birthTimestamp; // ─┐ packed together into one storage slot
    bool    isMale;         // ─┘
}
```

4つの事実、3つのストレージスロット、そしてトークンID `0`は決してミントされないため、「記録された親なし」の番兵として機能します。

## スコープ

この標準は`ILineageRegistry`と、それを強制する抽象コントラクト`LineageRegistry.sol`です。これにはノード、以下の6つのルール、および同意が含まれます。これは[[glossary/ERC-721|ERC-721]]を継承し、それ以外は何も継承しません — `AccessControl`さえもです。

リポジトリには、品種、動物名、血統登録簿参照、死亡記録を含む具体的な`PedigreeRegistry`も含まれています。これは提案の**一部ではありません**。これはドメイン層の作業例であり、コアがデプロイ可能であることを証明し、ガス数値の測定対象を提供するために存在します。

語彙について: `sireId`と`damId`は単に`parentMale`と`parentFemale`であり、私は意図的に動物の言葉を選びました。血統動物は私が実際に理解している用途であり、これが最も適切であると確信しているものです。植物のために設計したわけではありません — その分野に十分に精通していないため、そこで機能すると主張することはできません。また、人間の血統のために設計したわけでもありません。データモデルは適合しますが、人間の血統をトークン化することは、トークン標準が静かに解決すべきではない倫理的な問題を提起します。

構造的には、このモデルは一般的です — 2人の異なる性別の親を持つ個人のあらゆる系図は変更なしに適合し、公式にどの系図に適用すべきか喜んで聞きたいと思います。しかし、私が提案しているスコープは動物です。

## 非巡回性は無料

**コントラクトのどこにもサイクルチェックはなく、グラフは依然として証明可能に非巡回です。**

これは、レジストリが独立した理由で望む2つのルールから自然に導かれます。

1.  子孫がミントされるとき、両親は**すでに存在している**こと。
2.  トークンIDは**単調増加する**こと。

したがって、親のIDは常に子孫のIDより*低い*です。親のエッジをたどるとトークンIDは厳密に減少するため、サイクルは存在せず、上方向への探索は常に終了します — それを強制するための比較が1つも記述されることなく。

```
  #1 ♂   #2 ♀        #3 ♂   #4 ♀          創始者 — 親の記録なし
    └──┬──┘            └──┬──┘
       │                  │
     #5 ♀              #6 ♂                父 #1, 母 #2   /   父 #3, 母 #4
       └────────┬─────────┘
                │
              #7 ♂                         父 #6, 母 #5

  すべてのエッジは、より高いIDからより低いIDへ向かう — 構造上、常に
```

私が構築中のデモもあります。何が達成されようとしているかを視覚化できます（現在はポルトガル語ですが、直感的です）。

![血統登録](https://ethereum-magicians.org/uploads/default/optimized/3X/a/e/ae60e4bdc1851ea6722e766a3803b7a019897db0_2_690x434.png "血統登録")

これは年代順のルールではありません。年代順は別途強制され、別のものを保証します: 血統が**物理世界で起こり得た**ことを記述しているという約束です。自分の父より先に生まれた仔馬は、不正な血統登録簿データで最も一般的な形式であるため、そのルールもオプションではありません。

## 何が必須で、なぜこれらなのか

各ルールが通過しなければならなかったテスト: *もしこれがオプションだったら、グラフを信頼できるか？*

| ルール | それがない場合 |
| --- | --- |
| 性別付き親子関係 — 父は雄、母は雌 | 血統は血統ではない |
| 全か無かの親子関係 — 両親がいるか、どちらもいないか | 「親なし」と「片親」が区別不能になる |
| 親は事前に存在し、IDは単調増加する | 非巡回性が無料ではなくなり、無制限のチェックが必要になる |
| 一度書き込み — 記録された親子関係は上書きされない | 履歴が編集可能になり、記録は無価値になる |
| 年代順 — 親は子孫より厳密に先に生まれる | 仔馬が自分の父より先に生まれることが可能になる |
| 同意 — トークンを親として命名するには所有者の許可が必要 | 誰でも自分の動物をあなたのチャンピオンに紐付けられる |

同意は人々が予想しないものです。つまり、ここでの血統は**相互に合意された記録であり、一方的な主張ではありません**。許可はトークンごと（「この種牡馬はそのアドレスによって親として命名されてもよい」）または包括的（「そのアドレスは私が所有する任意のトークンを命名してもよい」）に付与されます。包括的な許可はトークンではなく*所有者*に従うため、後から購入した動物もカバーし、売却された瞬間に失効します。

## 何がオプションで、そのコストは何か

4つの拡張機能があり、それぞれに独自の[[glossary/ERC-165|ERC-165]] IDが付与されています。これは`ERC721Metadata`や`ERC721Enumerable`が[[glossary/ERC-721|ERC-721]]と関連する方法と同じです。デプロイメントは必要なレジストリを正確に構成し、コンシューマーは実行時に何が利用可能かを発見します。

| 拡張機能 | 追加されるもの | 必要条件 |
| --- | --- | --- |
| Offspring | 逆引きインデックス: `getOffspring`, `offspringCount` | — |
| LateParentage | `attachParentage` — 創始者を一度だけ後から昇格させる | — |
| Mergeable | 重複を生存者に統合し、転送用の墓標を残す | Offspring |
| Burnable | リーフノードを破壊する。子孫を持つものは拒否される | Offspring |

これらの分割の1つは数値で示す価値があります。なぜなら、それがこの標準がこのような形になった理由だからです。

| スタック | 2つの親を持つ登録 |
| --- | --- |
| コアのみ | 138,516 ガス |
| コア + Offspring | 227,269 ガス |
| 完全な参照構成 | 266,415 ガス |

`Offspring`は**88,753ガス**かかります — 親子関係のある登録ごとに2つのコールド`SSTORE`があり、コアが実行するすべての処理を合わせたよりもはるかに多いです。そして、同じ情報は`ParentageLinked`イベントから*オフチェーンで完全に再構築可能*です。

したがって、「この種牡馬の仔馬は誰か？」という質問に**オンチェーンで**答える必要がある場合にのみインストールしてください。コアのみのレジストリは、登録あたりのコストが48%安く、サイズも59%小さくなります — これが、私が個人的に常に望むものを含め、より多くの機能を必須コアに押し込むのをやめた理由です。

## 既知の制限事項

-   `attachParentage`とマージプリミティブにおける**2つの無制限な祖先探索**。深い血統の場合、どちらもガスを使い果たし、最も重要な古く、よく文書化された血統において、これらの操作が*永久に不可能になる*可能性があります。これは設計の最も弱い部分です。未解決の質問6を参照してください。
-   **`isMale`は存在しないトークンに対して`false`を返します**。そのため、「雌」と「不在」は、別途存在チェックを行わないと区別できません。未解決の質問1を参照してください。
-   **カスタムエラーではなくリバート文字列**を使用しています。これは標準のドラフト段階での可読性を保つためです。
-   **凍結されたインターフェースはありません。** 署名が変更されると、すべての[[glossary/ERC-165|ERC-165]] IDが移動します。
-   **テストスイートは構造化された骨格です。** コア、すべての拡張機能、および参照構成は、デプロイされたインスタンスに対してエンドツーエンドで実行されていますが、公開されているスイートはまだ十分な証明ではありません。今日、これを実際の資金のために使用することはありません。

## 未解決の質問 — これらが私が実際に助けを求めているものです

**1. `bool isMale`か、それとも`enum Sex { Unknown, Male, Female }`か？** 列挙型は上記の「雌 vs. 不在」の曖昧さを解消し、現在除外されている生殖モデルの余地を残します。これはコアへの[[glossary/ABI|ABI]]変更であるため、凍結される前に解決する必要があります。

**2. 単調増加するトークンIDには、私が気づいていないコストがあるか？** これらは非巡回性を無料にするものであり、私はこれに愛着を持っています。しかし、IDが登録順序を漏洩させ、IDを選択できない（既存の血統登録簿番号からトークンIDを導出できない）こと、そして紙の血統登録簿をインポートする際にすべての子孫の前にすべての祖先を挿入する必要があることを意味します。私が見ていないもっと悪い結果があるでしょうか？

**3. 標準はファントムプレースホルダーについて知るべきか？** 片方の親だけが文書化されている場合、全か無かのルールにより、もう片方の親を発明する必要があります。つまり、ペアを完成させるためだけに、空の名前のない、欠落した性別の創始者を登録します。そのノードは実際のトークンであり（譲渡可能で、親として使用可能）、決して存在しなかった動物を表しています。それが架空のものであることを示すものは何もなく、グラフを読み取るコンシューマーはプレースホルダーと真の未文書化の創始者を区別できません。`isPlaceholder`フラグがあればそれを修正し、コアを拡張しますが、それを除外すると慣習がドメイン層に残り、コンシューマーは推測することになります。どちらが正しいかわかりません。

**4. 既存の創始者に親をアタッチすることは標準の一部であるべきか？** 今日ではオプションであり、ID順序付けの議論を破る唯一の操作です — アタッチされた親は子よりも*高い*IDを持つ可能性があり、無料のサイクルチェックではなく実際のサイクルチェックが必要です。この必要性は現実的です。動物を登録し、その血統が数年後に明らかになることがあります。デフォルトで許可されるべきか、オプションのままにするべきか、それとも除外するべきか？

**5. 重複のマージはそもそも標準に含まれるべきか？** 同じ動物が2回登録されることはエッジケースではありません — 2人のブリーダーまたは2つのレジストリが同じ動物を記述する場合にまさに起こることであり、私が冒頭で述べた3つの問題の1つです。しかし、1つのトークンを別のトークンに統合することは、親子関係を調整し、サイクルを拒否するために祖先を探索し、古い参照がまだ解決されるように転送用の墓標を残すことを意味します。これはリポジトリ内で最も複雑で費用のかかるものであり、私がそれをオプションにした理由です。これは標準が負うには重すぎるか — それとも重複を調整できない系図標準は単に未完成なのか？

**6. 2つの無制限な祖先探索についてどうすればよいか？** 明らかな解決策は`MAX_ANCESTOR_DEPTH`定数ですが、**私はそれに反対です。** 系図記録は何世代にもわたって成長し続けることを意図しており — それがデータベースではなくブロックチェーンに置く理由全体です — 深度制限は、最も価値のある古く、深く、よく文書化された血統において、まさに標準を破ることになります。アタッチの場合には実際の解決策があります。提案された親のIDがすでに子のIDより低い場合、ID順序付けのみで安全性が証明され、探索をスキップできます。これは一般的なパスをカバーします。マージについては良い解決策がありません。オフチェーン証明？文書化され、受け入れられた制限？私が考えていない何か？

**7. クロスレジストリ連携 — オンチェーンが正しい答えなのか？** 親は裸の`uint256`であり、*この*コントラクトに存在しなければならないため、他のレジストリのトークンは単に未承認であるだけでなく、表現できません。3つの選択肢があります: **ミラーノード**（外部の動物を、起源ポインターを持つ通常のローカルトークンとしてインポートする — コアの変更なし、ローカルの非巡回性は維持されるが、`getOffspring`が断片化される）。**拡張された参照** `(chainId, registry, tokenId)`（正直な方法であり、異なる[[glossary/ERC|ERC]] — ノードが3倍になり、すべての読み取り署名が変更され、非巡回性は社会的保証に劣化する）。または**オフチェーンアテステーション**をインデクサーが消費する（データモデルの変更なしのフェデレーションであり、他の2つを凌駕する可能性が高い）。私は推測するよりもこれを除外しました。コアは今、これのために何かを予約すべきでしょうか？

**8. 4つのオプション拡張を持つ1つの[[glossary/ERC|ERC]]か、それとも5つの[[glossary/ERC|ERC]]か？** [[glossary/ERC-721|ERC-721]]のメタデータと列挙可能の扱いにならって、1つとして記述されています。反論としては、[[glossary/ERC-1155|ERC-1155]]と`ERC-1155 Supply`の分割があります。これは、[[glossary/ERC|ERC]]間の依存関係（`Mergeable`と`Burnable`はどちらも`Offspring`を必要とする）を犠牲にして、コアを小さく保ちます。

* * *

フレームワークが間違っていると言われても構いません。私が最も確信が持てないのは質問7であり、最も確信しているのは、血統登録簿の問題は現実のものであり、ブロックチェーンがそれをより良く解決できるということです。なぜなら、登録簿はオンチェーンに永遠に存在し続けるからです。
