ビットコインのジェネシスブロックから17年が経った今でも、暗号資産の送金は開発者向けのタスクのように感じられます。受信者にウォレットアドレスを尋ね、42文字の16進数文字列をコピーし、正しいネットワークにいることを確認し、手数料を支払うためだけにガス代トークン (gas token) を取得する必要があります。これらのステップのいずれかを間違えると、資金は永遠に失われます。一方、誰かにメッセージを送るのは3秒で済みます。メールアドレスや電話番号を入力するだけです。

このUXギャップは些細な不便さではありません。暗号資産のマスアダプション（普及）にとって最大の障壁となっています。明白な解決策は、これらの識別子をブロックチェーンアドレスに直接マッピングすることです。しかし、そうしようとする素朴な試みはすべて、ユーザーがますます重視するようになった唯一のもの、つまりプライバシーを犠牲にしてしまいます。あなたのメールアドレスを知っている人は誰でもあなたのアドレスを特定でき、そこからオンチェーン上のあなたの完全な金融履歴を再構築できてしまいます。

この記事では、プライバシーを犠牲にすることなくこのギャップを埋めるプロトコルであるHFIPayについて説明します。

## 問題点

暗号資産を送金するには、依然として送信者がウォレットアドレスを知っている必要があります。UX改善があったとしても、フローは「アドレスを尋ねる → 16進数文字列をコピー → 正しいネットワークを選択 → ガス代トークンを取得 → 送金」となります。

メールアドレス、電話番号、ソーシャルハンドルといった人間が判読しやすい識別子 (human-friendly identifiers) は、すでに人々がオンラインでお互いを識別する方法です。自然な目標は次のとおりです。
**`alice@example.com` にメッセージを送るのと同じ方法で暗号資産を送る。**

素朴なアプローチでは、識別子を決定論的にアドレスにマッピングします。例えば、`keccak256(identifier) → address` のようにです。これはシンプルですが、致命的なプライバシーの欠陥を導入します。アリスのメールアドレスを知っている人は誰でも、彼女のオンチェーンアドレスを特定し、サポートされているすべてのチェーン上で、彼女の完全なトランザクション履歴、トークン残高、取引相手との関係を検査できてしまいます。

## 解決策：HFIPayとその機能

HFIPayはプロトコルであり、アプリケーションではありません。あらゆるウォレットや支払いアプリに統合できます。プロトコルレベルで以下の特性を可能にします。

-   **受信者のウォレット設定は不要** — 受信者がまだ暗号資産アプリを一度も開いていなくても、資金を送金できます。
-   **列挙耐性 (Enumeration resistance)** — オンチェーンデータは、既知のメール、電話番号、ソーシャルハンドルのいずれに属するインテント (intents) があるかについて何も明らかにしません。
-   **事前請求時の非リンク性 (Pre-claim unlinkability)** — 同じ識別子への複数の支払いは、再利用可能なオンチェーンの受信者タグを残しません。
-   **非カストディアルな請求 (Non-custodial claim)** — リレー (relay) はルーティングを行いますが、資金をリダイレクトすることはできません。受信者のみがZKプルーフ（ゼロ知識証明）を介してリリースを承認できます。
-   **識別子に依存しない (Identifier-agnostic)** — メール、電話、Xハンドル、その他検証可能なあらゆる識別子で機能します。

HFIPayプロトコルを使用すると、誰でも次のことができます。

-   **誰にでも暗号資産を送金** — 受信者のウォレットアドレスを知る必要はなく、ウォレットを持っているかどうかさえ知る必要はありません。
-   **受信者は通知を受けて資金を請求** — まだウォレットを持っていない場合、請求時にその場で作成できます。
-   **初回使用後は自動請求** — 受信者が一度請求すると、それ以降の支払いは手動操作なしで自動的に請求できます。
-   **送信者は時間枠内でキャンセル可能** — 受信者が請求しない場合、送信者はタイムアウト前に資金を取り戻すことができます。
-   **未請求の送金は自動的に返金** — 有効期限期間 (expiry window) を過ぎると、資金は手動介入なしで送信者に返還されます。

## ENSとの比較

ENSはイーサリアムエコシステム (Ethereum ecosystem) で最も成熟したネーミングシステム (naming system) であり、不透明な16進数アドレスを人間が判読できる名前 (human-readable names) に置き換えるという実際の問題を解決しています。HFIPayは異なる問題を解決しています。以下に中立的な機能比較を示します。

| | ENS | HFIPay |
| --- | --- | --- |
| 識別子の種類 | .eth名（登録必須） | メール / 電話（既存、設定不要） |
| オンチェーンマッピング | 公開、列挙可能 | オンチェーンには保存されない |
| プライバシーモデル | アドレスは設計上公開 | チェーンはインテントごとのブラインド化された値のみを認識 |
| 受信者設定 | 受信前に必須 | オプション（遅延オンボーディング可能） |
| 識別子の列挙 | 誰でも任意の名前をクエリ可能 | チェーンの状態は識別子を公開しない |
| 信頼の前提 | ENSコントラクト（分散型） | リレー（以下の信頼モードを参照） |

ENSとHFIPayは競合するものではありません。HFIPayのリレーは、内部的に`.eth`名を他の識別子タイプの一つとして解決できます。違いは、オンチェーンにコミットされる情報と、それに続くプライバシー保証にあります。

## ERC-5564（ステルスアドレス）との比較

ERC-5564は、資金がオンチェーンの*どこに*着地するかを隠します。受信者のアドレスは一時的 (ephemeral) であり、その公開鍵にリンクできません。HFIPayは、より早い段階、つまり*人間が判読しやすい識別子 (human-friendly identifier) がオンチェーンの宛先 (on-chain destination) にどのようにマッピングされるか*を隠します。

```
送信者: alice@example.com を知っている
          ↓
  [リレー: プライベートな解決]        ← HFIPayのスコープ
          ↓
  オンチェーン: ブラインド化されたインテント
          ↓
  [受信者によるZK請求]
          ↓
  宛先アドレス (ステルスアドレスである可能性あり)   ← ERC-5564のスコープ
```

これら2つのメカニズムは補完的です。HFIPayは、支払いごとに新しいステルスアドレス (fresh stealth address) に資金をルーティングでき、識別子レベルとアドレスレベルのプライバシーを組み合わせることができます。

## HFIPayのメカニズム（非公式）

このプロトコルは3つの懸念事項を分離しています。

**1. プライベートルーティング（オフチェーン）**

送信者は`alice@example.com`を指定します。リレーはこれを登録された受信者レコードにプライベートに解決し、新しい`intentId`をサンプリングします。ワンタイム入金アドレス (one-time deposit address) を導出し、見積もられた資産と金額とともに、インテント固有の*ブラインド化されたバインディング* ρᵢ のみをコミットします。チェーンは識別子も再利用可能な受信者タグも認識しません。

**2. 送信者側の見積もり検証（オプション）**

*検証済み見積もり (verified-quote)* デプロイメントでは、リレーは資金提供前に、ρᵢを意図された受信者の隠されたバインディングキーコミットメントにリンクするオフチェーンの証明 (off-chain attestation) を返します。送信者は資金提供前にこれを検証できます。これにより、リレーが密かに資金を別の受信者にリダイレクトすることはできません。

**3. オンチェーン請求承認**

資金を請求するために、受信者はゼロ知識で（[ZK-ACE](https://arxiv.org/abs/2603.26970)を介して）資金提供されたインテントのブラインド化されたバインディングが、彼らの決定論的アイデンティティから派生したハンドルと一致することを証明し、彼らが選択した宛先へのリリースを承認します。リレーはルーティングとアベイラビリティ (availability) に関与しますが、インテントが資金提供された後に資金をリダイレクトすることはできません。

```
送信者                  リレー                   チェーン
  |                       |                       |
  |-- alice@emailに支払う --> |                       |
  |                       | (プライベートな検索)      |
  |<-- 見積もり (ρᵢ, τᵢ) --- |                       |
  |                       |                       |
  |-- インテントに資金提供 --------|---------------------> |
  |                       |                       |
                        受信者
                          |
                          |-- ZK請求証明 ---> |
                          |<-- 資金がリリースされた --- |
```

## プライバシー特性

この論文は2つの特性を形式化しています。

**列挙耐性 (Enumeration resistance)**: 既知のメールアドレス、電話番号、ソーシャルハンドルに属する資金提供されたインテント (funded intents) がどれであるかを、オブザーバーがオンチェーンデータから判断することはできません。オブザーバーが識別子を知っており、すべてのチェーンの状態を読み取れる場合でも同様です。

**事前請求時の非リンク性 (Pre-claim unlinkability)**: 請求が行われる前に、同じ識別子への複数の支払いが再利用可能な公開受信者タグを公開することはありません。各インテントは独立したブラインド化されたバインディングを使用します。請求が成功した後、宛先アドレスと資産額は（他のトランザクションと同様に）オンチェーンで可視になります。この論文は、請求後に何がリンク可能になるかを明示的に特徴付けています。

* * *

## 信頼モード

このプロトコルは2つのデプロイメントモードを定義しており、リレーに置かれる信頼の度合いを区別しています。

**ベースラインデプロイメント (Baseline deployment)**: リレーは、各インテントに正しい受信者をバインドすることを信頼されます。リレーとアプリケーションが信頼境界を共有する統合されたウォレット (integrated wallets) に適しています。

**検証済み見積もりデプロイメント (Verified-quote deployment)**: リレーは資金提供前に、送信者が検証可能な証明 (sender-verifiable attestation) を発行します。別のバインディング層 (binding layer) が識別子の所有権を独立して検証する（例：メールOTPやOIDCを介して）ため、リレーが異なる受信者を置き換えることは、送信者がそれを検出することなくはできません。バインディングは公開識別子レジストリなしで送信者が検証可能です。正式な扱いは論文のセクション2〜6に記載されています。
