> [!note] 原文
> [ERC-8418: Itemized Non-Fungible Token](https://ethereum-magicians.org/t/erc-8418-itemized-non-fungible-token/29693) — dojun (2026-09-15)

NFTコレクションは、その中に存在する特定のアイテムがいくつになるかをオンチェーンで証明できません。

コレクションは通常、多くのアイテム（アイテムの種類、チケットのクラス、アートシリーズなど）を保持しており、それぞれに意図されたエディションサイズがあります。発行者 (issuer) はこれらのサイズをメタデータ (metadata) で公開しますが、それらを強制するものはなく、他のコントラクトがそれらをチェックすることもできません。`tokenURI`は発行者が制御するサーバーを指しており、`"maxSupply": 100`と主張するJSONファイルは書き換えられる可能性があり、いずれにせよコントラクトはそれを取得したり解析したりすることはできません。

上限 (cap) は約束として存在します。私はそれを制約にしたいと考えています。

これは、ライブゲームのアイテムをオンチェーンに置くことから生まれました。ゲームが既に依存していた2つのプロパティは、[[glossary/ERC-721|ERC-721]]では表現されていないことが判明しました。それは、トークンが「何であるか」と、その種類のトークンが「いくつ存在しうるか」です。

### **識別子はトークンが何であるかを伝えない**

[[glossary/ERC-721|ERC-721]]では、トークンは番号と所有者です。オンチェーンでは、フレイムソードとブルーポーションを区別するものは何もありません。しかし、ゲームのルールのほとんどは、インスタンスではなくアイテムの観点から記述されます。例えば、レシピが何を消費するか、セットボーナスが何をカウントするか、交換が何を受け入れるか、といった具合です。

プロジェクトは、相互運用しない方法でこれを回避しています。一部は、プライベートなスキームで`tokenId`の上位ビットにアイテムをパックし、これにより範囲が制限され、すべての読み取り側がレイアウトを知る必要があります。他のプロジェクトは、`itemId`、`classId`、`category`、`series`など、彼らが選んだ名前でゲッターを公開するため、すべてのコンシューマーは特注のアダプターを作成します。私は、純粋に一つのコントラクトが別のコントラクトの分類を読み取れるようにするためだけに、`ownerOf`、`transferFrom`、および独自のゲッターという3つの関数インターフェースを宣言したデプロイ済みシステムを見たことがあります。

### **上限とアイテムは一つのメカニズム**

上限は何かに課されなければなりません。コントラクトはミント時 (mint time) に新しいトークンがどのアイテムに属するかを知る必要があり、その後、その関連付けを公開してカウントが監査できるようにする必要があります。アイテムを記録することが上限を強制可能にし、それを公開することが上限を検証可能にします。

アイテムを読み取ることは、それ自体で有用であることが判明します。マーケットプレイスはアイテムごとにグループ化でき、レンディングプロトコルはアイテムごとに価格を設定でき、インデックスはアイテムごとに重み付けできます。しかし、それを標準化する理由は、供給量の強制 (supply enforcement) にそれが必要だからです。

アイテムごとの上限が、ファンジブルトークンに対してコレクションの価格を設定するコントラクトに登録されている場合、その上限は価格設定式の項になります。発行者が静かに上限を引き上げることができる場合、それは全員の保有物の価格を再設定します。これが、インターフェース標準が表現でき、取引相手 (counterparty) が検証できるべき制約だと私は考えます。

### **既存の標準が不十分な点**

| 標準 | 制限 |
| --- | --- |
| [[glossary/ERC-721|ERC-721]] | アイテムがないため、分類するものがなく、アイテムごとの上限を強制することもできません。コレクション全体での供給量は、一つのアイテムの希少性については何も語りません。 |
| [[glossary/ERC-1155|ERC-1155]] | IDごとの供給量はありますが、IDを共有するトークンは区別できません。`balanceOf(owner, id)`は数量を返すため、2つのトークンを個別に承認したり転送したり、異なる来歴 (provenance) を持たせたりすることはできません。エディション番号も個別のIDも標準的な上限もありません。 |
| [[glossary/ERC-3525|ERC-3525]] | スロットと値を提供しますが、その主要な機能は金融商品の価値を分割・結合することです。供給量上限のセマンティクスはなく、ゲームアイテムやチケットを細分化することは無意味です。 |
| [[glossary/ERC-3440|ERC-3440]] | 既存の挙動に最も近いものです。限定版の実行を制限し、設定時に固定します。しかし、上限はコントラクトごとに1つの実行です。1000種類のアイテムを保持するコレクションには1000個のコントラクトが必要です。その主題は来歴のためのアーティスト署名であり、トークンがどの種類であるかを問い合わせる方法を公開していません。 |
| [[glossary/ERC-7496|ERC-7496]] | 任意の特性をオンチェーンに置くため、発行者は特性キーの下に種類を保存できます。特性は設計上変更可能 (mutable by design) であり、供給量会計 (supply accounting) を伴わないため、特性として保存された上限は発行者が書き換え可能な数値であり、メタデータが既に提供できない保証と同じです。 |
| [[glossary/ERC-8041|ERC-8041]] | 固定供給量とミント番号付けがありますが、コレクションスコープであり、[[glossary/ERC-8004|ERC-8004 (エージェントIDレジストリ)]]の[[glossary/NFT|NFT]]に特化しています。その設定はゲッターではなくイベントを通じて公開されるため、コントラクトはそれを読み取ることができません。 |

共通のギャップはレベルにあります。上限が存在する場合、それはコントラクト全体をカバーします。この提案はそれを一段階下に置きます。つまり、一つのコントラクトが多くのアイテムを保持し、それぞれが独自に強制される上限を持つというものです。

`}`

### **実装の選択ではなく、要件である2つの上限セマンティクス**

**上限は流通供給量ではなく累積ミント数を制限します。** もしバーンが容量を返却する場合、発行者は固定と宣伝された上限の下で無期限にミント、バーン、そして再度ミントを行うことができてしまいます。`itemTotalMinted`は`itemMaxSupply`に対してチェックされる値であり、`itemSupply`と`itemBurnedCount`はコンシューマーが両方を確認できるように個別に公開されます。

**上限は一度書き込み (write-once) です。** 作成後に引き上げられる上限は、それが置き換えるメタデータ以上の価値はありません。引き下げることも同様に安全ではありません。`itemTotalMinted`を下回るように設定されると、不変条件 (invariant) が遡及的に破綻します。

### **これが保証しないこと**

主張の範囲を明確にするため、はっきりと述べておきます。

これは、`itemId`ごとの累積ミント数を制限します。発行者が作成するアイテムの数には制限を設けません。あるアイテムの上限を使い果たした発行者は、実質的に同一の2番目のアイテムを作成し、その下でミントすることができます。アイテムをある種類のものの代理として扱うコンシューマーは、この標準ではなく発行者の分類体系に依存しています。検証可能になるのは、より狭く正確なことです。特定の`itemId`について、上限は作成時に固定され、これまでにミント数がそれを超えたことはありません。

### **未解決の質問**

以下の5点について、フィードバックを歓迎します。それぞれが、設計が別の方向に行くことも合理的にあり得た点です。

1.  **センチネルエンコーディング (Sentinel encoding)。** `maxSupply == 0`は「アイテムが作成されていない」ことを意味し、`type(uint256).max`は実質的に無制限を意味します。これにより、別途`created`フラグが不要になり、ミントガードは例外なしの単一比較で済みます。ゼロのオーバーロード (overloading zero) は許容できるでしょうか、それとも存在は独自のストレージフラグに置かれるべきでしょうか？
    
2.  **バーンされた`tokenId`の再利用。** この提案も[[glossary/ERC-721|ERC-721]]も、バーンされた`tokenId`を予約しないため、識別子は異なるアイテムの下で再度ミントされる可能性があります。上限は健全に保たれますが、`tokenId → itemId`をキャッシュしているコンシューマーは情報が古くなる可能性があります。私は、再利用を禁止するのではなく、注意点を文書化し、コンシューマーに`TokenMinted`を指示することを選択しました。なぜなら、禁止するとストレージコストがかかり、[[glossary/ERC-721|ERC-721]]自体もそうではないからです。代わりに、標準はバーンされた識別子を予約すべきでしょうか？
    
3.  **拡張としてのエディション。** コアの保証はエディション番号なしで完結するため、それらはオプションです。しかし、オプションのゲッターはコンシューマーが頼りにできないものです。ストレージの節約は断片化 (fragmentation) の価値があるでしょうか？
    
4.  **`tokenId`の割り当て。** 実装はシーケンシャルに割り当てることも、呼び出し元指定の`tokenId`を受け入れることもできます。呼び出し元による割り当ては、オフチェーンに既に存在する識別子空間とシステムを整合させることを可能にし、シーケンシャルはよりシンプルです。この標準はどちらの立場も取りません。取るべきでしょうか？
    
5.  **3つの供給量ゲッター。** `itemTotalMinted`は`itemSupply + itemBurnedCount`として導出可能です。この導出が実装者が上限チェックを誤る正確な場所であること、そして上限を正しく強制する実装は既に3つすべてを保存していることから、明示的に公開されています。この冗長性は正当化されるでしょうか、それとも標準は最小限のセットを公開すべきでしょうか？
