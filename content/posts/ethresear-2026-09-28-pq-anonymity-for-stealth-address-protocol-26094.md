# PQ SAP - PQ匿名性

> Hy、[@mmjahanara](https://ethresear.ch/u/mmjahanara)、[@Pierre](https://ethresear.ch/u/pierre)、[@winderica](https://ethresear.ch/u/winderica)、そしてKassandraの有益な議論とフィードバックに感謝します。

## TLDR;

この投稿は、ステルスアドレスプロトコル (Stealth Address Protocol) とその[[Post-Quantum|ポスト量子 (PQ)]]アップグレードに関する一連の投稿の2番目です。最初の投稿については、「[[Post-Quantum|ポスト量子]]ステルスアドレスプロトコル」を参照してください。

今後の投稿:

> スキーム6 [[PQ SAP - PQ Spending](https://ethresear.ch/t/pq-spending-for-stealth-address-protocol/26095)]

ステルスアドレスプロトコル (Stealth Address Protocol) は以下を可能にします。

- 受信者が公開の[[stealth-meta-address|ステルスメタアドレス]]を登録する
- 送信者が[[stealth-meta-address|ステルスメタアドレス]]と一時的な秘密（これもナンス）を使用して、受信者向けにワンタイムの[[stealth-address|ステルスアドレス]]を導出する
- 同じ[[stealth-meta-address|ステルスメタアドレス]]の異なるワンタイム[[stealth-address|ステルスアドレス]]（異なるナンスを意味する）への送信者から受信者への支払いは、リンク不可能である
- 送信者の匿名性は（*現在の*プロパティとして）保証されない

ステルスアドレスプロトコル (Stealth Address Protocol) としばしば組み合わされる（現在の）コンポーネントは以下の通りです。

- 受信者が公開鍵を登録できる[[stealth-meta-address|ステルスメタアドレス]]レジストリと、送信者がステルス支払いを発表できるアナウンスレジストリ
- 同じワンタイム[[stealth-address|ステルスアドレス]]が2回以上再利用されるのを防ぐための送信者側のナンスマネージャー
- ステルス支払いのためのステルス支払い発見またはスキャンサービス。この目的のために、通常、使用鍵と閲覧鍵を分離するデュアルキーステルスアドレスプロトコルに依存します。

```
 受信者 (Bob)                            送信者 (Alice)
 k_view, k_spend                         ナンスマネージャー: 新しいr、決して再利用しない
 M = (P_view, P_spend)                        |
      |                                       |
      | Mを登録                             | Mを検索
      v                                       v
 [メタアドレスレジストリ] ---------------------+
                                              |  s    = KA(r, P_view)
                                              |  P_st = P_spend + H(s)G
                                              |  R    = pub(r), vtag
                                              |
 [台帳]              value -> P_st  <-------+
 [アナウンスレジストリ]  (R, P_st, vtag) <---+
      |
      | Bob (または閲覧委任者) スキャン: s' = KA(k_view, R); vtag? P_spend+H(s')G == P_st?
      v
 Bobはk_spend + H(s')で使う

 リンク不可能: 同じM、異なるrからのP_st        [ 成立 ]
 送信者     : Aliceのアカウント資金 + アナウンス    [ 露出 ]
 鍵       : k_view = 検出 (委任可能), k_spend = 使用
```

[[ERC-6538|ERC6538Registry]]と[[ERC-5564|ERC5564Announcer]]を*永続的にオンチェーンで*監視している量子攻撃者は、Rと(K,V)、および[[stealth-address|ステルスアドレス]]Pへのすべてのステルス支払いを捕捉し、Rからr、Kからk、Vからvを回復できます。これにより、vを持つスキャナーとして、またkを持つ受信者として機能し、ステルス支払いへの完全な閲覧および使用アクセス権を持つことになります。

本稿では、SAPの2つのコアコンポーネント、すなわち(1/2)-ECDHとECDSAのアップグレードに焦点を当て、schemeId = 3, 5, 6のSAPを提案し、既存コンポーネントへの影響を解釈します。

ECDHをML-KEMに置き換える目的は、支払い発見と受信者のリンク不可能性を量子攻撃者から保護することです。ECDSAを置き換える目的は、支出承認を保護することです。スキーム2-5はECDSAを保持しているため、両方のプロパティを提供しません。

[[ERC-5564|ERC-5564]]のこの最初の拡張では、ECDHをPQ ML-KEMに置き換えることを試み、その結果、SAPのschemeId = 2-5となります。

> スキーム3には付随する[[repo for scheme 3](https://github.com/namnc/pq-stealth-scheme3-public/)]があり、これはPQ SAPアップグレードへの最良の第一歩です。

## ML-KEMの再確認

2024年8月13日に公開されたFIPS 203 for ML-KEM [[Module-Lattice-Based Key-Encapsulation Mechanism Standard](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf)]を採用します。

KEM（鍵カプセル化メカニズム）は、3つのアルゴリズムとパラメータセットのコレクションで構成されます。3つのアルゴリズムは以下の通りです。

- KeyGenと表記される確率的鍵生成アルゴリズム
- Encapsと表記される確率的「カプセル化」アルゴリズム
- Decapsと表記される決定論的「非カプセル化」アルゴリズム

```
Alice                          :                   Bob
                               :
+------------------+           :
|      KeyGen      |           :
+------------------+           :
     |       |                 :
     |       +-----------------:--------------------+
     v                         :                    v
+------------------+           :           +------------------+
| 非カプセル化鍵   |           :           | カプセル化鍵     |
+------------------+           :           +------------------+
     |                         :                    |
     v                         :                    v
+------------------+    +------:-----+     +------------------+
|      Decaps      |<---| 暗号文     |<----|      Encaps      |
+------------------+    +------:-----+     +------------------+
     |                         :                    |
     v                         :                    v
+------------------+           :           +------------------+
| Aliceの共有秘密の|           :           |  Bobの共有秘密の |
| コピー           |           :           | コピー           |
+------------------+           :           +------------------+
                               :
         r'                    :                    r
```

KEMは、上記のようにアリスとボブの2者間で共有秘密を確立するために使用されます。

- アリスはまずKeyGenを実行して、公開カプセル化鍵と秘密非カプセル化鍵を生成します。
- もう一方の当事者であるボブは、アリスのカプセル化鍵が与えられると、Encapsアルゴリズムを実行して、関連する暗号文とともに共有秘密鍵rを生成し、その暗号文をアリスに送信できます。
- アリスは、自身の非カプセル化鍵と暗号文を使用してDecapsアルゴリズムを実行し、共有秘密鍵のr' = rを取得できます。

ML-KEMには、ML-KEM-512、ML-KEM-768、ML-KEM-1024の3つのパラメータセットがあり、以下に示すように異なるパラメータサイズ（バイト）を持っています。

|  | カプセル化鍵 | 非カプセル化鍵 | 暗号文 | 共有秘密鍵 |
| --- | --- | --- | --- | --- |
| ML-KEM-512 | 800 | 1632 | 768 | 32 |
| ML-KEM-768 | 1184 | 2400 | 1088 | 32 |
| ML-KEM-1024 | 1568 | 3168 | 1568 | 32 |

まず、ML-KEMの構文を固定しましょう（\\lambdaはセキュリティパラメータ）。

- (dk,ek) \\leftarrow KeyGen(\\lambda)
- (r,c) \\leftarrow Encaps(ek)
- r' \\leftarrow Decaps(dk,c)

ML-KEMが成功すると、r' = rとなります。補足ですが、cが与えられた場合、攻撃者はそれが公開ekでカプセル化されたのか、公開ek'でカプセル化されたのかを判別できません。これが鍵の不可分性（IK-CCA、別名ANO-CCA）と呼ばれるもので、SAPにとって重要であることが判明しています。

### ML-KEMはANO-CCAを提供するか？

直感的かつ幸運なことに、提供します。量子ランダムオラクルモデル (QROM) における[[Post-Quantum|ポスト量子]]Kyberの匿名性に関する専門的な分析[[Post-Quantum Anonymity of Kyber](https://eprint.iacr.org/2022/1696)]があります。しかし、これはラウンド3のKyberを分析しているため、その結果を標準化されたML-KEMに適用するには、FIPS 203の変更点を考慮する必要があります。仕様では、FIPS 203変換は分析の図6の中間変換と一致しており、有効なカプセル化ではGの前半を返し、無効な暗号文では個別の暗号文依存の拒否鍵を使用します。[[ML-KEM and its ANO-CCA](https://ethresear.ch/_1GFxjmtTke10DYxB8jnjA)]における高レベルの説明を試みたものをご覧ください。

## 直接ML-KEM: SAP schemeId = 2

ECDHをML-KEMに直接置き換えます。

### 数学

Gを楕円曲線群の生成元とし、H(\\cdot)を共有秘密鍵からスカラーへの暗号学的ハッシュ関数とします。

- 受信者はランダムに秘密鍵kをサンプリングし、(dk,ek) \\leftarrow KeyGen(\\lambda)を実行し、K = kGである(K, ek)を公開レジストリに[[stealth-meta-address|ステルスメタアドレス]]として登録します。
- ワンタイム支払いの場合、送信者は（何らかの方法で）(K, ek)を取得し、(r,c) \\leftarrow Encaps(ek)を実行し、h = H(r)を計算し、P = K + hGを設定し、Pに資金を送り、その後cを公開します。
- 受信者、または受信者が非カプセル化鍵dkを委託したスキャンサービスは、まずr' = Decaps(dk,c)を非カプセル化し、h' = H(r')を再計算し、受信アドレスP' = K + h'Gを計算し、P =? P'をテストすることで、ステルス支払いを照合できます。
- しかし、kを持っている受信者のみ（dkしか持たないスキャンサービスでさえも）、公開鍵P = kG + hGに対するワンタイム秘密鍵k + hで資金にアクセスできます。

cは量子攻撃者に対して安全であるため（攻撃者はrを学習したり、ANO-CCAによりcをekにリンクしたりすることはできません）、[[stealth-meta-address|ステルスメタアドレス]] (K = kG, ek) へのリンクは、当該攻撃者に対して防止されます。

### 拡張された[[ERC-5564|ERC-5564]]

[[ERC-5564|ERC-5564]]は次のように拡張できます。

- 閲覧鍵ペア (v,V) をML-KEM鍵ペア (ek,dk) に置き換え、上記の数学に従ってアルゴリズムを変更します。`st:eth:0x<spendingPubKey><ek>`となります。
- NAIVEなビュータグh^\*を、hから抽出された最上位バイトとして1バイトのサイズで保持することを選択できます。これにより、r'を復元した後、h^\* =? H(r')\[0\]をチェックできます（schemeId-1と比較して異なる比率ではありますが、別のECスカラー乗算、EC加算、ハッシュの代わりに）。ただし、これには**匿名性リスク**が伴います（下記参照）。

[[ERC-5564|ERC5564Announcer]]は、[[stealth-address|ステルスアドレス]]に何かが送信されたことを通知するイベント (`Announcement(uint256 indexed schemeId, address indexed stealthAddress, address indexed caller, bytes mlKEMciphertext, bytes metadata)`) を発行するために、おそらく命名変更を除いて、変更する必要はありません。ただし、ML-KEM-768の場合、mlKEMciphertextは1088バイトです。

公開[[stealth-meta-address|ステルスメタアドレス]]の登録と取得を一元化する[[ERC-6538|ERC6538Registry]]は、現在の形式 (`mapping(address registrant => mapping(uint256 schemeId => bytes))`) を維持できます。ただし、ML-KEM-768の場合、カプセル化鍵のサイズは1184バイトであり、バイト部分は1151バイト増加します。

### 素朴なViewTag vs CRQC

思い出してください。

- P = K + hG = (k+h)G
- h^\* = h\[0\]

導出された公開鍵Pを知っているCRQCは、以下を行うことができます。

- p=\\log\_G(P)を回復します。
- レジストリ内の各候補公開使用鍵K\_iについて、k\_i=\\log\_G(K\_i)を回復します。
- h\_i=(p-k\_i)\\bmod nを計算し、h\_i\[0\]=h^\*であるかどうかをテストします。

正しい受信者は合格しますが、独立して生成された間違った候補は約1/256の確率で合格します。これにより、ML-KEMを破ることなく受信者リンクフィルタを提供できます。この攻撃にはPが必要であり、Pは通常のECDSAの支出から回復可能になります。この直接テストは、共有秘密から独立して調整とビュータグを導出することで防ぐことができます。

- h=H(DS1 \\parallel r)
- h^\*=H(DS2 \\parallel r)\[0\]

送信者はカプセル化によってrを知っており、受信者またはスキャナーは非カプセル化によってrを取得します。量子離散対数によってhを回復しても、独立して導出されたタグが直接明らかになることはありません。したがって、タグのプライバシーは、送信者がdkを知る必要なく、保護された共有秘密rに依存します。

この攻撃は、ML-KEMを介してPQ匿名性にアップグレードしようとするすべてのECDSAベースのSAP（本稿の2-5）に適用可能です。

### スキームID = 1への回顧

- 支出コスト（ガス代）は同じです。
- フォワードシークレットの問題は残っており、dkを保持している者は誰でもステルス支払いを[[stealth-meta-address|ステルスメタアドレス]]にリンクできます。
- ビュータグを保持しても、完全な非カプセル化が必要です。
- [[ERC-5564|ERC5564Announcer]]のアナウンスは約33倍に増加しますが、その一方で、これはDDoS攻撃を阻止するはずです。
- [[ERC-6538|ERC6538Registry]]の[[stealth-meta-address|ステルスメタアドレス]]は約18倍に増加します。
- ML-KEMのサイズはPIRとOMRを悪化させます。

### ハイブリッドコンバイナー: SAP schemeId = 3

(1/2)-ECDHをML-KEMに置き換えるスキーム2が[[Post-Quantum|ポスト量子]]匿名性にとって十分であることは理論的には理想的ですが、実際には、移行期間中（つまり、移行中およびCRQCが到着する前）にML-KEMのセキュリティをヘッジするために、ECDHとML-KEMの両方のハイブリッドコンバイナーに依存することが一般的です。したがって、実用的な使用のためにschemeId 3を提案します。スキーム3はスキーム1とスキーム2の組み合わせであり、具体的には次のとおりです。

- [[stealth-meta-address|ステルスメタアドレス]]は(K,V,ek)です。
- 送信者は受信者と2つの秘密を共有します。Vを使用したr\_{ec}（スキーム1と同様）と、ekを使用したr\_{pq}（スキーム2と同様）です。
- r\_{ec}とr\_{pq}を結合するために、ドメイン分離されたハイブリッドコンバイナーを採用します。

```
r = SHA3-256(DS || r_ec || r_pq || epk || ct || viewing_pk_ec || ek)
```

### セキュリティに関する考慮事項

[[Post-Quantum|ポスト量子]]匿名性はML-KEMの暗号文に**完全に**依存しているため、セキュリティのためには**少なくとも1回の**非カプセル化が必要です。したがって、「ビュータグをr\_{ec}のハッシュの最初のバイトにして、スキーム1と同じフィルタリングコストにする」といった「最適化」は、またしても壊滅的な最適化となります。

また、「スキーム1のメタアドレスを再利用する。スキーム3ではekをスキーム1のアドレスの末尾に追加することで機能するようだ」と考える人もいるかもしれません。これを行うと、本質的にスキーム1の履歴を引きずることになり、CRQCが到着した際には破綻すると考えられます。

## ペアワイズKEM-SAP schemeId 4,5

schemeId-2をペアワイズハイブリッド暗号化（同様にschemeId-3をschemeId = 5）でschemeId = 4に拡張できます。これは、共有秘密rを活用して、同じ送信者-受信者ペアのその後のトランザクションのために新しいナンスを導出することで実現します。これにより、ML-KEM暗号文（スキーム2および3）が削除され、元のephemeralPubKeyがschemeId-1よりもさらに小さい新しいephemeralPubKeyに置き換えられます。

読みやすさのため、スキーム4（ML-KEMのみのバージョン）のみを説明します。

### 数学

Gを楕円曲線群の生成元とし、H(\\cdot)をバイトからスカラーへの暗号学的ハッシュ関数とします。

- 受信者はランダムに秘密鍵kをサンプリングし、(dk,ek) \\leftarrow KeyGen(\\lambda)を実行し、K = kGである(K, ek)を公開レジストリに[[stealth-meta-address|ステルスメタアドレス]]として登録します。
- ステルスなペアワイズ鍵交換のために、送信者は（何らかの方法で）(K, ek)を取得し、(r,c) \\leftarrow Encaps(ek)を実行し、h = H(r)を計算し、P = K + hGを設定し、Pに0を送信し、その後cを公開します。
- 受信者、または受信者が非カプセル化鍵dkを委託したスキャンサービスは、まずr' = Decaps(dk,c)を非カプセル化し、h' = H(r')を再計算し、受信アドレスP' = K + h'Gを計算し、P =? P'をテストすることで、ステルスなペアワイズ鍵交換を照合できます。
- ワンタイム支払いの場合、受信者とすでにペアワイズ鍵rを共有している送信者は、ランダムに\\tilde{r}をサンプリングし、\\tilde{h} = H(r||\\tilde{r})を計算し、\\tilde{P} = K + \\tilde{h}Gを設定し、\\tilde{P}に資金を送り、その後\\tilde{r}を公開します。
- 受信者、または受信者がすでに交換されたペアワイズ鍵rを委託したスキャンサービスは、h'' = H(r||\\tilde{r})を再計算し、受信アドレスP'' = K + h''Gを計算し、P'' =? \\tilde{P}をテストすることで、ステルス支払いを照合できます。
- しかし、kを持っている受信者のみ（dkとrの両方を持っているスキャンサービスでさえも）、公開鍵\\tilde{P} = kG + \\tilde{h}Gに対するワンタイム秘密鍵k + \\tilde{h}で資金にアクセスできます。

### 標準

[[ERC-5564|ERC-5564]]は次のように拡張できます。

- 閲覧鍵ペア (v,V) をML-KEM鍵ペア (ek,dk) に置き換え、上記の数学に従ってアルゴリズムを変更します。`st:eth:0x<spendingPubKey><ek>`となります。
- ビュータグh^\*を保持し、hと\\tilde{h}から抽出された最上位バイトとして1バイトのサイズの\\tilde{h}^\*にも同様の処理を施すことができます。これにより、r'と\\tilde{r}を復元した後、h^\* =? H(r')\[0\]と\\tilde{h}^\* =? H(r||\\tilde{r})\[0\]をチェックできます（schemeId-1と比較して異なる比率ではありますが、別のECスカラー乗算、EC加算、ハッシュの代わりに）。

> 素朴なビュータグの導出は使用すべきではなく、匿名性リスクを排除するために、最初の連絡と実際の支払いメッセージの両方で、上記のビュータグと同じ処理を適用する必要があることに注意してください。

[[ERC-5564|ERC5564Announcer]]は、ステルス鍵交換にはschemeId-2（または3）を、ステルス支払いにはschemeId-4（それぞれ5）を使用できます。

公開[[stealth-meta-address|ステルスメタアドレス]]の登録と取得を一元化する[[ERC-6538|ERC6538Registry]]は、現在の形式 (`mapping(address registrant => mapping(uint256 schemeId => bytes))`) を維持できます。ただし、ML-KEM-768の場合、カプセル化鍵のサイズは1184バイトであり、バイト部分は1151バイト増加します。

### 以前のスキームへの回顧

- 送信者と受信者の間の最初の接触にはステルス鍵交換の追加オーバーヘッドがありますが、実際のステルス支払いのコストはスキーム1よりも低くなります。
- rは、送信者と受信者のペアごとに管理およびスキャンする新しい鍵となります（最初のマッチでショートサーキットされる可能性があります）。しかし、これは受信者がek（および/またはV）の代わりにrを委任できることを意味し、同時に、フォワードシークレットはペアワイズrによってよりきめ細かくなります。
- さらに、送信者が\\tilde{r}を公開せずに（rごとの）カウンターにした場合、\\tilde{h} = H(r||\\tilde{r})のランダム性は維持されますが、受信者は\\tilde{r}を保存する必要がなく、カウンターを追跡するか、単に0からスキャンするだけでステルス支払いを照合できます。実際、rの管理は以前のスキームのすべての共有秘密の管理よりも簡単です。

## 価値ある軽量な逸脱

### よりステルスなSAP

これまでのすべてのスキームの鍵ペアは鍵Kを維持していることに注意してください。数学的に言えば、KはVと同じ特性を持っています。つまり、1つの追加のephemeralPubKeyのコストで、送信者と受信者の間で追加の秘密を共有できます。これはSAPへの潜在的なアップグレードを開き、これを「よりステルスなSAP」と呼びます。これまでのすべてのスキームに適用できる、以下の追加ステップ（および既存のインフラストラクチャ[[ERC-5564|ERC5564Announcer]]と[[ERC-6538|ERC6538Registry]]と互換性のある新しいスキームにするためのいくつかの些細な[[ERC-5564|ERC-5564]]の変更）が必要です。

- 送信者はr\_Kをサンプリングします。
- R\_K = r\_KGとS\_K = r\_KKを計算します。
- R\_Kをアナウンスで公開します。
- アドレスBからP\_K = K + H(S\_K)Gに資金を送ります。
- P = K + H(S)Gはマッチング目的で保持され、アナウンスの[[stealth-address|ステルスアドレス]]フィールドに入ります。
- 送信者は別のアドレスAを使用してアナウンスを送信します。
- アナウンスと実際の支払いは異なるブロックで行うことができます。

具体的には、以下のようになります。

| 当事者 | 通知を認識するか | 実際の支払いアドレスを導出するか | 支出できるか |
| --- | --- | --- | --- |
| 送信者 | はい | はい | いいえ |
| vを持つスキャナー | はい | いいえ、暗号学的入力のみから | いいえ |
| k,vを持つ受信者 | はい | はい | はい |
| 外部の古典的オブザーバー | 直接ではない | 直接ではない | いいえ |

これにより、ステルス支払い（BからP\_Kへ）とアナウンス（呼び出し元Aとマッチング用の[[stealth-address|ステルスアドレス]]P）が効果的に切り離され、ステルス支払いがもはや明らかにステルス支払いとして分類されなくなります。さらに、これがもたらす大きな効果は、イーサリアムが他のブロックチェーンでのステルス支払いを促進するために使用できることです。つまり、イーサリアムはアナウンス用であり、実際の（誰もステルス支払いとは言えない）支払いは別のチェーンで行うことができます（外国のチェーンのアドレス指定スキームに対応するためにアルゴリズムを変更する方法が常にあると仮定して）。

重要: PQバージョンは、スキーム3と同様にS\_Kとr\_{pq}を組み合わせるべきであり、以下のようになります。

| オブザーバー | S_Kを知っているか？ | r_{pq}を知っているか？ | 支払いアドレスを再構築できるか？ |
| --- | --- | --- | --- |
| dkを持つ古典的スキャナー | いいえ | はい | いいえ |
| dkを持たない量子外部者 | はい | いいえ | いいえ |
| dkを持つ量子スキャナー | はい | はい | はい |

これは以前にも検討されたかもしれませんが、古典的な設定でこれを実現すると、スキーム1と比較してアナウンスコストが実質的に2倍になります（2つのephemeralPubKeyをアナウンスするため）。しかし、ML-KEMの追加を伴う[[Post-Quantum|ポスト量子]]設定では、このコストはほとんど無料になり、今ではさらに魅力的になっています。

### [[Post-Quantum|ポスト量子]]回復可能性

これは、任意のSAP（スキーム1でさえも）が検討できるアップグレードです。鍵kを、SAP操作（鍵管理中を除く）で決して使用されないシードsのハッシュとすることで、オンチェーンのアナウンス（ML-KEMによって保護された秘密rを持つ）と組み合わせることで、PQ回復可能性が得られます。つまり、量子インシデントが発生した場合、SAPメタアドレスの正当な所有者は、zkでk = H(s)を証明し、p = k + rの観測を使用して、アドレス回復において量子敵対者を打ち負かすことができます（強制可能で事前コミットされた回復ポリシー、または将来のコンセンサス介入に関する明示的な仮定がある場合）。これを完全なスキームに拡張することは、興味深く重要な将来の作業であり、検討する予定です。
