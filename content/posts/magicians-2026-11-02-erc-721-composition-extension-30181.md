自身のコンテナに資産を保持するトークン向けの[[ERC|ERC]]-721拡張です。トークンが存在する間はコンテナから何も持ち出せず、どのコントラクトもそのトークンが何で[[mint|ミント]]されたかを読み取ることができます。

これは、[@jay](https://ethereum-magicians.org/u/jay)が[[ERC-6551|ERC-6551]]スレッドで提案した2つの[[ERC|ERC]]-721拡張から発展したものです。1つはトークンを誰が[[burn|バーン]]したかを読み取るためのもので、現在は[[ERC-8423|ERC-8423]]となっています。もう1つは[[NFT|NFT]]の[[canonical assets|カノニカルアセット]]に関するものです。本提案は後者であり、資産が[[burn|バーン]]されるまで[[lock|ロック]]されたままになるトークンに焦点を絞り、前者の上に構築されています。

**問題点。** [[ERC-6551|ERC-6551]]のセキュリティに関する考慮事項では、アカウントを持つトークンのすべての購入者が知っておくべきケースが説明されています。アリスのトークンが10 ETHを保持するアカウントを所有しているとします。ボブがそのトークンを購入しようと提案し、アリスはアカウントを空にして提案を受け入れ、ボブは空のトークンを受け取ります。提案されている緩和策には、アカウントに留まることが期待される資産のリストと、所有者がそれらを取り出すのを防ぐ[[lock|ロック]]が含まれていますが、これらは[[ERC-6551|ERC-6551]]を汎用的に保つために、マーケットプレイスや実装に委ねられています。本提案は、ある種のトークンに対してこれら2つの提案を採用します。共通のインターフェースがなければ、マーケットプレイス、[[indexer|インデクサー]]、または[[wallet|ウォレット]]は、メタデータ内の数値から検証可能な下限を判断できません。それは現在の残高に頼ることになりますが、それは今そこにあるものを伝えるだけで、留まることが保証されているものではありません。

**アイデア。** 金の指輪は、金細工師の仕事と、それが作られている金の2つのものを同時に持ちます。指輪を破壊せずに金を取り出すことはできません。自分の金を金細工師に持ち込むコレクターを想像してください。その作品はその金で作られており、金を取り戻すには作品を破壊するしかありません。オンチェーンでは、金はネイティブアセットまたは[[ERC|ERC]]-20トークンであり、作品は[[ERC|ERC]]-721トークンであり、それを破壊することが[[burn|バーン]]です。各トークンは、[[mint|ミント]]時に何で構成されているかを宣言し、トークンが存在する間は誰も操作できないコンテナにそれを保持します。[[burn|バーン]]後、その時点でトークンを所有していたアドレスのみが資産を取り出すことができ、それは[[ERC-8423|ERC-8423]]によって記録されます。

**インターフェース。**

```solidity
/// @dev このインターフェースのERC-165識別子は0xd60a6c7eです
interface IERC721Composition /* is IERC721, IERC721BurnRecord, IERC165 */ {
    /// @param asset  ERC-20コントラクト、またはネイティブアセットの場合は0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE (ERC-7528)
    /// @param amount 宣言された量（アセットの最小単位）、ゼロではない
    struct Constituent {
        address asset;
        uint256 amount;
    }

    /// @notice トークンごとに一度、それをミントするトランザクションで発行されます（バッチミントを含む）
    event CompositionDeclared(
        uint256 indexed tokenId,
        address indexed account,
        bytes4 accountType,
        bytes accountData,
        Constituent[] constituents
    );

    /// @notice 宣言されたコンポジション（ミント時に固定）、アセットアドレスでソート
    function compositionOf(uint256 tokenId) external view returns (Constituent[] memory constituents);

    /// @notice 構成要素を保持するコンテナ、そのタイプ、およびそれを検証するためのデータ
    function compositionAccountOf(uint256 tokenId)
        external
        view
        returns (address account, bytes4 accountType, bytes memory accountData);
}

```

`accountType`はコンテナのインターフェースの[[ERC|ERC]]-165識別子であり、コンテナは`supportsInterface`を通じてそれを確認します。[[ERC-6551|ERC-6551]]アカウントの場合、それは`0x6faff5f1`であり、`accountData`は`abi.encode(implementation, salt)`であり、`account`はこのチェーン、このコントラクト、およびこのトークンIDに対して[[canonical registry|カノニカルレジストリ]]が計算するアドレスでなければなりません。他のコンテナタイプは独自のデータを定義します。コンテナは[[ERC-8423|ERC-8423]]から指示を受けます。`burnedBy`は、誰が開けるかをコンテナが知る方法です。

**提案されるルール（要約）。**

1.  **[[burn|バーン]]されるまで[[lock|ロック]]される。** トークンが存在する間、コンテナはその資産を移動させるいかなる実行、承認、検証もしてはなりません。[[burn|バーン]]後、`burnedBy`によって返されたアドレスのみがそれらを移動できます。このルールはメカニズムではなく結果に関するものであるため、どのコンテナタイプでも満たすことができます。後で変更することはできず、他のいかなるチェーンでもコンテナは何も検証しません。
2.  **[[ERC-6551|ERC-6551]]アカウント**は、間違いやすい2つの呼び出しについてこのルールを明記します。[[burn|バーン]]前は、`isValidSigner`と`isValidSignature`は決してそのマジック値を返しません。[[burn|バーン]]後は、[[burner|バーナー]]に対してのみ返します。
3.  **トークンごとに1つのコンテナ**であり、他のトークンによって使用されてはなりません。トークンを自身のコンテナに転送することはできません。
4.  **[[mint|ミント]]時に固定。** コンポジションとコンテナは、[[burn|バーン]]後も決して変更されません。
5.  **下限。** [[mint|ミント]]トランザクションが終了した時点で、コンテナは宣言された各量を少なくとも保持し、宣言された量がコンテナが実際に受け取った量を超えることはありません。後で送られたものは余剰であり、コンテナ内に留まり、[[burn|バーン]]後に残りの資産とともに引き出されます。
6.  **トークンごとに1つのイベント**を[[mint|ミント]]時に発行し、バッチ[[mint|ミント]]を含む、2つの関数が返すのと同じデータを含めます。
7.  [[burn|バーン]]されたIDの**再[[mint|ミント]]は不可**であり、トークンの記録された[[burner|バーナー]]は決して変更されません。
8.  **[[revert|リバート]]なし。** 両方の関数は任意のIDに対して応答します。空のコンポジションは「宣言されていない」を意味し、「ゼロとして宣言された」ではありません。[[burn|バーン]]後も、それらは以前と同じ値を返します。
9.  **構成要素**は、[[ERC|ERC]]-7528を介したネイティブアセットと[[ERC|ERC]]-20トークンであり、それぞれ最大1回、アドレスでソートされ、量がゼロより大きいものです。保有者による転送なしに残高が減少する可能性のあるトークン（例えば、下方リベース、凍結可能または差し押さえ可能なトークン）は宣言すべきではありません。そのようなトークンの下限を保護できるコンテナはありません。

**各事実の読み取り元。**

| 事実 | 読み取り方法 | 発表元 | 変更元 |
| --- | --- | --- | --- |
| 宣言されたコンポジション（下限） | compositionOf | CompositionDeclared（[[mint|ミント]]時） | なし（[[mint|ミント]]時に固定） |
| コンテナ、そのタイプ、検証データ | compositionAccountOf | CompositionDeclared（[[mint|ミント]]時） | なし（[[mint|ミント]]時に固定） |
| トークンが[[burn|バーン]]された時点の所有者 | burnedBy ([[ERC-8423|ERC-8423]]) | ゼロアドレスへの転送 | [[burn|バーン]]のみ（一度限り） |
| コンテナが現在保持しているもの | 構成要素: balanceOf、またはネイティブ残高 | 本提案にはなし | その後の[[deposit|デポジット]]、構成要素の発行者によるアクション、[[burn|バーン]]後の引き出し |

**スコープ外:** [[ERC-8423|ERC-8423]]のような[[mint|ミント]]と[[burn|バーン]]、価格、評価、[[oracle|オラクル]]、リバランスとイールド、トークンの分割、[[NFT|NFT]]をコンテナ内に含むような他の資産タイプ（これらは別の提案で扱われる可能性があります）。

**関連する作業。** 2つの提案が最も近いので、まずそれらについて述べます。

| 提案 | 内容 | 本提案との違い |
| --- | --- | --- |
| [[ERC-3589|ERC-3589]] (2021年、停滞) | ETHとトークンを[[NFT|NFT]]に組み込み、[[burn|バーン]]時に返却します。コンポジションはトークンID内のハッシュです。 | 共有残高ではなくトークンごとに1つのコンテナ。コントラクトが読み取れるコンポジション。実装のプロパティではなくルールとしての[[lock|ロック]]。 |
| [[ERC-8060|ERC-8060]] (オープンPR) | ネイティブETHを[[NFT|NFT]]に埋め込み、[[burn|バーン]]によってのみ償還可能。 | 複数の資産。[[mint|ミント]]時に固定され、トークンごとに検証可能なコンポジション。[[burn|バーン]]はインターフェース外に留まる。 |

その他、本提案が基づいている、または異なる提案は以下の通りです。[[ERC-6551|ERC-6551]]はコンテナを提供し、上記の緩和策を提案しています。[[ERC-4353|ERC-4353]]は、[[mint|ミント]]時にトークンを[[stake|ステーク]]し、[[burn|バーン]]時にのみ引き出すことをすでに提案していました。[[ERC-7527|ERC-7527]]は、共有準備金に対する関数によって価格設定されたアンラップ時のプレミアムを返済します。[[ERC-998|ERC-998]]、[[ERC-7401|ERC-7401]]、[[ERC-5700|ERC-5700]]、[[ERC-7590|ERC-7590]]は、所有者が取り出せるコンテンツを[[bind|バインド]]します。[[ERC-5058|ERC-5058]]、[[ERC-5753|ERC-5753]]、[[ERC-6982|ERC-6982]]、[[ERC-7066|ERC-7066]]は、トークンのコンテンツではなく転送を[[lock|ロック]]します。[[ERC-8414|ERC-8414]]（オープンPR）は、異なる目的で同じコンテナアプローチに到達しています。[[ERC-7656|ERC-7656]]はカスタムコンテナとして機能する可能性があります。また、[[ERC-4626|ERC-4626]]のような共有コンテナは、下限がトークンごとにチェック可能でなければならないため、適合しません。見落としている先行技術へのポインタも歓迎します。

**検証がまだ必要とすること。** 上記のデータは、どのコンテナが資産を保持し、どのコードがそれを管理しているかを読者に伝えますが、そのコードが本当に資産を保持しているかどうかを伝えることはできません。読者は2つのコードを認識する必要があります。コンテナのコードとトークンコントラクトのコードです。なぜなら、コンテナは`burnedBy`が指名する人物のために開かれるからです。これは[[ERC-6551|ERC-6551]]が`ownerOf`に置く信頼と同じです。最小限のプロトタイプには、[[ERC-6551|ERC-6551]]アカウントとカスタムコンテナに対してこれを行い、所有者が空にできる通常のアカウントを拒否するリーダーコントラクトが含まれています。したがって、宣言されたコンポジションは、これらの条件下で読者がチェックできる下限であり、トークンの価値に関する声明ではありません。

**私の質問:** マーケットプレイス、[[indexer|インデクサー]]、または[[wallet|ウォレット]]にとって、`compositionAccountOf`によって返されるアドレス、タイプ、および検証データは、オンチェーンでコンテナを検証するのに十分でしょうか、それとも他に何か必要でしょうか？
