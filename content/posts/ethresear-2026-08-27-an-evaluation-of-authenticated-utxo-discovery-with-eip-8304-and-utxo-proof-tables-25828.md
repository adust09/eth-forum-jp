## ステータスとスコープ

[[glossary/EIP|EIP]]-8304はドラフト提案です。ここで参照されているネイティブUTXO設計は、最終化されたプロトコル仕様ではなく、イーサリアムリサーチの提案です。この記事で説明されている統合は実験的なものであり、どちらの提案の一部でもありません。

実装されたプロファイルには以下が含まれます。

-   標準のEIP-8304エントリタイプ0から6
-   アプリケーション固有の4トピック`UtxoCreated`イベント
-   フォーマットバージョン2を使用するブロックごとのUPTオブジェクト
-   選択されたレコードのオープニングマルチプルーフ
-   [[glossary/block-hash|ブロックハッシュ]]をキーとするノード永続化
-   UPTの一括取得
-   最近のオープニングルートチェック
-   プロセス内ウォレットキャッシュ

まだ含まれていないもの：

-   独立して認証された実行ヘッダー
-   それらのヘッダーに対するアカウントおよびストレージ証明のウォレット側検証
-   古いオープニングルートのためのアーカイブおよびバッチパスサービス
-   標準化されたUPT RPCまたはワイヤーフォーマット
-   UPTの可用性または保持ネットワーク
-   最終的な入力ごとの使用済み証人（spend witness）のレシートなし構築

プロトタイプは、`ethrex_queryEip8304Table`や`ethrex_getUtxoProofs`などのEthrex固有のRPC、および以前のフルログ実験での選択ログRPCを使用しています。これらは標準のEthereum JSON-RPCメソッドではなく、EIP-8304によって定義されていません。

## 発見の問題

アリスがボブのために1 ETHのUTXOを作成したとします。

```
UtxoCreated(
  source    = Alice,
  recipient = Bob,
  index     = 2191,
  value     = 1 ETH
)
```

ボブのウォレットは少なくとも以下を知る必要があります。

-   グローバルUTXOインデックス
-   送信元と受信者
-   値
-   作成ブロックとイベント位置
-   出力が現在未使用であるかどうか
-   偽造または省略された結果を拒否するための十分な認証済み証拠

この記事では、EIP-8304のイベント位置は次のとおりです。

```
(block_number, transaction_index, transaction_relative_log_index)
```

標準のJSON-RPCログオブジェクトはブロック相対の`logIndex`を使用するため、2つの表現を比較する実装はそれらを明示的に正規化する必要があります。

ネイティブUTXOの状態は、すべてのオープニングを完全に保持するわけではありません。各グローバルインデックスの[[glossary/spent-bit|使用済みビット]]と、最近のブロックごとのオープニングルートのリングを保持します。古いブロックごとのルートは後でバッチルートに封印される場合があります。

オープニングルートは、レコードと有効なMerkleパスが取得された後にのみレコードを認証します。それはどのオープニングがボブに属するかを明らかにせず、オープニングの値を供給せず、不足している兄弟ハッシュも提供しません。

したがって、発見には4つの異なる質問が含まれます。

| 質問 | 必要な証拠 |
| --- | --- |
| ボブはどこで言及されましたか？ | 完全なEIP-8304受信者範囲証明 |
| どのようなオープニングフィールドがコミットされましたか？ | ブロックのネイティブオープニングルートに対して証明されたオープニングレコード |
| そのルートを再構築するMerkleマテリアルは何ですか？ | 選択されたレコード証明または共有されたブロックごとのマルチプルーフ |
| 出力は今すぐ使用可能ですか？ | 認証されたカノニカルステートに対して証明された現在の使用済みビット値 |

現在の設計では、単一の構造がこれら4つの質問すべてに答えることはありません。

## 発見インデックスとしてのEIP-8304

EIP-8304は、順序付けされたブロックごとおよび集約されたインデックステーブルを作成します。標準のエントリタイプは次のとおりです。

| タイプ | インデックスされたコンテンツ |
| --- | --- |
| 0 | ブロックハッシュ |
| 1 | トランザクションハッシュ |
| 2 | 発行ログアドレス |
| 3 | topics[0]、通常はイベントシグネチャ |
| 4 | topics[1] |
| 5 | topics[2] |
| 6 | topics[3]、存在する場合 |

エントリはバイナリエンコーディングによって辞書順に並べられます。ログエントリには、ブロック番号、トランザクションインデックス、およびトランザクション相対ログインデックスも含まれます。

この順序付けにより、サーバーはボブのパディングされたアドレスを含むすべてのタイプ5エントリをバイナリ検索できます。一致する区間、隣接する非一致境界、関連するリーフインデックス、およびテーブル長を含む証明は、そのテーブルから一致するエントリが省略されていないことを確立できます。

受信者範囲だけでは十分ではありません。どのコントラクトでもボブを`topics[2]`に配置できます。すべての候補位置で、ウォレットは少なくとも以下も認証する必要があります。

-   タイプ2: ネイティブUTXOボールトアドレス
-   タイプ3: `UtxoCreated`イベントシグネチャ

イベントスキーマがより多くのオープニングフィールドを公開する場合、他のトピックエントリを要求できます。

## プロトタイプで探求された3つの方法

これらは評価された3つの構成であり、可能なすべての発見設計の網羅的なリストではありません。

### 方法1 — 標準の`eth_getLogs`

ウォレットは、以下の情報を使用してブロック範囲のログを要求します。

-   UTXOボールトアドレス
-   `UtxoCreated`シグネチャ
-   ボブの受信者トピック

返されるログには、オープニングをデコードするために必要なすべてのインデックス付きトピック、イベントデータ、トランザクションメタデータ、およびブロックメタデータが含まれます。

![Screenshot (21)](https://ethresear.ch/uploads/default/optimized/3X/3/1/31e58b81a43ef001d13975574a13d1fe5cbe6791_2_690x223.png)

この方法は運用上魅力的です。

-   標準のRPCを使用します。
-   新しい可用性オブジェクトは必要ありません。
-   イベントデータを直接返します。
-   適切にインデックス化されたプロバイダーは、一般的なクエリに効率的に応答できます。

その核となる制限は信頼です。`eth_getLogs`は、プロバイダーが完全なカノニカル結果セットを返したことを証明しません。レシート証明は個々のログを認証できますが、それ自体では、範囲内のすべてのボブイベントが返されたことを証明しません。

ローカル実験で使用されたEthrexプロトタイプでは、`eth_getLogs`はブロックヘッダーブルームをチェックし、候補ブロックのブロックボディとレシートをロードします。したがって、これはEthrexのレシートスキャンベースラインとして説明されるべきであり、すべての本番プロバイダーのログインデックスアーキテクチャのベンチマークとしてではありません。

### 方法2 — カスタムフルログエントリを持つEIP-8304

最初の認証済みプロトタイプは、完全な生ログにコミットする非標準のタイプ7エントリを追加しました。概念的には次のとおりです。

```
SHA256(
  domain ||
  log_address ||
  encoded_topic_count || encoded_topics ||
  encoded_data_length || data
)
```

相互運用可能な仕様では、正確なドメインバイト、整数幅、バイト順序、およびリストエンコーディングを固定する必要があります。実装されたプロトタイプはドメイン文字列`EIP8304_LOG_V1`を使用しました。

ウォレットはまず、完全なボブの受信者範囲と、各候補位置での関連エントリを証明します。次に、選択された生ログのみを取得し、それぞれをタイプ7のコミットメントに対してチェックします。

![Screenshot (22)](https://ethresear.ch/uploads/default/optimized/3X/8/4/84bfab25884e635e89dca15f99cb675ae805c9dc_2_690x332.png)

この構成は、認証されたログペイロードと範囲の完全性を提供しますが、重要なコストがかかります。

-   EIP-8304のエントリセットを変更します。
-   インデックス付けされたすべてのログが別のテーブルエントリを追加します。
-   選択された生ログバイトは利用可能なままでなければなりません。
-   別途キャッシュされない限り、繰り返しのスキャンでも選択されたログが取得されます。
-   カスタムエントリはペイロードではアプリケーションに依存しませんが、プロトコルでは非標準です。

このプロトタイプは比較点として有用ですが、ここではEIP-8304の拡張としては提案されていません。

### 方法3 — UTXO証明テーブルを持つEIP-8304

UPT構成では、標準のEIP-8304タイプ0から6は変更されません。

EIP-8304は検索と範囲の完全性のためのみに使用されます。オープニングデータは、ネイティブUTXOのオープニングルートに対して別途認証されます。

![Screenshot (23)](https://ethresear.ch/uploads/default/optimized/3X/8/5/8556ead0be715751790ec057744dc84a32afaf86_2_690x332.png)

この分離は、構造が異なる順序付けと目的を持っているという事実を反映しています。

| 構造 | 順序付け | 目的 | 認証コミットメント |
| --- | --- | --- | --- |
| EIP-8304テーブル | エンコードされたエントリコンテンツとイベント位置 | ボブが言及されているすべてのイベントを検索 | EIP-8304テーブルルート |
| オープニングツリー / UPT | ブロック内のグローバルUTXOインデックス | オープニングフィールドの回復と証明 | ネイティブなブロックごとのオープニングルート |

UPTは[[glossary/consensus-state|コンセンサス状態]]ではありません。これは、ネイティブのオープニングルートによってすでにコミットされているデータのコンテンツおよび提供フォーマットです。

## イベントスキーマの区別

プロトタイプのベンチマークでは、このアプリケーション固有のイベントが使用されました。

```
event UtxoCreated(
    address indexed source,
    address indexed recipient,
    uint64 indexed index,
    uint256 value
);
```

そのログレイアウトは次のとおりです。

```
address   = UTXO_VAULT
topics[0] = keccak256("UtxoCreated(address,address,uint64,uint256)")
topics[1] = left_pad_32(source)
topics[2] = left_pad_32(recipient)
topics[3] = left_pad_32(index)
data      = uint256_be(value)
```

ネイティブUTXO研究提案は現在、以下を記述しています。

```
topics = [UtxoCreated_signature, source, recipient]
data   = (index, value)
```

この違いは、イベントデコード以上のものに影響します。

| プロパティ | 現在の研究提案 | プロトタイプスキーマ |
| --- | --- | --- |
| EIP-8304を通じて検索可能なソース | はい、タイプ4 | はい、タイプ4 |
| EIP-8304を通じて検索可能な受信者 | はい、タイプ5 | はい、タイプ5 |
| EIP-8304を通じて検索可能なインデックス | いいえ | はい、タイプ6 |
| イベントごとの追加EIPテーブルエントリ | いいえ | はい |
| トピックからの正確なインデックスとイベントの結合 | いいえ | はい |

プロトタイプスキーマでは、ウォレットはUPTの`index`、`source`、`recipient`を、同じイベント位置にあるタイプ6、タイプ4、タイプ5のエントリと相互参照します。

現在の提案のスキーマでは、UPT証明は依然としてオープニングフィールドを認証し、EIP証明はボールトによって発行されたボブイベントを認証します。ただし、オープニングリーフはトランザクション相対イベント位置にコミットしません。ブロックに同じ送信元と受信者を持つ複数の出力が含まれている場合、選択的サービスは、どちらのルートも壊すことなく、それらのイベント位置の関連付けを並べ替えることができます。

現在のイベントスキーマを使用する本番設計では、正確なイベント関連付けが必要かどうか、そしてもし必要ならそれをどのようにバインドするかを決定する必要があります。オプションには、レシート/ログ証明、オープニング設計における明示的な位置コミットメント、十分なデータを持つカノニカルな導出ルール、またはイベントスキーマの変更が含まれます。プロトタイプのタイプ6バインディングは、現在のネイティブ提案のプロパティとして提示されるべきではありません。

## UTXO証明テーブル

### オープニングツリー

Ethrexプロトタイプは、オープニングリーフを次のように定義しています。

```
opening_leaf = keccak256(
    uint64_be(index) ||
    source ||
    recipient ||
    uint256_be(value)
)
```

プリイメージは80バイトです。リーフはグローバルUTXOインデックスによって順序付けされ、次の2のべき乗までゼロハッシュでパディングされ、順序付けされたペアで折りたたまれます。

```
parent = keccak256(left || right)
```

これらのバイトレベルおよびパディングルールはプロトタイプルールです。これらはネイティブUTXO仕様の一部となるか、その仕様が採用するカノニカルなオープニングツリー定義に置き換えられる必要があります。

### レコード形式

各プロトタイプレコードは、転送エンコーディング前は88バイトです。

```
UtxoProofRecord
├── index:                          uint64   // 8 bytes
├── source:                         address  // 20 bytes
├── recipient:                      address  // 20 bytes
├── value:                          uint256  // 32 bytes
├── transaction_index:              uint32   // 4 bytes
└── transaction_relative_log_index: uint32   // 4 bytes
                                                --------
                                                88 bytes
```

ブロックレベルのオブジェクトには以下が含まれます。

```
UtxoProofTable (prototype format version 2)
├── format_version
├── chain_id
├── vault
├── block_number
├── block_hash
├── openings_root
├── records[]          // 昇順のグローバルUTXOインデックス
└── internal_nodes[]   // キャッシュされたオープニングツリーの内部ハッシュ
```

`U > 0`レコードの場合、`P = next_power_of_two(U)`とします。レコードはリーフのプリイメージを提供し、プロトタイプは`P - 1`個の内部ハッシュを格納します。

内部ノード配列は、ノード側の証明生成最適化であり、暗号学的に必要なデータではありません。すべてのレコードを保持するノードは、すべての内部ノードを再構築できます。完全な評価では、再構築によって節約されるストレージと、内部ノードインデックスを保持することによって節約されるCPUおよびレイテンシを測定する必要があります。

### コンテンツ識別子

プロトタイプは以下を計算します。

```
table_hash = SHA256("UPT_BLOCK_V2\0" || canonical_ssz_bytes)
```

テーブルハッシュは、1つの完全なシリアライズされたUPTオブジェクトを識別します。これはコンセンサスルートではなく、サーバーが応答とともにそれを返すという理由だけで応答を認証するものではありません。

選択されたレコードは、そのオープニングリーフを再計算し、提供されたマルチプルーフを独立して認証されたネイティブのオープニングルートに折りたたむことによって認証されます。テーブルハッシュは、コンテンツアドレッシング、マニフェスト、ミラー、または可用性ネットワークに依然として役立つ可能性があります。

### 構築と永続化

ブロックが実行された後、プロトタイプUPTビルダーは以下を実行します。

1.  ブロックのレシートから、残存する`UtxoCreated`ログをパースします。
2.  デコードされたオープニングごとに1つのレコードを作成します。
3.  グローバルUTXOインデックスでレコードをソートします。
4.  連続しないインデックスまたは重複するイベント位置を拒否します。
5.  カノニカルなオープニングリーフとルートを計算します。
6.  キャッシュされた内部ノード表現を構築します。
7.  正確なブロックハッシュの下にRocksDBにオブジェクトを保存します。

ブロックハッシュキーは競合するフォークを分離します。カノニカルなRPC処理は、テーブルをロードする前に現在のカノニカルハッシュを解決しますが、そのハッシュを独立して検証することはウォレットの責任です。

最近のUPTが存在しない場合、プロトタイプは保持されているレシートからそれを再構築できます。これは実装上の便宜であり、履歴がプルーニングされた後の長期的な可用性ソリューションではありません。

## 受信者優先クエリプロトコル

ウォレットは、テーブル内のすべてのボールトアドレスまたはイベントシグネチャエントリを要求するわけではありません。これらの範囲は、総UTXOトラフィックとともにスケーリングします。まず、1つの完全な受信者範囲から開始します。

```
ethrex_queryEip8304Table(
    first_block,
    table_size,
    [{ typeId: 5, content: left_pad_32(Bob) }],
    [2, 3, 4, 6]
)
```

`[2, 3, 4, 6]`の候補フィールドは、プロトタイプの4トピックイベントに適用されます。現在のネイティブ提案に対するクエリでは、タイプ6は要求されません。

各テーブルについて、サービスは以下を返します。

-   一致するすべてのタイプ5受信者エントリ
-   存在する場合は、直近の下限および上限範囲境界
-   一致した各位置で要求された候補エントリタイプ
-   トランザクションハッシュを関連付けるために必要なトランザクションエントリ
-   テーブル長とリーフ位置
-   1つの共有テーブルマルチプルーフ

ウォレットは、テーブル証明、完全な受信者区間、および候補分類を検証します。ネイティブUTXOイベントを識別する発行アドレスとシグネチャを持つ位置のみを保持します。

## バッチ処理された選択レコードの取得

EIP-8304の検証後、プロトタイプはキャッシュされていないすべての位置を1つのリクエストで送信します（実装上の上限に従います）。

```
ethrex_getUtxoProofs([
  {
    blockNumber,
    transactionIndex,
    logIndex // transaction-relative
  },
  ...
])
```

サーバーはブロックごとに位置をグループ化し、以下を返します。

```
blocks[]
├── formatVersion, chainId, vault
├── blockNumber, blockHash
├── openingsRoot, rootStorageSlot
├── tableHash, total recordCount
├── selected records[]
└── one shared proofNodes[] set
```

返されたブロックごとに、ウォレットは以下を検証する必要があります。

1.  期待されるフォーマット、チェーンID、ボールト、およびブロックグループ化
2.  要求されたすべてのイベント位置が正確に1つのレコードを生成したこと
3.  予期しないまたは重複するレコードが返されなかったこと
4.  選択されたイベントスキーマで利用可能なすべてのトピックフィールドがEIP証明と一致すること
5.  オープニングリーフがインデックス、ソース、受信者、および値から再計算されること
6.  必要なすべてのマルチプルーフノードが存在すること
7.  未使用の証明ノードが受け入れられないこと
8.  マルチプルーフが認証されたオープニングルートに折りたたまれること

現在のプロトタイプは、実行RPCからオープニングルートのストレージ値を取得します。本番の[[glossary/light-wallet|ライトウォレット]]は、さらに、信頼できる実行ヘッダーに対してボールトアカウントとステートプルーフを検証する必要があります。

完全な本番検証チェーンは次のとおりです。

![Screenshot (24)](https://ethresear.ch/uploads/default/optimized/3X/2/5/251e38280cfb9956bf9fd36171ef74a792a59df2_2_634x500.png)

認証されたヘッダーとステートプルーフのステップがなければ、ウォレットはプロバイダーが相互に一貫したルートとデータを返したことのみを証明します。カノニカルなイーサリアムチェーンとの合意を証明するものではありません。

この区別は、EIP-8304テーブルルート、オープニングルート、キャッシュに使用されるブロックハッシュ、および使用済みビットにも同様に適用されます。

## ウォレットのキャッシュとリオーグ処理

プロトタイプは以下をキャッシュします。

-   検証済みのEIP-8304クエリ結果（範囲とテーブルの終了ブロックハッシュ別）
-   テーブルルートのルックアップ（ブロックハッシュ、ストレージスロット、ルート別）
-   検証済みのUPTレコード（正確なブロックハッシュとイベント位置別）

テーブルクエリを再利用する前に、テーブルの終了ブロックハッシュを再読み込みします。ハッシュが変更された場合、すべての発見キャッシュをクリアします。子孫ブロックはその親チェーンにコミットするため、カバーされた範囲内の任意のブロックが変更されると、その後のカノニカルハッシュも変更されます。

このチェックはローカルキャッシュの無効化に役立ちますが、両方のハッシュ値が同じRPCから来る場合、それ自体はトラストレスではありません。本番ウォレットは、キャッシュキーを認証されたカノニカルヘッダーと比較し、ファイナライズ済み、安全、未ファイナライズの履歴に対する明確なポリシーを定義する必要があります。

キャッシュはUPTに固有のものではありません。レシートベースのウォレットも、デコードされたオープニングを保持し、最近のサフィックスのみを再検証できます。将来のパフォーマンス比較では、両方のアプローチに同等の永続性とリオーグポリシーを与えるべきです。

## エンドツーエンドのライフサイクル

### 1. 作成

1.  アリスまたはプロトコル決済がボブのために出力を作成します。
2.  ボールトは次のグローバルUTXOインデックスを割り当てます。
3.  残存する`UtxoCreated`イベントがオープニングを記録します。
4.  実行がリバートされた場合、ログもオープニングも残りません。

オープニングの`source`は、UTXOトランジションによって記録されたエンティティであり、必ずしも外部トランザクション送信者ではありません。これは、スポンサー付きトランザクションやプロトコル決済にとって重要です。

### 2. ブロックコミットメント

1.  EIP-8304は、カノニカルなレシートから標準のアドレスおよびトピックエントリを導出します。
2.  エントリは関連するEIP-8304テーブルにソートされます。
3.  ネイティブUTXO処理は、オープニングをグローバルインデックスで順序付けし、ブロックごとのオープニングルートをコミットします。
4.  非コンセンサスUPTオブジェクトが構築され、ブロックハッシュの下に保存されます。

EIP-8304とオープニングツリーは同じ実行履歴から導出されますが、異なるクレームを認証します。

### 3. 発見

1.  ボブのウォレットは、要求された履歴を、利用可能な整列されたEIP-8304テーブルに分解します。
2.  すべての完全なボブの受信者範囲を証明します。
3.  ボールトとイベントシグネチャによって候補位置を分類します。
4.  それらの位置の選択されたUPTレコードを取得します。
5.  関連するオープニングルートを取得し、認証します。
6.  オープニングマルチプルーフとスキーマ依存の結合を検証します。
7.  認証されたブロックIDの下に検証済みレコードをキャッシュします。

### 4. 使用可能性と使用

UPTは、使用済みステータスが時間とともに変化するため、使用済みステータスを保存しません。ウォレットは、発見された各グローバルインデックスの現在の使用済みビットを取得し、認証された現在のステートに対してそれを検証します。

使用済み入力は最終的に、以下と同等のデータを必要とします。

```
index
creation_block
source
recipient
value
opening_position
opening_siblings
batch_siblings
```

最近のUTXOの場合、オープニング証明は最近のリングにまだ存在するルートで終了します。古いUTXOの場合、証人（witness）は、そのブロックごとのルートから封印されたバッチルートへのパスも必要とします。

現在のデモトランザクションフォージャーは、返された共有UPTマルチプルーフを各入力のカノニカルな使用済み証人（spend witness）に変換する機能はまだありません。作成ブロックのログを読み取り、オープニングツリーを再構築します。したがって、プロトタイプは発見証明の構成を実証するものであり、完全なレシートなしの支出パイプラインを実証するものではありません。

## オープニング証明の例

あるブロックが、グローバルインデックスの昇順で4つのUTXOを作成したと仮定します。

```
position 0: #40  Alice -> Dave      2 ETH
position 1: #41  Carol -> Erin    0.5 ETH
position 2: #42  Alice -> Bob       1 ETH
position 3: #43  Frank -> George    3 ETH
```

プロトタイプスキーマでは、ボブのイベント位置におけるEIP-8304エントリには以下が含まれます。

```
type 2: UTXO_VAULT
type 3: UTXO_CREATED_TOPIC
type 4: left_pad_32(Alice)
type 5: left_pad_32(Bob)
type 6: left_pad_32(42)
```

選択されたUPTレコードは次のとおりです。

```
{
  index: 42,
  source: Alice,
  recipient: Bob,
  value: 1 ETH,
  transaction_index: 7,
  transaction_relative_log_index: 2
}
```

オープニングリーフを`L40`、`L41`、`L42`、`L43`とします。

```
                         openings_root R
                          /           \
                  H01 = H(L40,L41)  H23 = H(L42,L43)
                     /       \          /       \
                   L40       L41      L42       L43
```

`L42`の選択された証明には、`L43`と`H01`に相当する兄弟マテリアルが必要です。

```
L42 = keccak256(uint64_be(42) || Alice || Bob || uint256_be(1 ETH))
H23 = keccak256(L42 || L43)
R    = keccak256(H01 || H23)

assert R == authenticated_openings_root
```

プロトタイプは、出力が以下の条件をすべて満たす場合にのみ受け入れます。

1.  EIP-8304証明が完全なボブの範囲と期待されるボールトイベントを確立していること。
2.  プロトタイプのタイプ6エントリがUTXOインデックス42と一致していること。
3.  選択されたオープニングが認証されたオープニングルートに折りたたまれること。
4.  現在の認証された使用済みビットがクリアであること。

タイプ6のチェックはプロトタイプスキーマに固有のものです。

## セキュリティ特性

コミットメントルートとカノニカルヘッダーが独立して認証されていると仮定すると、この設計は以下に対処できます。

| プロバイダーの挙動 | ウォレットのチェック |
| --- | --- |
| テーブルからボブのイベントを1つ省略する | 完全なソート済み受信者範囲とその境界を検証する |
| 別のコントラクトからのイベントを返す | 同じ証明された位置でボールトアドレスを要求する |
| 異なるイベントタイプを返す | 同じ証明された位置で作成シグネチャを要求する |
| オープニングフィールドを変更する | リーフを再計算し、オープニングルートに対して検証する |
| 要求されたUPTレコードを省略する | 選択されたすべてのイベント位置に対して正確に1つのレコードを要求する |
| 無関係な証明マテリアルを追加する | 未使用または重複するマルチプルーフノードを拒否する |
| 別のフォークからのデータを再利用する | 認証されたカノニカルブロックIDでキャッシュをキー付けする |
| 古い使用可能性を返す | 支出前に最近の認証済みヘッダーで支出済み状態を検証する |
| UPTまたはテーブルバイトを非公開にする | コミットメントでは防止されない。別のソースまたは保持されたウォレットデータを使用する |

コミットメントは整合性を提供し、ソートされたEIP範囲についてはクエリの完全性を提供します。データアベイラビリティは提供しません。

## プロトタイプのパフォーマンス観測

ローカルの[[glossary/devnet|開発ネットワーク (devnet)]]実験は、一般的なパフォーマンス結果というよりも、実装上の観測として解釈するのが最適です。

2つの認証済み方法は別々のdevnet実行で測定されたため、それぞれは同じ行のレシートベースラインと比較されるべきであり、他の認証済み方法と直接比較されるべきではありません。コールド値は初回スキャン測定値であり、ウォーム値は繰り返しスキャンの中央値です。

| 実験 | ウィンドウ | コールドレイテンシ、レシート / 証明パス | コールド応答、レシート / 証明パス | ウォーム中央値、レシート / 証明パス | ウォーム応答、レシート / 証明パス |
| --- | --- | --- | --- | --- | --- |
| カスタムフルログタイプ7 | 100ブロック | 12.592 / 268.189 ms | 134,642 / 1,947,887 B | 8.790 / 10.711 ms | 134,642 / 129,770 B |
| カスタムフルログタイプ7 | 150ブロック | 11.828 / 426.530 ms | 226,906 / 3,033,305 B | 9.903 / 12.630 ms | 226,906 / 218,698 B |
| EIP-8304 + UPT | 100ブロック | 15.563 / 307.525 ms | 188,625 / 658,745 B | 15.727 / 5.889 ms | 188,625 / 7,500 B |
| EIP-8304 + UPT | 150ブロック | 14.387 / 386.561 ms | 296,973 / 1,027,430 B | 15.757 / 4.777 ms | 296,973 / 11,323 B |

### キャッシュされていない発見

標準のレシートログパスは、最初のローカルスキャンでは高速でした。証明の構築と検証が少なく、UPTパスよりも転送データが少なかったです。

両方の認証済み方法は、以下の追加コストを支払いました。

-   ブロックウィンドウをEIP-8304テーブルに分解する
-   完全な範囲証拠を構築する
-   テーブルエントリとマルチプルーフを転送する
-   ウォレットでテーブル証明を検証する
-   選択されたペイロードまたはUPTレコードを取得し、認証する

UPTのオープニング証明自体は比較的コンパクトでした。コールド応答の大部分は、選択されたオープニングマルチプルーフではなく、EIP-8304の候補エントリとJSON表現から来ていました。

### 繰り返しの発見

カスタムフルログ方式は、選択された生ログの取得を継続したため、マッチ数に比例したペイロードコストを維持しました。

UPTプロトタイプは、検証済みのテーブル結果と選択されたUTXOレコードをキャッシュしました。したがって、同じ履歴スキャンを繰り返すには、主にブロックIDチェックが必要であり、オープニングデータはローカルで再利用されました。このキャッシュポリシーの下では、UPTパスは、新しい`eth_getLogs`呼び出しよりも高速に完了し、実質的に少ない応答バイトを取得しました。

これは、認証されたUPTレコードがキャッシュ可能で再利用可能であるという証拠です。これはキャッシュ同等性の比較ではありません。この実験では、レシートパスにウォレット側のデコード済みログキャッシュは与えられませんでした。同じ履歴出力をすでに保持しているレシートウォレットも、それらを再度ダウンロードすることを回避できます。

### 実験が裏付けるもの

プロトタイプは、以下の限定的な結論を裏付けています。

-   EIP-8304範囲証明とネイティブオープニング証明は、1つのウォレットフローで構成できます。
-   選択されたUPTレコードは、オープニングフィールドの生ログ取得を置き換えることができます。
-   共有されたブロックごとのマルチプルーフは、UTXOごとに1つの独立したオープニングパスを送信することを回避します。
-   現在の実装では、証明の構築と検証が、キャッシュされていない認証済み発見を支配します。
-   検証済みのオープニングレコードは、キャッシュが認証されたカノニカルブロックIDに紐付けられている場合、安全に再利用できます。

UPTが一般的に`eth_getLogs`よりも高速であること、ある認証済み方法が実装間で他方よりも高速であること、または測定された挙動がリモートの[[glossary/mainnet|メインネット]]インフラストラクチャに引き継がれることを確立するものではありません。

## 制限と今後の作業

1.  **ドラフト依存性:** EIP-8304とネイティブUTXO設計の両方が変更される可能性があります。
2.  **プロトタイプイベントスキーマ:** ベンチマークは、現在のネイティブ提案には存在しないインデックス付きUTXOインデックスに依存しています。
3.  **信頼できるヘッダーチェーンなし:** ルートとカノニカルハッシュは同じ実行エンドポイントによって提供されました。
4.  **最近のルートのみ:** 古いオープニングとバッチパスは提供されません。
5.  **UPT可用性モデルなし:** コミットメントは保持または提供を保証しません。
6.  **キャッシュ同等性ベースラインなし:** レシート結果はUPTレコードのようにキャッシュされませんでした。
7.  **ローカル環境:** ネットワークレイテンシ、リモートプロバイダーの制限、異種クライアントはモデル化されていません。
8.  **小さな測定セット:** この実験は、安定したテールレイテンシの主張には不十分です。
9.  **異なる認証済み実行:** カスタムタイプ7とUPTプロトタイプは、異なるdevnet履歴で測定されました。
10. **高密度なワークロード:** 他のアクティビティ密度やテーブルアライメントでは、異なるコストが生じる可能性があります。
11. **使用済み状態のベンチマークなし:** 測定されたスキャンはオープニングを発見しましたが、認証された現在の残高は計算しませんでした。
12. **最終的な使用済み証人（spend-witness）統合なし:** トランザクションフォージャーは、依然としてログからオープニングパスを再構築します。
13. **ノードコストモデルなし:** UPTのストレージ、構築時間、同期、プルーニング、および[[glossary/denial-of-service|サービス拒否]]の制限を評価する必要があります。
14. **標準化されたエンコーディングなし:** UPTオブジェクト、証明ノード形式、およびRPCメソッドは実装固有のままです。

## 結論

EIP-8304とネイティブオープニングルートは、UTXO発見の補完的な部分を解決します。

EIP-8304は、カバーされたテーブル内でボブが言及されているすべてのイベントが返されたことを証明できます。オープニングルートは、選択されたUTXOのフィールドを証明できます。UTXO証明テーブルは、ウォレットが完全なレシートや生ログをダウンロードすることなく、選択されたオープニングレコードと共有されたMerkleマテリアルを利用可能にすることで、これらのコミットメントを接続します。

この構成は、認証された発見方法として有望ですが、その価値は主に証明の構成と選択的なデータ取得にあり、確立された普遍的な速度上の利点にあるわけではありません。本番設計には、正確なスキーマバインディング、認証されたヘッダーとステートプルーフ、古いルートの証人提供、可用性インセンティブ、標準化されたエンコーディング、および発見証明から使用済み証人（spend witness）への完全なパスが依然として必要です。
