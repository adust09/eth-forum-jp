買い手と[[glossary/AI-agents|エージェント]]サービスプロバイダーが注文に合意した後、以前の合意を失ったり、誤って追加の支出を承認したりすることなく、そのスコープ、価格、期限、または受諾基準を変更することにどのように同意できるか、という狭い相互運用性の問題についてフィードバックをいただきたいと思います。

これは探索的な議論であり、割り当てられた[[glossary/ERC|ERC]]ではありません。既存の作業や適切な拡張ポイントがすでにこれをカバーしている可能性があります。具体的なインターフェースへのポインタは特に有用です。

## 具体的な例

買い手は3つのプロジェクトに関するレポートを100ユニットで注文し、期限は明日です。実行中に、買い手は10のプロジェクトとスプレッドシートを要求します。プロバイダーは追加で80ユニットとより長い期限を提案します。両当事者は以下の点について曖昧さのない回答を必要とします。

-   各当事者はどの正確な変更を承認しましたか？
-   変更はいつ有効になりますか？
-   追加資金が利用できない場合はどうなりますか？
-   すでに提出された作業にはどの基準が適用されますか？
-   遅延した署名や競合する変更が現在の合意を置き換えることはできますか？

通常のフォローアップメッセージだけでは、追加の支払いを承認するものではありません。新しいカタログオファーを公開することも、既存の注文を変更することへの同意を確立するものではありません。

## 提案される境界

候補となる標準は、既存のサービス注文に対する署名付き変更と、それを適用するための条件を記述します。発見、交渉戦略、モデル実行、品質評価、紛争、および一般的なエスクロー設計は、他のコンポーネントに委ねられます。

最初の実験プロファイルは意図的に小規模です。

-   買い手1人、プロバイダー1人、支払い資産1つ、決済ドメイン1つ。
-   不変のIDと改訂履歴を持つ、すでに承認された注文。
-   価格の上昇または価格の据え置き、および期限の延長または期限の据え置き。
-   変更は注文がアクティブな間、かつ成果物が提出される前にのみ行われます。
-   両当事者が正確な変更を承認します。沈黙もチャットメッセージも承認とはなりません。

部分的な完了、返金、プロバイダーの変更、および支払い資産の変更には、個別のプロファイルまたは代替注文が必要です。最初のプロファイルは、発生した権利を黙って書き換えることはありません。

## 候補となるメッセージと適用ルール

変更は以下を識別します。

```
Amendment {
  orderId: bytes32
  baseRevision: uint64
  baseTermsHash: bytes32
  newTermsHash: bytes32
  nonce: uint256
  validUntil: uint64
}
```

ローカル実験の場合、コミットされた条件は次のとおりです。

```
Terms {
  scopeHash: bytes32
  acceptanceHash: bytes32
  totalPrice: uint256
  deadline: uint64
}
```

`newTermsHash`は、曖昧な自然言語の差分ではなく、完全な新しい条件にコミットします。スコープと受諾文書は、その正確なバイトからハッシュ化されます。それらのコミットメントは、内容の品質や可用性を確立するものではありません。[[glossary/signers|署名者]]はこれらの文書と、読みやすい変更前/変更後の比較にアクセスできる必要があります。

この実験では、`chainId`と`verifyingContract`の[[glossary/domain-separation|ドメイン分離]]を伴う[[glossary/EIP-712|EIP-712]]を使用します。注文IDは、承認された買い手、プロバイダー、資産、および決済コンテキストに解決されます。これらのバインディングは、このプロファイルでは変更によって変更できません。

変更を適用するには、以下が必要です。

1.  注文がまだアクティブであり、`now < currentTerms.deadline`であること（変更を適用する直前の現在の権威ある改訂版を使用）。以前に合意された延長は、このチェックに使用される期限を置き換えます。このプロファイルには、個別の不変の変更カットオフはありません。
2.  現在の改訂版、条件ハッシュ、およびナンスが署名されたベース状態と一致すること。
3.  両方の署名が承認された当事者に対して有効であり、変更が期限切れになっていないこと。
4.  提供された新しい条件が署名されたコミットメントおよび選択されたプロファイルの制限と一致すること。
5.  追加資金（`newTerms.totalPrice - currentTerms.totalPrice`）が確保され、新しい改訂版が1つの権威ある[[glossary/State-transition-function|状態遷移]]としてアクティブになること。資金差分、期限チェック、改訂版、条件ハッシュ、およびナンスはすべて、同じ現在のベース状態を使用します。`100 -> 180 -> 220`の場合、追加分は80、次に40です。

いずれかのチェックが失敗した場合、現在の条件と残高は変更されません。成功した遷移は改訂版とナンスを進め、古い改訂版からの競合する変更を使用不能にします。いずれかの当事者は、個別のナンス進行を通じて未処理の変更署名を明示的に無効にすることができます。これは基礎となる作業をキャンセルするものではありません。

提出された作業は、この初期プロファイルにおける変更の適格性を凍結します。提出および受諾記録は、正確な注文改訂版、条件ハッシュ、および結果ハッシュをバインドします。より柔軟なマイルストーン変更には、既存の提出物と獲得金額を保護するための明示的なルールが必要です。

アダプターの承認は、自動的に資金提供の証明とはなりません。同一チェーンの実装では、資金提供とアクティベーションを1つの[[glossary/EVM|EVM]]トランザクションにすることができます。オフチェーンのマーケットプレイスでは、耐久性のある予約とリカバリー設計が必要であり、その信頼境界は明示的に述べられる必要があります。クロスチェーンのアトミック性は、この提案の範囲外です。

## 既存の作業との関連

-   [[glossary/ERC-8414|ERC-8414]]は、バージョン管理されたタスクテンダーとテンダーエコノミクスを提供します。この提案は、既存のサービス契約の変更に相手方が同意することについて尋ねています。これはテンダーの固定報酬を変更するものではありません。互換性のある統合には、リンクされた補足または代替の手段が必要となる場合があります。
-   [[glossary/ERC-8001|ERC-8001]]は、汎用的な[[glossary/AI-agents|エージェント]]調整と同意を提供します。中心的な疑問は、注文変更のセマンティクスが、個別の[[glossary/ERC|ERC]]ではなく、そのフレームワーク上のプロファイルであるべきかどうかです。
-   [[glossary/ERC-8412|ERC-8412]]は、事前登録された受諾基準に対応しています。変更は、対象となる将来の作業に対して新しい基準コミットメントを参照できますが、保護された提出物に添付された基準は保持されます。

これらは構成候補であり、統合がすでに実装されているという主張ではありません。

## 実装実験とFinchのユースケース

Finchの公開[[glossary/AI-agents|エージェント]]統合ドキュメントは、バージョン管理されたオファー、永続化されたコール権限、論理的な呼び出し、条件ハッシュ、および非同期の補足入力という有用な動機付けとなる例を提供します。提案された統合は、履歴サービスバージョンとディスパッチ記録を保持しながら、合意された注文条件の改訂レイヤーを追加するものです。これは提案されたユースケースであり、Finchのプロダクションデプロイメントや承認を主張するものではありません。

ローカルのJavaScript実験では現在、[[glossary/EIP-712|EIP-712]][[glossary/EOA|EOA]]署名、補足的なモック資金提供、古い改訂版の拒否、署名の無効化、および改訂版にバインドされた提出と受諾を試行しています。これは実行可能な[[glossary/State-transition-function|状態遷移]]マシンの実験であり、監査済みのエスクローコントラクトではありません。コントラクトウォレット署名、委任された権限、耐久性のあるストレージ、実際の資産転送、およびFinchアダプターは実装作業として残っています。

次の有用な相互運用性テストでは、あるクライアントが変更を作成し、別々に実装されたコンシューマーが公開されたテストベクトルを使用してそれを検証および適用することになります。

## レビュアーへの質問

1.  これは欠けている相互運用性の境界ですか、それとも既存のインターフェースで十分ですか？
2.  これは独立した[[glossary/ERC|ERC]]であるべきですか、[[glossary/ERC-8001|ERC-8001]]プロファイルであるべきですか、それともコマース/テンダー標準の補完であるべきですか？
3.  作業が提出された後に変更を凍結することは、合理的な最初のプロファイルですか？
4.  どの資金提供/アクティベーション保証が共通であるべきで、どれがアダプターに属すべきですか？
5.  別の実装で具体的なワークフローとテストベクトルを比較したいですか？

## 非拘束的なスコープ投票

この投票は方向性に関する助言的なフィードバックであり、[[glossary/ERC|ERC]]の承認投票ではありません。特に既存の作業との重複がある場合は、選択理由を説明してください。最初のフィードバック期間は2026年10月13日09:30 UTCに終了します（公開から約3日後）。技術的な異議は投票結果に関わらず関連性を持ちます。

-   サービス注文変更のための独立した最小限の[[glossary/ERC|ERC]]を検討する
-   これを既存の[[glossary/ERC|ERC]]のプロファイルまたは拡張として定義する
-   これをアプリケーション層に留める。まだ共有標準は必要ない
-   選択する前により多くの実装証拠が必要
